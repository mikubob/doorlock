### 关键设计点
1. 六道防线：顺序反转 / 分页截断检查 / 逐行字段校验 / 数据量闸门 / 事务替换 / 可观测。

## 追加：Lua 脚本外置 + 关于 Thread.sleep 的结论（同日）

用户 review 提了两个点，均已处理。

### 1. Lua 脚本外置（已改）
- 脚本从 Java 内联字符串抽到 `soft_common/src/main/resources/lua/release_lock.lua`（**新增 resources 目录**，soft_common 此前没有）。
- 加载方式：`RedisScript.of(new ClassPathResource("lua/release_lock.lua"), Long.class)`，静态字段 + `loadScript()` 私有方法做存在性校验（类加载期即失败 → 打包遗漏在启动阶段暴露）。
- **踩坑记录**：不要用 `new DefaultRedisScript<>(text)` 再 `setLocation(...)`——`sha1` 字段只在它作为 Spring Bean 被调用 `afterPropertiesSet()` 时初始化，手工 `new` 走不到。已反编译 `spring-data-redis 2.4.15` 确认 `RedisScript.of(Resource, Class)` 的 `getSha1()` 是**懒计算 + 双检 + 检查 `isModified()`**，安全。
- 资源打包已验证：`soft_common/target/classes/lua/release_lock.lua` 存在，与源文件 `diff` 一致（父 POM 里 `**/**` 那块 `filtering=true` **未**破坏 `.lua`，因为脚本里没有 `${}` / `@` 占位符）。

### 2. Thread.sleep 结论（未新增代码，原本已删）
- 确认全仓**已无** `Thread.sleep`（仅 `ScheduleSyncOnStartupRunner` 的 Javadoc 里提到旧实现，属说明文字）。原 `ScheduledTasks.executeOnStartup()` 的 `Thread.sleep(5000)` 在上一轮改造中已随 `@PostConstruct` 一并删除。
- 结论：`@PostConstruct` 里 sleep 不规范，三层原因——① 时机错且是"用时间赌正确性"（上下文未 refresh 完，sleep 完紧跟清空全表这种破坏性操作）；② 阻塞容器主启动线程，拖累 readiness probe 与优雅启停；③ 不可取消/无超时/无重试。
- **「延迟执行」不该用 sleep 表达**，按意图选：等容器就绪 → `ApplicationRunner` / `ApplicationReadyEvent`；等外部依赖 → 带退避的重试 / `RetryTemplate`；稍后异步 → 线程池 / 延迟队列；周期执行 → `@Scheduled`。
- 当前策略：同步失败即放弃、保留旧数据、等下一周期或手工触发。若将来要"OA 抖动自愈"，加**带退避的重试**（如 3 次 / 2s·4s·8s），不要把 sleep 加回来。
- 文档已补：`doc/T-01-...md` 的「防线 5」新增「为什么 Lua 脚本要放独立文件」小节，「防线 6」新增「为什么不再用 Thread.sleep」+ 按意图选工具的对照表；验收用例补 B-4（锁能正常释放）/ B-5（不会误删他人锁）。

## 追加 2：Lua 脚本改放 soft_main（用户指正资源位置，同日）

用户指出「我原来的配置文件都放在 `soft_main/src/main/resources`」。核实后确认这是**项目既有约定**，且先例明确：`CourseScheduleMapper.java` 在 `soft_mapper`，而 `CourseScheduleMapper.xml` 在 `soft_main/src/main/resources/mapper/`，配置写 `classpath:mapper/*.xml`。

**改动**：`soft_common/src/main/resources/lua/release_lock.lua` → **`soft_main/src/main/resources/lua/release_lock.lua`**；`soft_common/src/main/resources/` 整个目录删除（已确认 soft_common 下除 lua 无其他资源）。**Java 代码零改动** —— `ClassPathResource("lua/release_lock.lua")` 用的是 classpath 相对路径，与物理模块无关，classpath 在运行期合并。

**原理与边界（已实测）**：写了个 `ClassPathResource#exists` 探针验证——
- `soft_common/target/classes` + `soft_main/target/classes`（应用真实形态）→ `exists = true` ✅
- 仅 `soft_common/target/classes` → `exists = false` ❌

即 `RedisLockUtils` **运行期依赖 soft_main**；单模块复用会在启动阶段快速失败（`IllegalStateException`），不会静默降级成「无锁」。要恢复自包含只挪文件即可。

**打包验证（`mvn -B clean package -DskipTests`）**：
- fat jar 内条目 = `BOOT-INF/classes/lua/release_lock.lua` ✅
- `soft_common.jar` 内**无** lua 残留 ✅
- 源码 / `target/classes` / jar 内三处 MD5 一致 = `633809a4a1bc14d344daa061e39c9919`（filtering=true 未破坏脚本）✅
- 6 模块全绿，`Total time: 01:18 min`

**顺带修正两处此前的错误结论**（已同步进 MEMORY.md）：
1. 之前记的「`target/` 被 git 跟踪」是**错的**：`.gitignore` 有 `**/target/`，`git ls-files` 确认未跟踪，`mvn clean/package` 不影响 `git status`。
2. `soft_main/pom.xml` 自带 `<resources>` 块，**在本模块内覆盖**父 POM 配置 → soft_main 下所有资源（含 `.lua`）都按 `filtering=true` 处理（不是父 POM 那个 `**/*.*` 非过滤条目生效）。
