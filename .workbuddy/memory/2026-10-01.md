### 核心结论
- 原问题是**三层叠加**：① 生产 key/secret 明文进了 Git（安全事件，须 OA 侧吊销重发）；② 密钥写死在 static 常量里无法按环境切换；③ 工具类是静态方法 + 吞异常返回 null。
- 三者纠缠：**不 Bean 化就无法注入配置，不注入配置密钥就只能继续硬编码**——所以「破静态」是硬约束而非风格偏好。
- 新方案：`OaProperties(@ConfigurationProperties)` + `OaApiClient(@Component)` + `OaApiException`，整体删除 `OaRequestAPIUtils`（含 main 入口）。
- 八道防线：密钥完全外置（占位符 + 环境变量）／Bean 化／ObjectMapper 替代手拼 JSON／token 缓存（提前 5 分钟过期）／异常语义化（**空数组 ≠ 失败**）／启动期校验密钥非空快速失败／日志脱敏（顺带结掉 R-04）／连接 finally 释放。

### 关键设计取舍（值得复用）
- **密钥空值默认 + 启动即失败**：给「能跑通」的默认值会掩盖配置缺失，把问题推迟到线上首次同步。宁可启动失败。
- **上线顺序是硬依赖**：必须「先拿新密钥 → 再配环境变量 → 最后发布代码」，否则发布即启动失败。
- **本次强烈不建议代码回滚**：回滚会退回已被吊销的旧密钥，导致鉴权失败；如必须回滚需先与 OA 确认旧密钥有效性。
- `page-size` 从硬编码常量上移为配置，供 T-01 分页闸门共用同一语义（分页拉取本身仍未实现，属 T-01 遗留边界 3）。

### 与 T-01 的衔接
T-01 第七条预留的「改造为 `OaApiClient` 时只需把 `doSync` 首行换掉，校验与替换逻辑不受影响」在本文中兑现。
职责边界：**T-01 保证「拿到数据后不丢」，T-02 保证「密钥安全 + 拿不到时说得清原因」。**

## T-03 Excel 巡查结果导入 —— 完整解决计划书（仅文档，未改代码）

来源问题：`doc/项目TODO清单分析与解决方案.md` 中的 T-03【P1】，关联任务卡 IMP-03。

### 产出
- 新增 `doc/T-03-Excel巡查导入映射失效与解析中断-完整解决方案.md`，体例对齐 T-01/T-02 计划书（九章 + 附录）。

### 核心结论（T-03 真实根因，TODO 注释本身是误导）
- TODO 写「应该是没有读到数据的，需要排查原因」——**方向错**。数据读到了，是搬运时被静默丢掉。
- `BeanUtils.copyProperties`（Spring 版）**只在属性名相同且类型可赋值时才复制**。`CheckResultModel` 全是 `String`，`CheckResult` 的 `date` 是 `Date`、三个人数 + 三个是否列是 `Integer` → **该行实际只搬了 9 个 String 字段**，其余 7 个得默认值。而紧随其后 101~120 行又手工赋了这些值 → **这行既无用又误导**。
- 次级缺陷：① `Integer.parseInt` 遇到空/`-`/含空格 → NFE，`saveData()` 整批中断；② 日期只认 `yyyy-MM-dd`，中文 Excel 输出的 `2024/5/5` 直接抛；③ `item.getIsLate().length()` 无判空 → NPE；④ 每 100 条独立 `saveBatch`，**外层无整次导入事务**，第 3 批失败留下前 2 批脏数据；⑤ `count - 1` 统计错误（**EasyExcel 的 `invoke` 不回调表头行**，`count` 本就是数据行数）。

### 最容易被忽略的两个点（写进计划书）
- **`college` 无来源**：`CheckResultModel` 里根本没有该字段，导入记录 `college` 恒为 null；而**几乎所有统计 SQL 都按 `college` 分组/过滤**（`getCollegeStatistics`/`getMonthlyAbsenceDetailByCollege`/`findByCollege`…）→ 数据「导进去了但报表查不出来」。三种策略：S1 取上传人 `user.getCollege()`（推荐）/ S2 Excel 加学院列（会改模板）/ S3 保持空。
- **`@ExcelProperty(index = 1..17)` 按列序定位**（第 0 列被跳过）：若上传 Excel 插了列，字段会**整体错位且不报错**，比原现象更隐蔽。

### 方案骨架
显式映射（删 `copyProperties`）+ 容错解析（`parseIntSafe` / 五格式 `DateTimeFormatter` / `isYes`）+ 行级失败隔离（`invoke` 单行 try/catch，`RowParseException` 带行号）+ **整次导入一个事务**（`TransactionTemplate` 内分批 `saveBatch`，事务边界不受分批影响）+ `CheckResultImportResult` 回执。

### 必须先实测再动手的一点
`CheckResultServiceImpl#uploadCheckResult` 里那个 `transactionTemplate.execute` 只包住 `excelUtils.readScheduleExcel(file)` 这次**调用**，而 `invoke` 回调由 EasyExcel 内部驱动——**两者是否同一事务未知**，决定改造时事务边界放哪层（计划书用例 C-2）。

### 相关既有隐患（本方案不改，已记录）
- `arrival_rate` / `food_bring_rate` 是 `varchar` 却参与 `AVG()`，存量数据形如 `'96.15%'`，隐式转数行为依赖 `sql_mode`。
- `ExcelUtils.readScheduleExcel` 注释写「读取第二个 sheet 页」，实际 `doReadAll()` 读全部 sheet。
- `/schedule/upload` 只验用户存在，**无权限校验**（属 T-05 系列）。

## T-03 第二轮：两项遗留已决策并落地（编译通过）

用户对第一轮末尾提出的 4 个决策点全部选了「最稳妥档」：模板由**老师线下维护**（可能被改）、超限**整体拒绝**、
拒绝要**接口层可见**、列序**仅锚点告警**。

### 修掉一个我自己引入的逻辑错误（重要教训）
第一轮把 `max-rows` 判定放在 `invoke` 里抛 `RowParseException`，**完全失效**：
`data.add(convert(...))` 已执行、`successCount++` 已累加，抛异常只是让 `failCount++`，
**超出部分照常入库**（`fail-fast-on-error=false` 时）。且行号 `0` 无意义。
→ 根因：**「整份文件不可接受」与「某一行填错」是两类事，不能共用行级异常通道。**

### 改动
- **新增** `soft_service/.../listener/ImportRejectedException.java` —— 整次导入拒绝异常，含 `reason`。
- `CheckResultDataListener`：
  - 删掉 `invoke` 内的 max-rows 判定；
  - `doAfterAllAnalysed` 新增**两道整次导入闸门**（顺序：max-rows 超限 → fail-fast-on-error），
    均抛 `ImportRejectedException`，**都在 `persistAtomically()` 之前**，故零写入；
  - 新增 `invokeHeadMap` 锚点校验（「日期」是否在 `index=1`）：默认 `strict-head-check=false` 只告警 + 写回执，true 时拒绝整次导入；
  - 新增字段 `headWarning` / `headRowCount`，`getResult()` 抽出 `buildMessage()` 把告警并入 `message`。
- `CheckResultImportResult` 新增 `headRowCount`。
- `CheckResultImportProperties` 新增 `strictHeadCheck = false`。
- `CheckResultServiceImpl` 加 `@Slf4j`，捕获 `ImportRejectedException` 打 warn 后**原样上抛**。
- `ScheduleController` 加 `@Slf4j`，捕获 `ImportRejectedException` → `ApiResult.error("导入被拒绝：" + reason)`（code=400）。
- 三个 `application-*.yml` 增加 `strict-head-check: false`。

### 关键的框架行为（实测确认，值得记住）
- **EasyExcel 2.x 的 `@ExcelProperty`：`index` 优先于 `value`**，`value` 只在 `index` 缺失时兜底 →
  当前模型全部写了 `index`，所以**按列序定位是事实**，插列即整体错位且不报错。
- **`doAfterAllAnalysed` 里抛异常会被 EasyExcel 静默丢弃**：被 `catch (Exception e)` 包住后只打一条 warn 日志，
  然后继续返回结果 → 若不显式上抛，接口会返回「成功 0 条」的 200 假成功。这是「整次拒绝要可见」必须单独处理的原因。

### 测试发现并修复的真实缺陷（重要）
`isYes()` 我第一版写成**全等比较**（`"是".equals(t) || "1".equals(t) || "Y".equalsIgnoreCase(t)`），
导致「是否迟到」列填 **「是，第 1 节迟到 10 分钟」** 这类**带补充描述的写法被判定为「否」**，
于是出现 **`remark` 里写着迟到、`is_late` 却是 0** 的数据自相矛盾。
> 原实现用 `"是".equals(...)` 同样有这个问题（原始代码里 `remark` 会收长文本但 `is_late` 不变），
> 但**我本有机会修掉却没修，还差点当成测试数据写错**——是 A-6 用例把它挡下来的。
**修复**：改为「以『是』/『1』/『Y』开头即判定为是」，并优先排除以「否/无/不」开头的否定写法。
新增 A-6b（否定描述 → 0）与 A-6c（肯定描述 → 1，且与 remark 一致）两条回归用例。

## 修复登录 500：`BindingException: Parameter 'updateTime' not found`（★ 重要框架坑）

用户报「`user` 明明没有 `updateTime` 字段，登录却报 `Parameter 'updateTime' not found. Available parameters are [param1, et]`」，
要求修掉所有同类错误。**已修复 + 全量编译通过**。

### 根因（与数据库、实体都无关，是 MyBatis API 用错）
`MyMetaObjectHandler` 用 `metaObject.hasSetter("updateTime")` 当防线，**但 `hasSetter` 对 `Map` 恒返回 `true`**：
- `MetaObject` 按被包装对象分派 Wrapper：普通实体 → `BeanWrapper`（查真实 setter，准确）；`Map`/`ParamMap` → `MapWrapper`（属性名合法即 `hasSetter=true`）。
- MyBatis-Plus `updateById` 时传进来的**不是实体而是 `MapperMethod.ParamMap`**（键 `param1`/`et`，正是报错里的 `[param1, et]`）。
- 于是 `hasSetter=true` → `getSetterType("updateTime")` → `MapWrapper.getSetterType` = `map.get(name).getClass()` → `ParamMap.get()` 对缺失 key **直接抛 `BindingException`**（不是返回 null）。
- **结论：只要实体没有 `updateTime` 字段 + 调用 `updateById`/`update(entity,wrapper)`，必炸。** 影响 `User`（登录）、`CheckResult`、`Notice` 等，属全站性问题。

### 精确复现的正确姿势（踩坑记录）
- **`SystemMetaObject.forObject(普通HashMap)` 复现不出来**：其 `MapWrapper.getSetterType` 返回 `Object.class` 不抛异常，会掩盖问题。
- 必须用 **`MetaObject.forObject(...)` + 真实 `MapperMethod.ParamMap`**，才会抛与线上**逐字一致**的
  `BindingException: ... Available parameters are [param1, et]`。
- 依赖：`mybatis-3.5.2.jar` + `mybatis-plus-core/extension/annotation-3.2.0.jar`；
  用 `D:/CodeEnvironment/JDK1.8/bin/javac` 编译，classpath 用 `cygpath -w` 转换。

### 修复
`soft_common/.../hanlder/MyMetaObjectHandler.java` 新增 `hasWritableTimeField()`：
1. `getOriginalObject() instanceof Map` → 直接 `false`（排除 ParamMap 场景）；
2. `hasGetter && hasSetter` 双重校验（保证 `getSetterType` 不炸）。
`insertFill`/`updateFill` 全部改用；顺手 `fieldType.equals(X)` → `X.class.equals(fieldType)`。
**安全性**：Map 参数本来就无法按字段 setter 填充（key 是形参名），跳过不丢功能。

### 附带修复
`sys_operation_log.user_id` 库里是 **`text`**，实体 `SwitchRecord.userId` 是 `Integer` →
`SwitchRecordMapper` 的 `selectByUserId` / `countByUserId` 改为 `user_id = CAST(#{userId} AS CHAR)`。
（该 Mapper 全用 `@Insert/@Update/@Select` 注解，**不经 MP 的 MetaObjectHandler**，与上面的 bug 无关。）

### 验证

- 修复后 `updateFill(ParamMap)` 无异常 ✅
- `javap` 确认字节码含 `instanceof java/util/Map` 分支 ✅

`information_schema` 核对（或跑对齐脚本）。`migration/` 目录**目前尚不存在**（只是文档里的规划），
所以 V 序号暂时是空的。

## 排查「登录不上」：SQL 日志是误导，真因是密码大小写（★ 值得记住的假象）

用户报 `ab` 账号登录不上，贴出的日志只有两条 SQL（`selectOne` 命中 1 行 + `UPDATE last_login`，
`Updates: 1`），看起来「像登录成功了」。**这两条 SQL 是正常的，不是报错**。

### 为什么日志会骗人（★ 根因机制，永久有效）
`UserDetailsImpl.loadUserByUsername` 的执行顺序是：
`getOne(user_name=?)` → **`updateLastLogin(...)`** → `new AccountUser(..., getUserAuthority(userId))`。
`updateLastLogin` 位于**密码校验之前**，而密码校验在 `DaoAuthenticationProvider` 里、`loadUserByUsername` 返回之后。
→ **密码错误时 `last_login` 一样会被写成功。** 所以「`UPDATE sys_user SET last_login` 成功 ≠ 登录成功」。

### 定位手法（可复用）
1. 直连 `POST /api/login`（context-path 是 `/api`，端口 9696）复现，看真实响应体：
   密码错 → **HTTP 200 + body `{"msg":"用户名或密码错误","code":406}`**（注意 HTTP 状态是 200，
   前端若只看 HTTP 码会误判）。`LoginFailureHandler` 把所有 AuthenticationException 都吞成这句话。
2. **验证码明文要从 Redis 取**：`/api/captcha` 返回的 `data.code` 是写死的 `200`（业务码），
   **不是**验证码文本；真值是以 token(UUID) 为 key 存在 Redis 里的（`redisUtils.set(key, code, 120)`，
   纯字符串无引号）。取法：`redis-cli -h 127.0.0.1 -p 6379 -a 123456 GET <token>`。
3. **离线判定密码**：直接对 `sys_user.password` 跑 bcrypt 比对（Python `bcrypt.checkpw` 可校验
   Spring 的 `$2a$10$` 哈希），不用反复打接口。**实测本库密码约定 = 工号**（抽样 120 个用户，
   `password == user_name` 全部命中），**唯一例外就是 `ab`**（`user_id=4`，管理员账号，
   密码是 `Admin@Rjxy`，**首字母大写**）。用户口述的 `admin@rjxy` 全小写对不上。
4. 辅助判据：Redis 里 `authority::4` 有值说明 `getUserAuthority` 从没抛异常；
   `user::ab` 为空说明 `LoginSuccessHandler` 从未执行（即从未登录成功）。

### 结论
`ab` 的哈希在**本地库与线上库完全一致**（`$2a$10$nuR894Rb...`），哈希本身没坏，
只是与用户以为的口令不匹配。**没有代码缺陷，不需要改代码。**
（如需重置：走 `/user/reset/{id}` 会重置为 `encode(userName)`，即 `ab`，但这会覆盖现有口令，先确认。）
