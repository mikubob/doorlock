### 0.2 鉴权说明

```
Authorization: Bearer {token}
```

- 普通用户 token：`subject = 用户名,userId`
- **开锁专用 token（调整）**：`subject = lock_password:{timestamp}:{userId}`
  - **【调整】** 携带真实 `userId`（原实现无用户信息，导致日志只能写 `-1`）
  - **【调整】** Redis Key 用 token 的 **MD5 摘要**（原取前 8 位，存在碰撞）
  - **【调整】** 有效期 10 分钟（原为长周期）

鉴权失败统一 JSON：

```json
{ "code": 401, "msg": "未登录或登录已过期", "data": null }
```

## 1 门锁授权管理

### 1.1 权限校验

#### 基本信息

| 项目 | 值 |
|---|---|
| 接口路径 | `/api/lock/permission/check` |
| 接口描述 | 校验当前登录用户是否有权操作指定门锁（返回判定链路，便于排障） |
| 请求方式 | GET |
| Content-Type | application/x-www-form-urlencoded |

#### 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| lockId | int | 是 | 门锁 ID |
| channel | int | 否 | 通道号，默认取门锁的 `channel` 列 |

#### 请求示例

```
GET /api/lock/permission/check?lockId=12&channel=1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

#### 响应参数

| 参数名 | 类型 | 说明 |
|---|---|---|
| data.hasPermission | boolean | 是否有权操作 |
| data.decideBy | string | 判定来源：`gray-off` / `super-admin` / `admin` / `permission` / `schedule-fallback` / `no-permission` |
| data.permissionId | long | 命中的授权记录 ID（`decideBy=permission` 时有值） |
| data.reason | string | 说明文案 |

#### 响应示例

```json
{
  "code": 0,
  "msg": "操作成功",
  "data": {
    "hasPermission": true,
    "decideBy": "permission",
    "permissionId": 1024,
    "reason": "命中角色授权（实训楼管理员）"
  }
}
```

#### 业务逻辑说明

判定链路（**六级**，见实施方案 1.4）：

1. 灰度开关 `lock.auth.enabled = false` → 放行（`gray-off`）；
2. 超级管理员 → 放行（`super-admin`）；
3. 管理员角色（`weight >= 5` 且 `role_code` 含 `ADMIN`）→ 放行（`admin`）；
4. **查 `sys_lock_permission`**：按 `subject_type`（user/role/dept）+ `scope_type`（lock/room/group）+ 通道 + 时间窗 + 有效期匹配 → 放行（`permission`）；
5. **排课回退**：`sys_course_schedule` 中 `JGH = 当前用户工号` 且 `JSH = 该锁教室` 且 `SKRQ = 今天` → 放行（`schedule-fallback`）；
6. 否则拒绝（`no-permission`）。

> 第 5 步用 `SKRQ`（上课日期 `yyyyMMdd`）而非 `ZC` + `XQJ`，因为教务已把单双周/调课/停课烘焙进 `SKRQ`。

### 1.3 新增授权

#### 基本信息

| 项目 | 值 |
|---|---|
| 接口路径 | `/api/lock/permission/add` |
| 接口描述 | 新增一条门锁授权 |
| 请求方式 | POST |
| Content-Type | application/json |

#### 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| subjectType | string | 是 | `user` / `role` / `dept` |
| subjectId | long | 是 | 主体 ID |
| scopeType | string | 是 | `lock` / `room` / `group` |
| scopeId | string | 是 | 范围 ID |
| channel | int | 否 | 通道号 1-8；**0 表示全部通道**，默认 0 |
| timeStart | string | 否 | 每日时段起 `HH:mm:ss`，为空不限 |
| timeEnd | string | 否 | 每日时段止 |
| validFrom | string | 否 | 生效时间 `yyyy-MM-dd HH:mm:ss` |
| validTo | string | 否 | 失效时间 |
| remarks | string | 否 | 备注 |

#### 请求示例

```json
{
  "subjectType": "user",
  "subjectId": 35,
  "scopeType": "lock",
  "scopeId": "12",
  "channel": 0,
  "timeStart": "07:00:00",
  "timeEnd": "22:00:00",
  "validFrom": "2026-03-01 00:00:00",
  "validTo": "2026-07-31 23:59:59",
  "remarks": "张三，实训室管理员"
}
```

#### 响应参数

| 参数名 | 类型 | 说明 |
|---|---|---|
| data.id | long | 新授权 ID |

#### 响应示例

```json
{ "code": 0, "msg": "授权成功", "data": { "id": 1025 } }
```

#### 业务逻辑说明

1. 校验 `timeStart < timeEnd`、`validFrom < validTo`；
2. 校验 `channel` 在 0-8 之间（0 = 全部）；
3. 校验 `scopeType='lock'` 时 `scopeId` 对应的锁存在；
4. 写入 `sys_lock_permission`，`create_by` 取当前登录用户；
5. **唯一约束** `uk_subject_scope`（`subject_type, subject_id, scope_type, scope_id, channel`）冲突时返回 `"该授权已存在"`，提示改用修改接口。
