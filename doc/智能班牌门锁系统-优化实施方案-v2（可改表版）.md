# 智能班牌门锁系统 — 优化实施方案 v2（可改表版）

> 本文档是《智能班牌门锁系统-优化实施方案.md》（**不改表版**）的**姊妹篇**，对应**允许修改数据库表**的路线。
>
> **两条路线互斥**：本文档所属路线允许 `ALTER TABLE` / `CREATE TABLE`；不改表版的全部方案（Redis 承载 + `remarks` 存 JSON）在本路线中**不再采用**。
>
> **与不改表版的核心差异**：
> | 维度 | 不改表版 | **本版（可改表）** |
> |---|---|---|
> | 授权数据 | Redis `lock:perm:*` | **`sys_lock_permission` 表**（可追溯、可审计、不丢） |
> | 流水扩展字段 | 塞进 `remarks` JSON（无法索引） | **独立列**（`card_no` / `result_code` / `trigger_type`，可索引可筛选） |
> | 设备状态 | Redis 心跳（掉电即丢） | **`sys_lock_device_status` 表**（历史可追溯） |
> | 任务日志 | Redis List（仅留 200 条） | **`sys_lock_task_log` 表**（完整历史、可分析） |
> | 通道号 | 继续占用 `remarks` | **独立 `channel` 列**，`remarks` 回归备注 |
> | 课表联动 | 配置文件承载节次时间 | **`sys_term_calendar` 表** + 配置文件 |
> | 数据可迁移性 | 依赖 Redis 持久化策略 | **标准 SQL，可备份可迁移** |
>
> **数据库具体改了什么** → 见配套文档《智能班牌门锁系统-数据库表变更清单.md》（逐表逐字段对照 + V1~V15 脚本全文 + 回滚）。
> **接口契约** → 见配套文档《智能班牌门锁系统-接口文档-v3（可改表版）.md》。

## 一、总体思路与决策

### 1.1 核心原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **先止血，再治病** | P0 必须先修 S-01/S-05/R-01/R-03/C-11 —— 这 5 条直接导致越权、认证绕过、假成功、数据清空、重复写入 |
| 2 | **设备为准，库为缓存** | 门状态以设备实际回执为准，DB 只记录"已确认执行成功"的状态 |
| 3 | **新表新名，不动老数据** | 新建 7 张表用新命名；存量表只**加列**，不删列、不改名、不改类型（唯一例外见 1.3） |
| 4 | **改动要有回滚开关** | 新增灰度开关 `lock.auth.enabled`，首次上线先关后开 |
| 5 | **契约变更同步 Apifox** | 按团队 ApifoxHelper 约定，所有 Controller 与 DTO/VO 必须写 Javadoc |

### 1.2 实施批次总览

| 批次 | 内容 | 是否涉及 DDL | 可独立发版 |
|---|---|---|---|
| **P0-A** | 纯代码修复（S-05、R-01、R-03、C-11、R-18/C-12） | ❌ 零 DDL | ✅ |
| **P0-B** | 授权模型 + 密码体系（V1、V8、V9、V12、V13、V14） | ✅ | ✅ |
| **P1** | 定时任务重构 + 课表联动基础（V5、V10、V4） | ✅ | ✅ |
| **P2** | 设备状态 + 刷卡流水 + 分组（V2、V3、V6、V7、V11） | ✅ | ✅ |
| **P3** | 代码治理 + 可观测性 | ❌ 零 DDL | ✅ |

### 1.3 关于"不改动现有列"的 3 个例外

本方案原则上不动现有列，但有 3 处**必须**修改类型，否则新方案跑不通：

| # | 表.列 | 改动 | 原因 | 前置动作 |
|---|---|---|---|---|
| 1 | `sys_operation_log.user_id` | `text` → `int` | `text` 无法建索引，而按人查流水是高频操作 | **必须先清洗非数字值** |
| 2 | `sys_lock_info.remarks` | `text` → `varchar(255)` | 通道号迁走后回归"备注"，`text` 无法建索引 | 先检查 `CHAR_LENGTH > 255` |
| 3 | `sys_lock_info.switch_status` | `NULL` → `NOT NULL DEFAULT -1` | 三态语义（1/0/-1）需要明确默认值 | 无 |

> 这 3 处已在《数据库表变更清单》第 6.2 节单列风险等级，其中 `user_id` 标为**高风险**（需数据清洗）。

### 1.4 授权判定优先级（**核心设计**）

```
① 灰度开关 lock.auth.enabled = false  → 放行（观察期）
② 超级管理员（role_code = 'SUPER_ADMIN'）  → 放行
③ 管理员角色（role_code 含 'ADMIN' 且 weight >= 5）  → 放行
④ sys_lock_permission 表命中（含时间窗/有效期校验）  → 放行
⑤ 排课回退：该教师在该教室当前时段有课  → 放行
⑥ 否则  → 拒绝，并落 sys_lock_permission 审计（result_code = 403）
```

**排课回退为什么用 `SKRQ` 而不是 `ZC` + `XQJ`**：

`sys_course_schedule` 中 `SKRQ` 是**上课日期（`yyyyMMdd`）**，教务系统已把单双周、调课、停课全部烘焙进去了。P0 阶段直接比对 `SKRQ = 今天` 即可，无需实现周历推算。`ZC` + `XQJ` 的周历推算留给 P1 的课表联动生成任务时使用（配合新增的 `sys_term_calendar`）。

## 三、P0 安全修复（S 级）

### S-01 无锁级授权

- **问题**：`SecurityConfig` 中 `anyRequest().authenticated()`，任何登录用户可开任意锁；`sys_menu` 有 `sys:lock:open` 权限码但无 `@PreAuthorize` 消费。
- **方案**：
  1. 建 `sys_lock_permission` 表（V1）；
  2. 新增 `LockPermissionService#decide(userId, lockId, channel)`，实现 1.4 的六级判定；
  3. 新增 `LockPermissionEvaluator implements PermissionEvaluator`，注册到 `SecurityConfig`；
  4. `SamrtLockController` 开锁入口加 `@PreAuthorize("@lockPerm.hasPermission(authentication, #lockId)")`；
  5. **内部方法调用绕过注解风险**：在 Service 层再调一次 `decide()` 兜底；
  6. 拒绝时写审计（`result_code = 403`）。

```java
@Service
public class LockPermissionService {

    /** 统一判定入口 */
    public LockDecision decide(Long userId, Integer lockId, int channel) {
        if (!authEnabled) return LockDecision.allow("gray-off");
        if (isSuperAdmin(userId))  return LockDecision.allow("super-admin");
        if (isAdmin(userId))       return LockDecision.allow("admin");

        LockPermission p = permissionMapper.match(userId, lockId, channel, LocalDateTime.now());
        if (p != null) return LockDecision.allow("permission:" + p.getId());

        // 排课回退：SKRQ = 今天 且 JSH 匹配 且 JGH = 当前用户工号
        int n = courseScheduleMapper.countTodayByTeacher(userId, lockId2Jsh(lockId), todayYyyyMMdd());
        if (n > 0) return LockDecision.allow("schedule-fallback");

        return LockDecision.deny("no-permission", 403);
    }
}
```

**授权表查询 SQL**（含时间窗与有效期）：

```java
@Select("SELECT p.* FROM sys_lock_permission p " +
        "WHERE p.status = 1 " +
        "  AND (p.valid_from IS NULL OR p.valid_from <= NOW()) " +
        "  AND (p.valid_to   IS NULL OR p.valid_to   >= NOW()) " +
        "  AND (p.channel = 0 OR p.channel = #{channel}) " +
        "  AND ( (p.time_start IS NULL OR CURTIME() BETWEEN p.time_start AND p.time_end) ) " +
        "  AND ( " +
        "        (p.subject_type='user' AND p.subject_id=#{userId}) " +
        "     OR (p.subject_type='role' AND p.subject_id IN (SELECT role_id FROM sys_user_role WHERE user_id=#{userId})) " +
        "      ) " +
        "  AND ( " +
        "        (p.scope_type='lock'  AND p.scope_id = CAST(#{lockId} AS CHAR)) " +
        "     OR (p.scope_type='room'  AND p.scope_id = (SELECT JSH FROM sys_lock_info WHERE lock_id=#{lockId})) " +
        "     OR (p.scope_type='group' AND p.scope_id = (SELECT CAST(group_id AS CHAR) FROM sys_lock_info WHERE lock_id=#{lockId})) " +
        "      ) " +
        "ORDER BY p.channel DESC, p.time_start DESC LIMIT 1")
LockPermission match(@Param("userId") Long userId,
                     @Param("lockId") Integer lockId,
                     @Param("channel") int channel,
                     @Param("now") LocalDateTime now);
```

- **数据库影响**：V1 新建 `sys_lock_permission`；V8 加 `sys_lock_info.group_id`。
- **验收**：A 老师开非本人授课教室的锁 → 403；开本人授课教室 → 成功但仅本人可开。

### S-02 全局单密码

- **问题**：`LockPasswordServiceImpl.getEnabledPassword()` 用 `last("LIMIT 1")` 只取一条，全系统共用一个开锁密码。
- **方案**：**不改表**（`sys_lock_password` 结构够用）→ 在代码层支持"多密码 + 作用范围"：
  1. 用 `description` 字段约定 scope 格式：`lock:12`、`user:35`、`*`（全局兜底）；
  2. `verify(input, scope)` 优先匹配精确 scope，未命中回落 `*`；
  3. 校验顺序：`lock:{id}` → `user:{id}` → `*`。

```java
public LockPassword resolve(String scope) {
    // 优先级：精确 scope > 全局兜底
    LockPassword p = baseMapper.selectOne(new QueryWrapper<LockPassword>()
            .eq("status", 1).eq("description", scope).last("LIMIT 1"));
    if (p != null) return p;
    return baseMapper.selectOne(new QueryWrapper<LockPassword>()
            .eq("status", 1).eq("description", "*").last("LIMIT 1"));
}
```

> **替代方案（更规范）**：若可继续改表，建议 V16 给 `sys_lock_password` 加 `scope_type` + `scope_id` 两列，用列而非 `description` 约定。**本方案默认走代码约定**，避免再动表。

- **数据库影响**：无（仅代码层）。
- **验收**：为 `lock:12` 设独立密码后，该密码只能开 12 号锁。

### S-03 登录防爆破缺失

- **问题**：`CaptchaFilter` 只拦 `/api/login`，不拦 `/lock/login`；`JwtAuthenticationFilter` L54-71 的 IP 限流**整段被注释**。
- **方案**：
  1. `CaptchaFilter` 拦截路径改为可配置集合，默认含 `/api/login` 与 `/api/lock/login`；
  2. 恢复限流，改为 **Redis 计数**（多实例一致）：`lock:login:fail:{account}:{ip}`，5 次失败封禁 5 分钟；
  3. 封禁记录落库到 `sys_operation_log`（`operation_method = 登录失败`），便于事后审计。

```yaml
yue:
  captcha-paths:
    - /api/login
    - /api/lock/login
lock:
  login:
    max-attempts: 5
    lock-seconds: 300
```

- **数据库影响**：无（Redis + 现有日志表）。
- **验收**：`/api/lock/login` 不带验证码 → 400；连续 5 次错密码 → 429。

### S-04 密码强度无约束

- **问题**：`setPassword` 仅校验非空 + `length() > 6` 报错（即**最大 6 位**），无字符要求。
- **方案**：抽 `PasswordPolicy.validate()`：长度 6~12、至少含数字/字母/符号中两种、禁弱口令（`123456`/`111111`/连续重复）。

- **数据库影响**：无。
- **验收**：`123456`、`111111`、`abcd` 被拒；`Ab12#x` 通过。

### S-05 认证绕过（**P0 最高优先级**）

- **问题**：`verifyOldPassword` 中 `if (getEnabledPassword() == null) return true;` —— 系统未设密码时，**任意密码均可通过**。
- **方案**：改为 `throw new BizException(ErrorCode.LOCK_PWD_NOT_INIT)`，前端引导走"首次初始化"流程（初始化接口需管理员权限）。

```java
public boolean verifyOldPassword(String input) {
    LockPassword p = getEnabledPassword();
    if (p == null) throw new BizException(ErrorCode.LOCK_PWD_NOT_INIT);   // 不再 return true
    return encoder.matches(input, p.getPassword());
}
```

- **数据库影响**：无。**改动量：1 行。优先级：最高。**
- **验收**：清空 `sys_lock_password` 后调改密接口 → 返回"密码未初始化"，不放行。

### S-06 开锁 Token 的 Redis Key 碰撞

- **问题**：`redisKey = suffix + "-lock_token-" + token.substring(0,8)` —— 同一毫秒签发的两个 token 前 8 位可能相同，A 的票据被 B 覆盖。
- **方案**：Key 改用完整 token 的 MD5 摘要；同时把 subject 改为携带真实 userId：

```java
// 原：subject = "lock_password:" + System.currentTimeMillis()
// 新：
String subject = "lock_password:" + System.currentTimeMillis() + ":" + userId;
String redisKey = suffix + "-lock_token-" + DigestUtils.md5DigestAsHex(token.getBytes(UTF_8));
redis.opsForValue().set(redisKey, userId, Duration.ofMinutes(10));   // 原为长周期，收窄到 10 分钟
```

- **数据库影响**：无。
- **验收**：同毫秒签发两个 token → Redis 出现两个不同 Key；旧票据不再互覆盖。

### S-08 密码设置接口无角色校验

- **问题**：`setPassword` / `resetPassword` 无 `@PreAuthorize`，任意登录用户可改全局密码。
- **方案**：加 `@PreAuthorize("hasAnyAuthority('sys:lock:op','sys:lock:password:set','ROLE_ADMIN')")`。
  - **注意**：`sys_menu` 中权限码 `sys:lcok:op` 是拼写错误，V12 已修正为 `sys:lock:op`。

- **数据库影响**：V12（数据订正）。
- **验收**：无 `sys:lock:op` 权限的账号调用 → 403。

### S-09 鉴权失败返回非标准响应

- **问题**：`AccessDeniedException` / `AuthenticationException` 落到容器默认 `/error`，前端拿不到 `ApiResult`。
- **方案**：`SecurityConfig` 注册 `authenticationEntryPoint` + `accessDeniedHandler`，统一输出 `{code:401/403, msg, data:null}`。

- **数据库影响**：无。
- **验收**：无 token → `{"code":401}`；有 token 无权限 → `{"code":403}`。

### S-10 CORS 全开

- **方案**：改配置驱动白名单（`cors.allowed-origins`），移除 `*`。

- **数据库影响**：无。

### S-11 Controller 实例字段共享状态

- **问题**：`SamrtLockController` L45 `private final ExecutorService executorService = Executors.newFixedThreadPool(10);`、L48 `private HashSet<...SearchResult> devicesList;` —— Controller 单例，`devicesList` 被并发请求共享。

- **数据库影响**：无。
- **验收**：20 并发搜索，结果互不串号。

## 四、P0 可靠性修复（R 级）

### R-01 开锁结果不校验（"假成功"，**最高优先级**）

- **问题**：`SmartLockSwitch.openDoor` 创建 `CompletableFuture` 后**从未 get/join**，方法 `void`；Controller 侧**先落库为"已开"再调 SDK**。设备离线/密码错/超时，数据库也已记成成功。
- **方案**：
  1. `openDoor` 改 `public static boolean`，阻塞等待（总超时 8s）；
  2. **调整顺序：先调 SDK，成功后再落库**；
  3. 无论成败都写日志（`result_code` + `result_msg` 进新列）；
  4. 加幂等令牌防连点（`sys_operation_log` 无需额外表，用 Redis `lock:op:nonce:*` 30s）。

```java
// SmartLockSwitch
public static boolean openDoor(String ip, int port, String sn, String channel, long timeoutMs) {
    CompletableFuture<Boolean> f = CompletableFuture.supplyAsync(() -> doOpen(ip, port, sn, channel));
    try {
        return Boolean.TRUE.equals(f.get(timeoutMs, TimeUnit.MILLISECONDS));
    } catch (TimeoutException e) {
        log.warn("openDoor timeout ip={} sn={}", ip, sn); return false;
    } catch (Exception e) {
        log.error("openDoor error ip={} sn={}", ip, sn, e); return false;
    }
}
```

```java
// Controller（顺序调整后）
boolean ok = SmartLockSwitch.openDoor(lock.getIpAddress(), lock.getPortNumber(),
                                      lock.getSnCode(), String.valueOf(lock.getChannel()), 8000);
switchRecordService.record(lock.getLockId(), userId, OperationMethod.OPEN.getCode(),
                           ok ? 0 : ErrorCode.LOCK_OPEN_FAILED, ok ? "开锁成功" : "设备未响应",
                           "manual", lock.getChannel(), null, request.getRemoteAddr());
if (!ok) return ApiResult.fail(ErrorCode.LOCK_OPEN_FAILED, "设备未响应，开锁失败");

smartLockMapper.updateSwitchStatus(lock.getLockId(), 1);   // 仅在真开后落库
```

- **验收**：拔网线开锁 → 返回失败、`switch_status` **保持 0**、`sys_operation_log` 有一条 `result_code != 0` 的记录。

### R-11 `loopCount` 语义不一致

### R-14 `countDay` 解析脆弱

- **问题**：`ScheduleLoad` 用 `char[]` 按原下标取数字；`trantoScheduleTask` 用 `Arrays.toString(int[])` 存 `[1, 2, 3]`；`setTimerTask` 用 `mapper.readValue(countDay, int[].class)` 回读 —— **两种写法互不兼容**。
- **方案**：统一为逗号分隔字符串，抽 `CountDayCodec`，**解码兼容旧格式**：

```java
public final class CountDayCodec {
    public static String encode(int[] days) {   // [1,2,3] -> "1,2,3"
        if (days == null || days.length == 0) return "";
        return Arrays.stream(days).distinct().sorted()
                     .mapToObj(String::valueOf).collect(Collectors.joining(","));
    }
    public static int[] decode(String s) {      // 兼容 "[1, 2, 3]" / "1,2,3" / "1234567"
        if (s == null || s.isBlank()) return new int[0];
        String t = s.replaceAll("[\\[\\]\\s]", "");
        if (t.contains(",")) {
            return Arrays.stream(t.split(",")).filter(x -> !x.isEmpty())
                         .mapToInt(Integer::parseInt).toArray();
        }
        return t.chars().map(ch -> ch - '0').toArray();   // 旧格式兜底
    }
}
```

- **数据库影响**：V10（可顺带清洗历史 `count_day` 为统一格式）。
- **验收**：用旧数据 `[1, 2, 3]` 重启，任务仍正确恢复；新写入为 `1,2,3`。

### D-11 详解（性能关键）

**问题**：`SmartLockMapper` 全部 5 处查询都是：

```sql
LEFT JOIN sys_classroom c ON l.JSH COLLATE utf8mb4_general_ci = c.JSH COLLATE utf8mb4_general_ci
```

列上套 `COLLATE` → **索引完全失效，走全表扫描**。

**方案**（V11 后）：

```java
// 方案 A：加 lock_id 后直接从教室定位门锁
@Select("SELECT l.* FROM sys_lock_info l WHERE l.lock_id = #{lockId}")
LockInfo selectByIdSimple(Integer lockId);

@Select("SELECT * FROM sys_classroom WHERE lock_id = #{lockId}")
Classroom selectByLockId(Integer lockId);

// Service 层合并（两次主键查询，均走索引）
public LockInfoVo getDetail(Integer lockId) {
    LockInfo l = mapper.selectByIdSimple(lockId);
    if (l == null) return null;
    Classroom c = classroomMapper.selectByLockId(lockId);
    return merge(l, c);
}
```

**方案 B**（若不加 `lock_id`）：去掉 SQL 中的 `COLLATE`（V11 已让两列 COLLATE 统一为 `utf8mb4_general_ci`）。

> ⚠️ 注意：`sys_lock_info` 建表时是 `utf8mb4_0900_ai_ci`（dump 显示），`sys_classroom.JSH` 是 `utf8mb4_general_ci` —— **两者确实不同**，所以原来需要 COLLATE。V11 已把 `sys_classroom.JSH` 的索引建立在该 collation 上，配合应用层两段查询可完全绕开该问题。

**生成逻辑**：

```java
@Transactional
public SyncResult syncFromCourseSchedule(String academicYear, String term, int week) {
    int removed = scheduleTaskMapper.deleteBySource("courseSchedule");   // 先清理旧任务
    // 换算该周日期范围
    TermCalendar wc = calendarMapper.selectWeek(academicYear, term, week);
    // 拉课表
    List<CourseSchedule> courses = courseScheduleMapper.selectByWeek(academicYear, term, week);

    int generated = 0, skipped = 0;
    for (CourseSchedule cs : courses) {
        // 排除节假日
        if (calendarService.isHoliday(cs.getSakrq())) continue;
        LockInfo lock = lockMapper.selectFirstByJsh(cs.getClassroomNumber());
        if (lock == null) { skipped++; continue; }

        LocalDate date = DateUtil.parseYyyyMMdd(cs.getSakrq());
        Period p = periodProps.of(cs.getClassPeriod());          // 配置的节次时间

        createTask(lock, date, p.getStart().minusMinutes(openAhead),
                   OperationMethod.AUTO_OPEN, "courseSchedule", cs.getId());
        createTask(lock, date, p.getEnd().plusMinutes(closeDelay),
                   OperationMethod.AUTO_CLOSE, "courseSchedule", cs.getId());
        generated += 2;
    }
    return new SyncResult(generated, skipped, removed);
}
```

## 十二、上线与回滚策略

### 12.1 灰度开关

```yaml
lock:
  auth:
    enabled: false        # 首次上线先关，观察 1 天再置 true
  schedule:
    enabled: false        # 课表联动同样先关
```

**首日流程**：
1. 部署代码 + 执行 DDL；
2. `lock.auth.enabled = false` → 观察 1 天，记录"若开启会被拒绝"的请求（打日志不拦截）；
3. 确认无大量误拒绝后置 `true`。

### 12.2 分批发布顺序

| 步骤 | 内容 | 可否独立回滚 |
|---|---|---|
| 1 | P0-A 代码上线 | ✅ 回退版本 |
| 2 | 执行 V13、V1~V12、V14 | ⚠️ 需按第八章回滚 SQL |
| 3 | P0-B 代码上线，`auth.enabled=false` | ✅ |
| 4 | 观察 1 天，置 `auth.enabled=true` | ✅ 改回 false |
| 5 | P1、P2 依次上线 | ✅ 各自回退 |

### 12.3 回滚触发条件

| 条件 | 动作 |
|---|---|
| 开锁成功率下降 > 10% | 立即置 `auth.enabled=false` |
| 出现 `Unknown column` 报错 | 检查 DDL 是否漏执行 |
| 开锁记录页面 500 | 检查 `V9` 与 Mapper 是否同批发布 |
| 任务重复触发 | 检查 `uk_lock_task` 是否建成 |
| 数据异常（状态大量变 -1） | 回滚 V8 的 `switch_status` 默认值 |

### 12.4 数据库回滚

完整回滚 SQL 见《智能班牌门锁系统-数据库表变更清单.md》**第八章**。回滚顺序与执行顺序相反。
