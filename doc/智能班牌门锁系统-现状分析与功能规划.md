## 一、结论摘要

### 一句话结论

**当前代码只完成了"远程开关门"这一件事，而一个校园门锁系统应有的"授权 → 感知 → 联动 → 运维"四个环节全部处于缺失或半缺失状态。**

### 三个最关键的判断

**判断一：安全模型是空的，这是目前最高风险。**

- 门锁接口只校验"是否登录"，不校验"能否开这把锁"。全校任意一个能登录后台的账号，拿到班牌 SN 就能开任意教室的门。
- 全系统只有一个共享开锁密码，且该登录接口免登录、无验证码、无频率限制。**破解一次 = 全校所有教室的门都能开。**
- 开锁日志用 `userId = -1` 记录密码开锁，出事查不到人，审计等于失效。

**判断二：SDK 能力利用率约 1.4%，最大的价值点被浪费。**

- `DoorAccessIO.jar` 提供 **296 个 Door8800 命令类**（Card 18 / Data 30 / DateTime 6 / Door 68 / Holiday 9 / Password 10 / System 131 / TimeGroup 5 / Transaction 16）。
- 代码实际只调用了 **4 个命令**：`SearchEquptOnNetNum`、`HoldDoor`、`CloseDoor`、`ReadWorkStatus`。
- 最核心的**刷卡流水采集（`ReadTransactionDatabase`）完全没接**——学校最关心的"谁、几点、进了哪间教室"目前一条数据都拿不到。

**判断三：项目里"该有的料"其实都已经备好了，缺的是接通。**

- 仓库里已有全套课表数据同步：`sys_course_schedule` 每天凌晨 3 点从 OA 拉取全校排课，含学年、学期、**教学周次（`ZC`）**、周几、节次、教室号、教师工号、教师姓名、上课日期。
- 仓库里已有完整审批流引擎：`Flow` / `FlowTask` / `FlowController` / `FlowService` / `ApproveParam`。
- 但门锁的定时任务仍然只支持**手工配置"周几 + 几点"**，配不出单双周，也无法按排课自动开关；教室借用审批与门锁授权之间**没有任何连线**。

### 问题分布统计

| 级别 | 含义 | 数量 |
|---|---|---|
| S 级 | 安全问题，可导致越权开门 / 数据泄露 | 11 |
| R 级 | 可靠性与并发问题，可导致功能实际失效 | 18 |
| D 级 | 数据模型与表结构问题 | 13 |
| C 级 | 代码质量与可维护性问题 | 15 |
| O 级 | 运维与可观测性问题 | 8 |
| **合计** | | **65** |

其中**必须优先处理的严重缺陷（会导致功能实际出错）有 4 条**：S-01（无授权模型）、S-02/S-03（密码体系）、R-01（开锁结果不校验）、C-11（批量导入锁设备逻辑错误）。

## 二、系统现状盘点

### 2.1 系统定位与边界

该仓库是一个**混合系统**，同时承载两套业务：

| 业务域 | 说明 | 本文档是否覆盖 |
|---|---|---|
| 教务 / 教学质量管理 | 教学巡查、课程、考试、学生信息、项目建设、审批流、教学评估 | 否（仅作为可复用资产引用） |
| **智能班牌门锁** | 电子班牌扫码开锁、远程开关门、开锁密码、定时开关锁、开关记录 | **是** |

判定为门锁子系统的代码集合：

- Controller：`SamrtLockController`、`LockPasswordController`、`SwitchRecordController`
- Service：`SmartLockService(Impl)`、`LockPasswordService(Impl)`、`SwitchRecordService(Impl)`、`ScheduleService(Impl)`
- Mapper：`SmartLockMapper`、`LockPasswordMapper`、`SwitchRecordMapper`、`ScheduleMapper`
- 设备通信：`SmartLockSwitch`、`CloseDoorCommand`、`SearchDeviceCommand`、`CommandAllocator`、`MyConnectorEvent`、`NetworkInfo`
- 调度：`QuartzConfig`、`QuartzJobFactory`、`SmartLockQuartz`、`ScheduleLoad`
- 模型：`LockInfo`、`LockPassword`、`SwitchRecord`、`ScheduleTask`、`Classroom`、`ScheduleTaskDto`、`WeeklyTimerRequest`
- 入口依赖：`SoftApplication`、`SecurityConfig`、`JwtAuthenticationFilter`、`AuthUrlConfig`

## 三、现有问题清单

### 3.1 S 级：安全问题

#### S-01【严重】门锁接口无"锁级"授权，任意登录用户可开任意教室的门

- **位置**：`SamrtLockController#updateSwitchStatus`（`SamrtLockController.java` L202-256）
- **现象**：
  ```java
  @PostMapping("/updateSwitchStatus")
  public ApiResult updateSwitchStatus(@RequestBody LockInfo lockInfo, Authentication authentication) {
      String username = authentication.getName();
      boolean isLockOnlyToken = "LOCK_ONLY_USER".equals(username);
      LockInfo byId = smartLockService.getByBoardSn(lockInfo.getBoardSn());
      if (byId == null) return ApiResult.error("你的sn不存在");
      // ……直接开锁，没有任何"该用户是否有权操作该锁"的判断
  }
  ```
- **影响**：只要持有任意有效用户 token（任何一个辅导员、行政人员、甚至只给某学院开的账号），构造 `boardSn` 即可开启全校任意一间教室的门。**这是可被直接利用的越权漏洞。**
- **建议**：引入门锁授权模型（见附录 B 的 `sys_lock_permission`），开锁前强制校验：
  1. 管理员角色 → 放行全部；
  2. 教师 → 仅放行"本人当前或近邻时段有排课"的教室（数据来自 `sys_course_schedule`）；
  3. 借用审批通过者 → 仅放行审批范围内的教室与时间窗；
  4. `LOCK_ONLY` 密码 token → 按 S-02 改造后绑定范围；
  5. 其余一律拒绝并记录尝试日志。

#### S-02【严重】全系统单一共享开锁密码，无绑定、无范围、无追溯

- **位置**：`LockPasswordController`（L45-110）+ `LockPasswordServiceImpl` + `sys_lock_password`
- **现象**：`sys_lock_password` 只保留**一条** `status = 1` 的记录，`getEnabledPassword()` 的查询是 `status=1 LIMIT 1`。任何人知道这一个密码，就能换取一个 `LOCK_ONLY` token。
- **影响**：
  1. 密码一旦外泄，**全校所有教室门全部失守**；
  2. 无法按教学楼 / 学院 / 教室划分范围；
  3. 无法追溯使用者：`updateSwitchStatus` 中密码开锁统一写 `userId = -1`，日志只能看出"有人用密码开的"。
- **建议**：
  - 短期：密码改为**按范围 + 按时段**（如"1 号楼保洁，仅 06:00-08:00"），并给每次密码使用记录来源 IP；
  - 中期：改为**一人一码**，或完全废弃共享密码，改由"扫码 → 审批 → 一次性临时密码"流程；
  - 长期：接 SDK 的 `WritePassword` 下发**设备本地临时密码**（可设有效期），实现"一间教室一个临时码"。

#### S-03【严重】开锁密码登录接口无防爆破措施

- **位置**：`LockPasswordController#lockPasswordLogin`（L45-77），白名单配置在 `application-prd.yml` L73-74
- **现象**：
  - `/lock/login` 在 `yue.url` 白名单中，`permitAll`；
  - `CaptchaFilter` 只处理 `"/api/login".equals(uri) && "POST".equals(req.getMethod())`，**不拦 `/lock/login`**；
  - `JwtAuthenticationFilter` 里的 IP 黑名单限流代码**已被整段注释**；
  - 密码长度上限 6 位。
- **影响**：可对 6 位以内数字密码进行无限次在线爆破。即使按最常见的 6 位纯数字且做满防护，100 万种组合；实际学校大概率用 6 位以内、含弱口令 —— **在线爆破几分钟到几小时即可命中，命中即等于拿到全校开门权**。
- **建议**（缺一不可）：
  1. 加图形/滑块验证码；
  2. 按 IP + 按账号双维度失败计数，5 次锁定 15 分钟，20 次进黑名单；
  3. 失败响应统一延迟 + 统一文案，不区分"密码错误/密码不存在"；
  4. 成功/失败均记录日志（IP、时间、UA）；
  5. 密码长度至少 6 位且禁止弱口令字典。

#### S-04【高】开锁密码强度校验缺失

- **位置**：`LockPasswordController#setLockPassword` L89-97
- **现象**：只校验 `password != null`、`trim()` 非空、`length() > 6` 报错。**没有最小长度、没有字符类型要求**。`"1"` 也能设置成功。
- **影响**：配合 S-03，爆破成本近乎为零。
- **建议**：长度 6-12 位；禁止纯重复字符、连续数字（`123456`、`000000`）、与工号/手机号相同；设置时给出强度提示。

#### S-05【高】开锁密码设置可被绕过旧密码校验

- **位置**：`LockPasswordServiceImpl#verifyOldPassword` L36-46
- **现象**：
  ```java
  LockPassword lockPassword = getEnabledPassword();
  if (lockPassword == null) {
      // 如果没有设置过密码，则不需要验证旧密码
      return true;
  }
  ```
- **影响**：只要 `sys_lock_password` 中启用记录被误删、被全部置为 `status = 0`、或表被清空，**任何已登录用户都可无凭证直接重置全局开锁密码**。结合"设置密码接口无角色限制"，这是一个完整的接管路径。
- **建议**：首次设置走独立的初始化流程（仅超级管理员 / 需二次验证）；`verifyOldPassword` 在找不到启用记录时应返回 `false` 并告警。

#### S-06【高】开锁专用 token 无范围绑定，且 Redis key 设计存在碰撞

- **位置**：`LockPasswordController#lockPasswordLogin` L60-66；`JwtAuthenticationFilter` L91-112
- **现象**：
  1. token 的 subject 仅为 `lock_password:{时间戳}`，**不携带任何可操作范围**，因此天然可用来开任意锁；
  2. Redis key 使用 `token.substring(0, 8)` 作为唯一标识 —— JWT 前 8 位是固定头部，**大量 token 的前 8 位完全一致**，会造成 key 互相覆盖，表现为"新登录把旧 token 挤下线"或更糟的校验错乱。
- **影响**：权限范围失控 + token 校验不可靠。
- **建议**：Redis key 改用完整 token 的 SHA-256 摘要；subject 中携带 `scope`（教室列表 / 楼栋 / 有效期），在 `updateSwitchStatus` 中校验。

#### S-07【高】设备通讯密码全项目硬编码

- **位置**：`SmartLockSwitch` L54、L114；`CommandAllocator` L51、L69
- **现象**：设备通讯密码固定为 `"FFFFFFFF"`（SDK 默认值），且写死在源码的多处。
- **影响**：任何能访问校园网、知道设备 IP 的人，都可用默认密码直接对门禁控制器下发开锁指令，**完全绕过本系统**。这是物理安全层面的重大风险。
- **建议**：用 SDK 的 `WriteConnectPassword` 批量改为强密码，配置化到 `application-prd.yml` 并加密存储；`ReadConnectPassword` 用于校验。

#### S-08【高】门锁设备管理接口无角色控制

- **位置**：`SamrtLockController#addLockInfo` / `#deleteLock` / `#updateLock` / `#searchcheck` / `#insertLock`
- **现象**：均无 `@PreAuthorize`。
- **影响**：任意登录用户可增删改锁设备记录，可把某把锁的 `JSH` 改成别的教室、把 `remarks`（通道号）改错，造成**开关错门**；也可批量删除设备记录，使定时任务全部失效。
- **建议**：设备管理限定管理员角色；`JSH` / `remarks` 变更需二次确认并留操作日志。

#### S-09【中】敏感信息通过控制台输出

- **位置**：`SamrtLockController#insertLock` L149（打印设备 SN / IP / 端口）；`ScheduleController#debugUserInfo` L288-318（**临时调试接口未移除**，会打印用户名、学院、缓存对象）
- **影响**：设备台账与用户信息泄露到日志文件/终端；`/debug/userInfo` 属于上线前应清理的调试后门。
- **建议**：移除调试接口；日志改用 `logback` 分级输出并脱敏（SN / IP 掩码）。

#### S-10【中】CORS 全放开

- **位置**：`SecurityConfig#corsConfigurationSource` L136-145
- **现象**：`addAllowedOrigin(ALL)` + `addAllowedHeader(ALL)` + `addAllowedMethod(ALL)`，注册到 `/**`。
- **影响**：任意站点可发起跨域请求。配合 S-01，钓鱼页面即可诱导已登录用户执行开锁。
- **建议**：管理端域名白名单化；门锁相关接口增加 CSRF 防护或自定义请求头校验。

#### S-11【中】设备搜索结果的暂存方式不安全且不可靠

- **位置**：`SamrtLockController` L48 `HashSet<...> devicesList;`（**Controller 单例的实例字段**）+ L112-159
- **现象**：搜索结果存在 Controller 成员变量中，下一次搜索会覆盖，任何人可触发覆盖。
- **影响**：并发搜索互相污染；`insertLock` 在未先调用 `searchcheck` 时 `devicesList` 为 `null` 直接 NPE。
- **建议**：搜索结果带会话标识与过期时间存入 Redis；`insertLock` 改为显式接收设备列表，或先做空判断。

### 3.2 R 级：可靠性与并发问题

#### R-01【严重】开锁指令的执行结果完全没有被校验

- **位置**：`SmartLockSwitch#openDoor` L46-103
- **现象**：
  ```java
  CompletableFuture<Boolean> futurePrice = new CompletableFuture<>();
  // …… 在 detail.Event 的各回调里 complete / completeExceptionally
  allocator.AddCommand(cmd);
  // 方法结束 —— futurePrice 从未被 get() / join() / 返回
  ```
  `CommandTimeout`、`ConnectorErrorEvent`、`PasswordErrorEvent` 全部只 `System.out.println` + `completeExceptionally`，而**没有任何人消费这个 Future**。
- **影响**：**只要 TCP 包发出去，接口就返回"开锁成功"，但门可能根本没开。** 门锁设备离线、IP 变了、通讯密码错、门锁故障，用户和前端都无法感知。这是可靠性上最严重的问题。
- **建议**：改为同步等待并设超时（如 `future.get(5, SECONDS)`），把结果向上返回；失败时回滚数据库状态、记录失败日志、返回明确错误。`closeDoor` 走的是 `CloseDoorCommand`，连 Future 都没有，需一并改造。

#### R-02【高】先写库、后发指令，状态与设备实际不一致

- **位置**：`SamrtLockController#updateSwitchStatus` L231-253
- **现象**：先 `smartLockService.updateSwitchStatus(...)` 落库，再 `SmartLockSwitch.openDoor(...)`。
- **影响**：指令失败时数据库已标记为"已开锁"，与设备实际状态相反，且无法自愈。
- **建议**：改为"先指令、后落库"，或落库时带上"指令结果 / 待确认"状态字段，由设备回执确认。

#### R-03【高】异步状态回写造成状态漂移与相互覆盖

- **位置**：`SamrtLockController#queryStatus` L440-473 + `SmartLockSwitch#queryDoorStatus` L141
- **现象**：`queryDoorStatus` 在回调里直接 `targetLockInfo.setSwitchStatus(dp.GetDoor(1)); smartLockService.update(targetLockInfo);`，而 `SmartLockMapper.update` **会一并覆盖 `JSH`、`switch_status`、`remarks` 三个字段**。
- **影响**：
  1. 用户刚开锁，`queryStatus` 的旧快照回写会把状态改回"关"；
  2. 若查询期间管理员修改了该锁的 `JSH` 或通道号，会被查询结果覆盖回旧值（**数据丢失**）。
- **建议**：状态回写只更新 `switch_status`（用 `updateSwitchStatus` 而非 `update`）；引入"最后指令时间"，早于该时间的设备快照不回写。

#### R-04【高】同锁并发开关无并发控制

- **位置**：`SamrtLockController#updateSwitchStatus` L214-231
- **现象**：`if (lockInfo.getSwitchStatus() == byId.getSwitchStatus())` 判重是"读-判断-写"三步非原子操作。
- **影响**：两个请求同时到达，都读到 `switch_status = 0`、都判定通过、都下发开锁指令并各写一条日志；日志重复、状态错乱。
- **建议**：用数据库行锁 / 悲观锁（`SELECT ... FOR UPDATE`）或 Redis 分布式锁按 `lockId` 加锁；接口增加幂等键。

#### R-05【高】静态全局状态导致线程间互相污染

- **位置**：`SmartLockSwitch` L27 `public static int StatusSwitch = -1;`、L28 `public static LockInfo lockInfo;`、L46 `public static void openDoor(...)`、L179 `public static void closeDoor(...)`
- **影响**：`StatusSwitch` / `lockInfo` 全局共享，多线程/多请求下互相覆盖。虽然 `queryDoorStatus` 已经改成传参（注释里也承认了"避免静态变量竞态条件"），但静态字段仍保留且 `openDoor` 仍为 static，属于遗留隐患。
- **建议**：删除静态可变字段；`SmartLockSwitch` 作为 Spring Bean 注入使用；改为无状态方法。

#### R-06【高】Controller 单例可变字段 + 空指针风险

- **位置**：`SamrtLockController` L48 `HashSet<SearchEquptOnNetNum_Result.SearchResult> devicesList;`
- **影响**：见 S-11。此外 `insertLock` 中 `if (!devicesList.isEmpty())` 未判 null，首次直接调用即 NPE。
- **建议**：移到方法局部变量或 Redis。

#### R-07【中】状态查询线程池过小且为全量轮询

- **位置**：`SamrtLockController` L45 `Executors.newFixedThreadPool(10)`、L448-465
- **现象**：固定 10 线程，对全部设备（旧库 `AUTO_INCREMENT = 22212`，即使实际几百台）逐一发起 TCP 查询；`CompletableFuture.allOf(...).join()` 无超时。
- **影响**：几百台设备时响应时间达数十秒；一台设备卡死会拖长整体；`join()` 无超时会长时间挂起请求线程。
- **建议**：改用 SDK 的 `BeginWatch` 长连接事件驱动 + 低频兜底校准；线程池改为有界队列 + 超时熔断；分页/分组查询。

#### R-08【中】SDK 超时与重试参数叠加，最坏耗时过长

- **位置**：`SmartLockSwitch` L57-62 与 L117-122
- **现象**：`tcp.Timeout = 5000`（连接）、`detail.Timeout = 3000`（命令）、`detail.RestartCount = 3`（重试 3 次）。
- **影响**：单次开锁最坏 `3 × 3000ms` 以上，用户点击后长时间无响应。
- **建议**：开锁这类实时操作应压低超时（如命令 1500ms、重试 1 次），并在接口层设总超时。

#### R-09【中】异常被吞，故障静默

- **位置**：`SmartLockSwitch#openDoor`（所有 `completeExceptionally` 无人消费）；`SamrtLockController#queryStatus` L456（`System.err.println` 后仍 `return lockInfo`）
- **影响**：设备故障、密码错误、超时全部静默，接口仍返回成功。
- **建议**：接入日志框架按 ERROR 级别记录，并在返回值中携带每台设备的执行结果。

#### R-10【高】一把锁只能挂一个定时任务

- **位置**：`QuartzConfig#createJobDetail` L32 `withIdentity("smartLockJob_" + lockId, "smartLockGroup")`
- **现象**：JobKey 只由 `lockId` 决定。而 `addTimer`（L370-372）与 `setTimerTask`（L502-504）在注册前都会 `if (scheduler.checkExists(jobDetail.getKey())) scheduler.deleteJob(...)`。
- **影响**：**同一把锁配置"早上 8 点开锁 + 晚上 9 点关锁"两个任务时，后注册的会把前一个任务删掉**，实际只有一个生效。而现实场景中"每间教室一对开关任务"是最基本的需求。
- **建议**：JobKey 改为 `smartLockJob_{lockId}_{taskId}`；删除任务时按 `taskId` 定位；建立 `taskId → JobKey` 映射表。

#### R-11【高】`loopCount` 语义在不同代码路径下不一致

- **位置**：
  - `SamrtLockController#addTimer` L362：`if (scheduleTask.getLoopCount() > -2)` → 走带次数的分支
  - `QuartzConfig#createCronTrigger(jobDetail, cron, repeatCount)` L66：`if (repeatCount != null && repeatCount >= 0)` → 才真正写入 `maxExecutionCount`
  - `SamrtLockController#setTimerTask` L492：`if (scheduleTask.getLoopCount() > 0)`
- **影响**：同一个 `loopCount` 值（如 `0` 或 `-1`）在"新增任务"和"改状态重新注册"两条路径下行为不同 —— 新增时无次数限制、改状态时可能变成有次数限制，任务可能被意外终止或永不终止。
- **建议**：明确 `loopCount` 语义（建议 `-1 = 无限`，`>0 = 剩余次数`），抽出统一的 `resolveTrigger()` 方法，禁止在两处分别判断。

#### R-12【中】执行次数更新非原子，无乐观锁

- **位置**：`SmartLockQuartz#execute` L64-65 读 `loopCount` 再 `updateLoopCount(currentCount - 1, taskId)`；`SmartLockMapper#updateLoopCount` L63-64 为无条件 UPDATE
- **影响**：多实例部署、任务重叠执行、或 Quartz misfire 重放时，次数会算错（可能变成负数或永不归零）。
- **建议**：改为 `UPDATE ... SET loop_count = loop_count - 1 WHERE task_id = ? AND loop_count > 0`，按影响行数判断。

#### R-13【中】定时任务无执行历史、无失败重试、无告警

- **位置**：`SmartLockQuartz#execute` L26-70
- **现象**：只有 `System.out.println("定时任务启动")` / `"定时任务结束"`；异常抛出 `JobExecutionException` 后无人处理；数据库无执行结果字段。
- **影响**：管理员无法知道"昨天早上的自动开锁到底成功没有"。这是教务场景中的高频问题（上课了门没开 → 投诉）。
- **建议**：新增 `sys_lock_task_log`（任务 ID、计划时间、实际时间、结果、失败原因、耗时）；失败重试 1-2 次；连续失败推送告警。

#### R-14【中】启动恢复定时任务的 `countDay` 解析方式极脆弱

- **位置**：`ScheduleLoad#run` L29-35
- **现象**：
  ```java
  char[] charArray = scheduleTask.getCountDay().toCharArray();
  for (int i = 0; i < charArray.length; i++){
      if(charArray[i] >= '0' && charArray[i] <= '9') {
          Days[i] = Integer.parseInt(String.valueOf(charArray[i]));
      }
  }
  ```
  逐字符提取数字，且**写入 `Days[i]` 时用的是原字符串下标 `i`**（不是过滤后的下标）。
- **影响**：`countDay` 存的是 `Arrays.toString(int[])` 的结果（形如 `"[0, 1, 2]"`），其中 `[`、`,`、空格、`]` 占位后，`Days` 数组会留下大量 `0` 值 → **本该只在周三开的门，可能变成周一周二周一都在开**，且 `Days` 长度与真实天数不符。
- **建议**：统一改用 Jackson 反序列化（`setTimerTask` 里已经在用 `mapper.readValue(countDay, int[].class)`），并统一存储格式为纯 JSON 数组、去掉 `Arrays.toString`。

#### R-15【高】`countDay` 字段存在两种互不兼容的解析方式

- **位置**：
  - 写入：`SamrtLockController#trantoScheduleTask` L523 `Arrays.toString(scheduleTaskDto.getCountDay())` → `"[0, 1, 2]"`
  - 读取 A：`ScheduleServiceImpl#insert` L39-65 **按字符遍历**，`switch(charArray[i])` 匹配 `'0'`~`'6'`，遇到 `'['`、`','`、`' '`、`']'` 全部落空
  - 读取 B：`SamrtLockController#setTimerTask` L483 `mapper.readValue(countDay, int[].class)` 按 JSON 解析
- **影响**：同一字段两种解析方式并存；`task_details` 的中文描述会包含错误/重复的周几；`ScheduleLoad` 解析出错（见 R-14）。**这是定时任务功能不稳定的根本原因之一。**
- **建议**：统一存储为 `"[0,1,2]"` 无空格 JSON；所有读取处统一用 Jackson；`ScheduleServiceImpl` 的文字拼装改为基于 `int[]` 生成。

#### R-16【高】开锁通道号依赖 `remarks` 文本，解析失败即抛异常

- **位置**：`SmartLockSwitch#openDoor` L65 `parameter1.Door.SetDoor(Integer.parseInt(Channel), 1)`、`CloseDoorCommand#execute` L38
- **现象**：`Channel` 来自 `LockInfo.getRemarks()`（`updateSwitchStatus` L235 / L245 传入 `byId.getRemarks()`）。
- **影响**：`remarks` 为 `null`、空串、或填写了非数字备注（如"1号门，靠走廊"）→ `NumberFormatException` → **开锁接口 500，且数据库状态已被改写**（因为先写库，见 R-02）。
- **建议**：`remarks` 拆出独立字段 `channel_no`（int，1-4，带默认值与校验）；开锁前校验范围；保留 `remarks` 作为真正的备注。

#### R-17【中】无幂等控制

- **位置**：`SamrtLockController#updateSwitchStatus`
- **影响**：前端重复点击、网络重试、脚本调用都会重复下发指令并重复写日志。项目里已有 `@RepeatSubmit` 注解与 `RepeatSubmitInterceptor`，但**门锁接口一个都没加**。
- **建议**：开锁接口加 `@RepeatSubmit`，或引入请求幂等键。

#### R-18【中】定时任务状态更新被重复调用

- **位置**：`SamrtLockController#updateTimerStatus` L327 与 L331
- **现象**：
  ```java
  scheduleService.updateStatus(scheduleTaskTemp);            // 第一次
  if (scheduleTask.getTaskStatus() == 1) { setTimerTask(...); }
  if (scheduleService.updateStatus(scheduleTaskTemp) > 0) {  // 第二次
  ```
- **影响**：多余的数据库写入；`taskStatus` 与 Quartz 注册之间可能出现"库已更新、Job 未生效"或反之的不一致窗口。
- **建议**：只调用一次，或用 `@Transactional` 包裹并明确顺序：先注册 Job，成功后再更新状态。

### 3.3 D 级：数据模型与表结构问题

#### D-01【中】`sys_lock_info` 存在废弃字段与字段挪用

- **现象**：`college`、`classroom` 为老字段，代码已改用 `JSH` 联表；`remarks` 被挪用为"开锁通道号"。
- **影响**：新老字段并存，维护者容易取错列；`remarks` 语义污染（见 R-16）。
- **建议**：下掉 `college` / `classroom`；新增 `channel_no`；`remarks` 归还备注用途。

#### D-02【高】`sys_operation_log.user_id` 类型为 `text`

- **现象**：语义是用户 ID，却是 `text` 类型，且密码开锁写 `-1`。
- **影响**：无法建索引、无法外键关联 `sys_user`，按用户查询日志性能差；`-1` 无法区分具体使用者。
- **建议**：改为 `int`，允许 `NULL` 表示"未知/系统"；新增 `operator_type`（1 用户 / 2 密码 / 3 定时 / 4 刷卡 / 5 系统）与 `operator_ref`（记录具体密码 ID 或卡号）。

#### D-03【高】`sys_operation_log` 无任何业务索引

- **现象**：仅 `PRIMARY KEY (switch_id)`。`SwitchRecordMapper` 提供按 `lock_id`、`user_id`、`operation_time` 范围查询，全部走全表扫描。
- **影响**：日志表会持续增长（现有 `AUTO_INCREMENT = 1631`，实际接入刷卡流水后增长会快几十倍），查询将迅速劣化。
- **建议**：加 `idx_lock_time(lock_id, operation_time)`、`idx_user_time(user_id, operation_time)`、`idx_time(operation_time)`；按季度分区或定期归档。

#### D-04【高】开关日志字段严重不足

- **缺失字段**：来源 IP、操作渠道（远程/定时/密码/刷卡/按钮）、执行结果（成功/失败/超时）、失败原因、教室快照（JSH / 教室名）、设备 SN、操作后设备返回码、请求耗时、关联任务 ID、关联审批单号。
- **影响**：出事无法追溯，无法做故障率统计，无法做异常分析。
- **建议**：见附录 B 的 `sys_lock_operation_log` 改造 DDL。

#### D-05【中】`sys_lock_info` 缺少设备台账字段

- **缺失**：设备别名/位置备注、门数（通道数）、在线状态、最后心跳时间、最后通讯时间、固件版本、设备型号、安装日期、维保到期日、责任人/负责人、所属校区/楼栋/楼层（当前靠 `JSH` 联表，但锁可能未绑定教室）。
- **影响**：无法做资产管理、无法做离线告警、无法做维保提醒。
- **建议**：补充上述字段，其中 `online_status` / `last_heartbeat` 支撑 O-01。

#### D-06【高】`sys_lock_password` 未纳入版本管理且缺少管理字段

- **现象**：三份 SQL dump 中均无该表建表语句。
- **缺失字段**：`create_user`（谁设置的）、`expire_time`（有效期）、`scope_type` / `scope_value`（适用范围：全校/校区/楼栋/教室）、`fail_count` / `locked_until`（防爆破）、`last_used_time`。
- **影响**：环境重建时表缺失；密码无法分级、无法过期、无法追溯设置人。
- **建议**：补齐 DDL 与字段，并纳入 `soft_main/src/sql/`。

#### D-07【中】`sys_schedule_task.count_day` 字段注释与实际严重不符

- **现象**：注释为"计数日期（如：2024-01-01）"，实际存 `"[0, 1, 2]"`。
- **影响**：误导后续开发者（本次分析中已确认代码里确实出现了两种解析方式，见 R-15）。
- **建议**：改注释为"重复执行的星期数组，0-6 对应周一至周日，JSON 格式"；补齐 `task_type`、`status`、`last_exec_time`、`next_exec_time`。

#### D-08【中】教室与锁的关联健壮性差

- **现象**：`sys_lock_info.JSH`（text）与 `sys_classroom.JSH`（varchar(50)）JOIN，且 SQL 中显式写了 `COLLATE utf8mb4_general_ci` 强制对齐字符集；两侧都无索引。
- **影响**：字符集/排序规则不一致时 JOIN 失败或走全表扫描；教室号一改，锁就"孤儿化"。
- **建议**：`sys_lock_info` 增加 `classroom_id`（bigint）外键指向 `sys_classroom.id`，`JSH` 仅作冗余展示；加索引；教室删除时校验是否存在关联锁。

#### D-09【中】`Classroom.boardSn` Java 类型与数据库类型不匹配

- **位置**：`Classroom.java` L31 `private int boardSn;` vs `sys_classroom.board_sn varchar(50)`
- **现象**：实际数据形如 `YS06H07260306000550`、`YS06H07260306000506`（非数字）。
- **影响**：`ClassroomController#list` 走 MyBatis-Plus 映射时对非数字值会抛 `NumberFormatException` 或静默丢值；`/classroom/list` 是白名单接口，影响面大。
- **建议**：改为 `String`。注意 `LockInfo.boardSn` 已是 `String`，两者需统一。

#### D-10【中】`selectByBoardSn` 返回单条，一间教室多锁即报错

- **位置**：`SmartLockMapper#selectByBoardSn` L34-40（`WHERE c.board_sn = #{boardSn}`，无 `LIMIT`），调用方 `smartLockService.getByBoardSn()` 返回 `LockInfo`（单对象）
- **影响**：若某教室安装了多把锁（如"教室 + 准备间"两把），查询会抛 `TooManyResultsException`，**开锁接口直接不可用**。
- **建议**：明确业务约束（一班牌一锁，加数据库唯一约束）或改为返回列表并由前端/班牌选择通道。

#### D-11【中】`sys_schedule_task` 缺少必要的任务元数据

- **缺失**：任务类型（每周固定 / 单次 / 按课表 / 按审批）、生效日期区间、排除日期（节假日）、作用对象（单锁 / 楼栋 / 学院）、创建来源。

#### D-12【高】仓库 SQL dump 与线上表结构已不同步

- **现象**：
  - `soft_manage.sql`（2024 版）、`soft_manage20251104.sql`、`soft_manage_all.sql` 中，`sys_lock_info` **都还是老结构**（含 `college` / `classroom`，无 `JSH`）；
  - 三份 dump 中**都没有 `sys_lock_password`**；
  - `sys_classroom` 只在 `sys_classroom.sql` 和 `soft_manage_all.sql` 中存在。
- **影响**：
  1. 按 dump 重建的环境**跑不通现有代码**（Mapper 里写的是 `l.JSH`）；
  2. 新同事按 dump 理解数据模型会得出错误结论；
  3. 密码表结构无版本记录，出问题无法追溯。
- **建议**：用线上 `mysqldump` 重新导出仅结构；把 `JSH`、`board_sn`、`sys_lock_password`、以及所有新增字段补进 dump；建立增量迁移目录（如 `soft_main/src/sql/migration/`）。

#### D-13【低】`sys_lock_info` 主键值域已消耗较大

- **现象**：老 dump 中 `AUTO_INCREMENT = 22212`。
- **影响**：说明历史上存在大量测试数据或反复导入；也可能存在历史脏数据（`JSH` 为空、`remarks` 非法）导致开锁异常。
- **建议**：上线前做一次数据体检：`JSH` 为空、`JSH` 在 `sys_classroom` 中不存在、`sn_code` 重复、`remarks` 非 1-4、`ip_address` 格式非法。

### 6.2 关键设计决策建议

| 决策点 | 建议 | 理由 |
|---|---|---|
| 授权粒度 | 用户 × 教室 × 时间窗 × 通道 | 满足"任课教师""借用者""保洁""管理员"四类角色 |
| 授权来源 | 排课（自动）+ 审批单（手动）+ 人工授（管理员） | 三条来源合并计算最终权限 |
| 状态权威 | **设备为准**，数据库为缓存 | 避免 R-02 / R-03 的状态漂移 |
| 指令模型 | 异步下发 + 回执确认 + 失败重试 + 执行日志 | 解决 R-01 |
| 事件模型 | `BeginWatch` 长连接为主，轮询兜底 | 解决 R-07 / O-01 |
| 任务模型 | 一把锁多任务；任务 = 策略（何时）+ 作用对象（哪些锁） | 解决 R-10 |
| 时间模型 | 支持"教学周 + 周几 + 节次"与"绝对日期时间"两种 | 解决 F-2-1 / F-4-2 |
| 日志模型 | 统一操作日志表 + 事件流水表，分渠道、带结果 | 解决 D-02 / D-03 / D-04 |

```sql
  ADD COLUMN `job_key`        varchar(128)    NULL COMMENT 'Quartz JobKey，支持一锁多任务',
  MODIFY COLUMN `count_day`   varchar(255) NULL COMMENT '重复执行的星期数组(JSON)，0-6对应周一至周日',
  ADD KEY `idx_job_key` (`job_key`);
```

## 附录 D：命名与规范问题清单

| 类别 | 问题 | 建议 |
|---|---|---|
| 类名拼写 | `SamrtLockController` → 应为 `SmartLockController` | 重命名 |
| 权限码拼写 | `sys:lcok:op` → 应为 `sys:lock:op` | 修改数据库 + 前端同步 |
| 菜单重复 | `sys_menu` 102「定时任务」与 103「定时计划」同 path 同 component，且 102 状态为 0 | 合并 |
| 命名冲突 | `ScheduleController`（教学巡查）与 `ScheduleTask` / `ScheduleMapper` / `ScheduleService`（门锁定时任务）语义冲突 | 前者改 `InspectionController` / `CheckResultController`；后者加 `Lock` 前缀 |
| 表名与实体名不一致 | 实体 `SwitchRecord` ↔ 表 `sys_operation_log`；实体 `LockInfo` ↔ 表 `sys_lock_info`；实体 `ScheduleTask` ↔ 表 `sys_schedule_task` | 统一为 `sys_switch_record`，或至少加注释标注 |
| 字段一物多用 | `remarks` 既是备注又是通道号；`loop_count` 既是配置的循环次数又是已执行次数 | 拆字段 |
| 注释与实现不符 | `sys_schedule_task.count_day` 注释"计数日期（如：2024-01-01）"；`ScheduleTask.timedOperation` 注释"0=关锁，1=开锁" 但代码只处理 1 | 同步修正注释 |
| 注释乱码 | `WeeklyTimerRequest.daysOfWeek` 的 Javadoc 出现 `��别代表周一到周日` | 修复 |
| 死代码 | `CommandAllocator#getTcpCommandDetail()`（测试设备）、`WeeklyTimerRequest`（未使用）、`SearchDeviceCommand.localIp`（未使用）、`MyConnectorEvent`（空实现）、`JwtAuthenticationFilter` 中被注释的限流代码 | 清理 |
| 调试残留 | `ScheduleController#debugUserInfo` | 移除 |
| 日志 | 全项目 `System.out.println` | 统一 `@Slf4j` + logback，分级并脱敏 |
| 事务 | 门锁相关 Service 无 `@Transactional`，多表写入（改状态 + 记日志）无原子性 | 加事务，或明确接受最终一致并补偿 |
