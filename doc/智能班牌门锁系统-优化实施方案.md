# 智能班牌门锁系统 — 优化实施方案（不改表版）

> 本文档针对《智能班牌门锁系统-现状分析与功能规划.md》中列出的 **65 项问题（S/R/D/C/O）** 与 **6 大类功能缺失（F-1-1 ~ F-6-6）**，给出**可落地的具体实施方案**。
>

> - 全部修复通过 **代码层改造** 完成；
> - 需要"新承载能力"（状态、心跳、流水、授权、幂等等）的场景，一律使用 **Redis / 进程内存 / 现有表已有列** 承担；

> 涉及业务接口的新增与调整，另见配套文档《智能班牌门锁系统-接口文档-v2.md》（严格沿用 `smart_class_card_and_lock_api.md` 的文档格式）。

## 一、约束与总体思路

### 1.1 为什么不改表也能做完

原分析文档中，"必须改表"的诉求集中在四类：

| 原诉求 | 依赖的新结构 | 不改表可否实现 | 替代手段 |
|---|---|---|---|
| 门锁分级授权 | `sys_lock_permission` 新表 | **可以** | Redis Hash + 角色/班级规则推导 |
| 开锁流水明细 | `sys_lock_card_record` 新表 | **部分可以** | 复用 `sys_operation_log` 现有 5 列 + `remarks` 承载扩展位 |
| 设备在线状态/心跳 | `sys_lock_device_status` 新表 | **可以** | Redis Hash（TTL 即心跳超时） |
| 任务执行日志 | `sys_lock_task_log` 新表 | **可以** | 复用 `sys_schedule_task.loop_count` + Redis 计数 + 应用日志 |

结论：**四类核心能力全部可在不改表的前提下落地**，代价是：

1. 部分数据（授权、心跳、任务明细）**不落库**，仅存 Redis —— 需接受"Redis 掉电后授权缓存可重建、心跳丢失、任务明细仅保留最近 N 条"的取舍；
2. 流水明细受 `sys_operation_log` 现有列限制，扩展字段（如卡号、结果码）只能挤进 `remarks`（text 类型，可存 JSON），**列表查询仍需在应用层反序列化**；
3. 需要新增一份 **Redis Key 规范**（见 1.2），作为与运维/其他模块的契约。

> ⚠️ **唯一无法绕过的一条**：原文档 D-12（`sys_lock_info` 的 SQL dump 里是 `college`/`classroom`，线上是 `JSH`）。如果线上确实已有 `JSH` 列，则属于"dump 未同步"，**修 dump 文件即可，不动线上表**；如果线上也没有 `JSH`，则说明当前代码本身跑不起来（`SmartLockMapper` 里全部 SQL 都在 JOIN/写 `JSH`），需要先与 DBA 确认线上真实结构。本文档按"线上已有 `JSH`，dump 落后"处理。

### 1.2 五种不改表的承载手段

**手段 A — 代码层修复**

适用：逻辑缺陷（双重调用、结果不校验、并发竞态、解析脆弱、拼写错误）。零副作用，优先级最高。

**手段 B — Redis 承载"新表"语义**

统一 Key 规范（**新增，不改表**）：

| Key 模式 | 类型 | 含义 | TTL |
|---|---|---|---|
| `lock:perm:{userId}` | Hash | 字段名 `lockId`，值为 `"1"`；用户可开锁的设备白名单 | 无（由角色变更时主动失效） |
| `lock:perm:role:{roleId}` | Set | 成员为 `lockId`，角色级批量授权 | 无 |
| `lock:heartbeat:{lockId}` | String | 最近一次心跳时间戳（ms） | 90s（写入即续期） |
| `lock:status:{lockId}` | String | `1`=开 / `0`=关 / `-1`=未知（缓存门状态，**权威值仍在 `sys_lock_info.switch_status`**） | 300s |
| `lock:op:nonce:{lockId}:{nonce}` | String | 开锁幂等令牌（防重放/重复提交） | 30s |
| `lock:task:count:{taskId}` | String | 定时任务剩余执行次数（Redis 权威，替代非原子 DB 自减） | 与任务同生命周期 |
| `lock:task:log:{taskId}` | List | 任务最近 200 条执行记录（JSON 字符串） | 无（LPUSH + LTRIM 200） |
| `lock:pwd:ver:{userId}` | String | 密码版本号，用于签发时绑定、改密后整体失效 | 无 |
| `lock:device:lock:{sn}` | String | 设备操作互斥锁（SET NX PX 8000），替代 `synchronized` 单机锁 | 8s |

**手段 C — 复用现有表已有列**

| 现有列 | 现语义 | 复用为 |
|---|---|---|
| `sys_operation_log.remarks`（text） | 未使用 | 存 JSON 扩展：`{"cardNo":"...","resultCode":0,"channel":1,"trigger":"cron"}` |
| `sys_schedule_task.remarks`（text） | 备注 | 存 JSON：任务来源/创建人/设备 SN |
| `sys_schedule_task.task_details`（text） | 任务描述 | 结构化存 JSON，替代额外拆列 |
| `sys_lock_info.remarks`（text） | 实为通道号 | **保持通道号语义不变**，新增字段一律走 Redis |
| `sys_lock_info.college/classroom` | 历史列 | 若线上存在，可承载"所属楼栋/分组"扩展 |

**手段 D — 进程内存（仅限无状态可重建的短生命周期数据）**

适用：调用去重窗口、SDK 回调映射表。**必须用 `ConcurrentHashMap` + 定时清理**，禁止再出现 `public static` 可变字段（见 R-05）。

**手段 E — 配置文件 / 常量收敛**

适用：硬编码密码、白名单、限流阈值、CORS 白名单（见 S-07 / S-03 / S-10）。

## 二、S 级问题修复方案（11 项，安全/正确性）

### S-01 无锁级授权：任何登录用户可开任意锁

- **现象定位**：`SecurityConfig.java` → `authorizeRequests()...anyRequest().authenticated()`。`SamrtLockController.updateSwitchStatus()`（L202-256）只用 JWT 认证，不校验"该用户是否有权操作该 `lockId`"；`sys_menu` 中虽有 `sys:lock:open` 权限码，但无任何 `@PreAuthorize` 消费它。
- **风险**：越权开锁，属于**门禁系统最严重的安全漏洞**。
- **修复方案（不改表）**：
  1. 新增 `LockPermissionService`，授权数据存 Redis：
     - 角色级：`lock:perm:role:{roleId}`（Set，成员为 lockId）由管理端接口维护；
     - 用户级：`lock:perm:{userId}`（Hash，字段 lockId）；
     - 用户在教室上课场景可由 `sys_course_schedule`（JGH + JSH）**动态推导**，不落任何存储。
  2. 新增 `LockPermissionEvaluator implements PermissionEvaluator`，注册到 `SecurityConfig`；表达式用 `@PreAuthorize("@lockPerm.hasPermission(authentication, #lockId)")`。
  3. 在 `SamrtLockController.updateSwitchStatus` / `openDoor` 入口处调用同一判定，**双保险**（注解可能被内部调用绕过）。
  4. `LOCK_ONLY_USER` 走单独分支：仅允许 `lockId` 在其 Redis 白名单内，且票据未过期。

```java
// soft_service/.../service/LockPermissionService.java（新增）
@Service
public class LockPermissionService {
    private final StringRedisTemplate redis;
    private final CourseScheduleMapper courseScheduleMapper;

    /** 是否有权操作某台锁 */
    public boolean hasPermission(Long userId, Integer lockId, Collection<String> roles) {
        String lk = String.valueOf(lockId);
        // 1) 角色级授权
        for (String r : roles) {
            Boolean m = redis.opsForSet().isMember("lock:perm:role:" + r, lk);
            if (Boolean.TRUE.equals(m)) return true;
        }
        // 2) 用户级授权
        Object v = redis.opsForHash().get("lock:perm:" + userId, lk);
        if ("1".equals(v)) return true;
        // 3) 任课关系动态推导（不落库）
        return courseScheduleMapper.countByTeacherAndRoom(userId, lockId2Jsh(lockId)) > 0;
    }
}
```

```java
// soft_mapper/.../CourseScheduleMapper.java 新增方法（只 SELECT，不改表）
@Select("SELECT COUNT(1) FROM sys_course_schedule s " +
        "JOIN sys_lock_info l ON l.JSH = s.JSH " +
        "WHERE s.JGH = #{userId} AND l.lock_id = #{lockId}")
int countByTeacherAndRoom(@Param("userId") Long userId, @Param("lockId") Integer lockId);
```

- **表结构影响**：**无**。授权数据在 Redis；任课关系复用现有 `sys_course_schedule` 只读查询。
- **验收点**：用 A 老师账号对非本人授课教室的锁调开锁接口 → 返回 `403 / 无权限操作该设备`；对本人授课教室 → 成功。

### S-02 全局单密码：`getEnabledPassword()` 只取第一条

- **现象定位**：`LockPasswordServiceImpl.java` → `getEnabledPassword()` 中 `wrapper.eq("status",1); wrapper.last("LIMIT 1")`。全系统只有一条生效密码，所有班牌/所有用户共用。
- **风险**：一处泄露 = 全部门锁失守；无法按设备/按人签发。
- **修复方案（不改表）**：
  1. **DB 层**：`sys_lock_password` 不新增列，但**已有列足够**承载"按锁/按人"语义——把 `status` 之外可用的维度放进 `password` 记录本身无法扩展，故采用**组合校验**：
     - 仍保留 DB 中一条"系统兜底密码"（`status=1` 的最新一条）；
     - 新增 **Redis 隔离层**：`lock:pwd:scoped:{scope}`（String，BCrypt 值），`scope` 形如 `lock:12`（按设备）或 `user:35`（按人）。
  2. 校验顺序：`scoped 命中 → 直接校验`；未命中 → 回落 DB 兜底密码。
  3. 签发接口 `POST /lock/password/issue` 写 Redis；撤销接口删 Key。

```java
public boolean verify(String input, Long userId, Integer lockId) {
    String scopedKey = "lock:pwd:scoped:" + (lockId != null ? "lock:" + lockId : "user:" + userId);
    String hash = redis.opsForValue().get(scopedKey);
    if (hash == null) {
        LockPassword p = getEnabledPassword();          // DB 兜底
        if (p == null) return false;                     // 见 S-05，必须 false
        hash = p.getPassword();
    }
    return encoder.matches(input, hash);
}
```

- **表结构影响**：**无**（Redis 承载 scope 语义）。**取舍**：Redis 丢失后 scoped 密码失效，需重新签发；DB 兜底密码始终可用。
- **验收点**：为 `lock:12` 签发专属密码后，该密码只能开 12 号锁；用它在 13 号锁校验失败。

### S-03 登录防爆破缺失：验证码不拦 `/lock/login`，IP 限流被注释

- **现象定位**：
  - `CaptchaFilter.java` L28 起：只对 `"/api/login"` + `POST` 生效，**不拦 `/lock/login`**；
  - `JwtAuthenticationFilter.java` L54-71：整个 IP 黑名单/限流代码块被 `/** */` 注释。
- **风险**：开锁密码可被在线暴力枚举。
- **修复方案（不改表）**：
  1. `CaptchaFilter` 的 `if` 条件改为 **URI 后缀集合匹配**：`Set.of("/api/login","/api/lock/login").contains(uri)`，并允许配置化（`yue.captcha-paths`）。
  2. 在 `JwtAuthenticationFilter` 恢复限流，改用 **Redis** 实现（多实例一致），阈值来自配置：

```java
// 新增 LoginAttemptGuard
@Component
public class LoginAttemptGuard {
    private final StringRedisTemplate redis;
    @Value("${lock.login.max-attempts:5}")   private int max;
    @Value("${lock.login.lock-seconds:300}") private int lockSec;

    public void onFail(String key, String ip) {
        String k = "lock:login:fail:" + key + ":" + ip;
        Long n = redis.opsForValue().increment(k);
        if (n != null && n == 1L) redis.expire(k, Duration.ofSeconds(lockSec));
        if (n != null && n >= max) redis.opsForValue().set("lock:login:ban:" + ip, "1", Duration.ofSeconds(lockSec));
    }
    public boolean banned(String ip) {
        return Boolean.TRUE.equals(redis.hasKey("lock:login:ban:" + ip));
    }
}
```

  3. `LockPasswordController.login` 入口先查 `banned(ip)`，失败时 `onFail`。

- **表结构影响**：**无**。
- **验收点**：连续 5 次错误后第 6 次直接返回 `429 / 尝试过于频繁`；`/lock/login` 缺验证码返回 `400`。

### S-04 开锁密码强度无约束

- **现象定位**：`LockPasswordController.setPassword`：仅判断非空 + `length() > 6` 报错（即最大 6 位），**无最小长度、无字符要求、无弱口令库**。
- **风险**：可设 `1`、`1234` 等弱口令。
- **修复方案（不改表）**：抽 `PasswordPolicy` 工具类，规则：长度 6~12、**至少含两种字符类型**、禁止连续/重复（`123456`、`111111`）、不在弱口令字典。

```java
public final class PasswordPolicy {
    private static final Pattern WEAK = Pattern.compile("^(\\d)\\1+$|^012345|^123456|^654321|^111111|^888888$");
    public static void validate(String p) {
        if (p == null || p.length() < 6 || p.length() > 12) throw new BizException("密码长度须为 6~12 位");
        long kinds = Stream.of(p.matches(".*[a-zA-Z].*"), p.matches(".*\\d.*"), p.matches(".*[^a-zA-Z0-9].*"))
                           .filter(Boolean::booleanValue).count();
        if (kinds < 2) throw new BizException("密码须包含数字、字母或符号中的至少两种");
        if (WEAK.matcher(p).find()) throw new BizException("密码过于简单，请更换");
    }
}
```

- **表结构影响**：**无**。
- **验收点**：`123456` / `111111` / `abcd` 均被拒；`Ab12#x` 通过。

### S-05 `verifyOldPassword` 在无密码时返回 `true`（认证绕过）

- **现象定位**：`LockPasswordServiceImpl.verifyOldPassword`：`if (getEnabledPassword() == null) return true;`
- **风险**：**系统尚未设置密码时，任何人可用任意密码通过校验**。
- **修复方案（不改表）**：改为 `return false`，并返回明确错误码 `LOCK_PWD_NOT_INIT`，前端引导进入"首次初始化"流程（初始化接口需管理员权限）。

```java
public boolean verifyOldPassword(String input) {
    LockPassword p = getEnabledPassword();
    if (p == null) throw new BizException(ErrorCode.LOCK_PWD_NOT_INIT);  // 不再放行
    return encoder.matches(input, p.getPassword());
}
```

- **表结构影响**：**无**。
- **验收点**：清空 `sys_lock_password` 后调用改密 → 返回"密码未初始化"，不放行。

### S-06 开锁 Token 的 Redis Key 用前 8 位拼接，存在碰撞

- **现象定位**：`LockPasswordController.login`：`redisKey = suffix.concat("-lock_token-").concat(token.substring(0,8))`；`JwtAuthenticationFilter` 同一规则。subject 为 `lock_password:{timestamp}`，**同一毫秒签发两个 token 会得到完全相同的 Redis Key**。
- **风险**：A 的票据被 B 覆盖 → 越权；Redis 中票据可被猜中。
- **修复方案（不改表）**：Key 改用 **完整 token 的 SHA-256 摘要前 32 位**（或直接 `DigestUtils.md5DigestAsHex(token.getBytes())`），并加 `expire`。

```java
private String tokenKey(String token) {
    return suffix + "-lock_token-" + DigestUtils.md5DigestAsHex(token.getBytes(StandardCharsets.UTF_8));
}
```

- **表结构影响**：**无**。
- **验收点**：同一毫秒签发两个 token，Redis 中出现两个不同 Key；旧票据被新票据覆盖的问题消失。

### S-07 通讯密码 `"FFFFFFFF"` 硬编码

- **现象定位**：`CommandAllocator.java` L51、L69；`SmartLockSwitch.openDoor` 内亦有同类硬编码。
- **风险**：密码泄露、无法按环境切换、无法轮换。
- **修复方案（不改表）**：抽 `LockSdkProperties`（`@ConfigurationProperties(prefix="lock.sdk")`），配 `comm-password`，默认 `FFFFFFFF`，生产环境由配置中心/环境变量注入；所有调用点改读配置。

```yaml
lock:
  sdk:
    comm-password: ${LOCK_SDK_PWD:FFFFFFFF}
    search-timeout-ms: 3000
    tcp-timeout-ms: 5000
    restart-count: 3
```

- **表结构影响**：**无**。
- **验收点**：修改配置后 SDK 使用新密码；源码中不再出现字面量 `FFFFFFFF`。

### S-08 开锁密码设置接口无角色校验

- **现象定位**：`LockPasswordController.setPassword` / `resetPassword` 无任何 `@PreAuthorize`；`SecurityConfig` 未开启基于角色的限定（`prePostEnabled=true` 已开但无用例）。且 `yue.url` 白名单包含 `/lock/login`（应当放行）**但未包含 `setPassword`**，靠 `anyRequest().authenticated()` 兜底 —— 任意登录用户均可改全局密码。
- **风险**：普通学生账号可改开锁密码。
- **修复方案（不改表）**：
  1. 在 `LockPasswordController` 各类管理方法加 `@PreAuthorize("hasAnyAuthority('sys:lock:op','ROLE_ADMIN')")`；
  2. 修正 `sys_menu` 中错误权限码 `sys:lcok:op` → `sys:lock:op`（**注意：这是数据订正，属"修改数据"而非"修改表结构"，不在禁止范围内；如数据也禁止改动，则在代码中同时兼容两个码**）。

```java
@PreAuthorize("hasAnyAuthority('sys:lock:op','sys:lock:password:set','ROLE_ADMIN')")
@PostMapping("/setPassword")
public ApiResult setPassword(@RequestBody LockPasswordDto dto) { ... }
```

- **表结构影响**：**无**（仅 `sys_menu` 数据行可选的订正）。
- **验收点**：无 `sys:lock:op` 权限的账号调用 → `403`。

### S-09 全局异常与统一返回未覆盖鉴权失败

- **现象定位**：`@RestControllerAdvice` 若只处理 `Exception`，则 Spring Security 抛出的 `AccessDeniedException` / `AuthenticationException` 会落到 Servlet 容器的默认 `/error`，返回 HTML 或非 `ApiResult` 结构，前端无法统一处理。搭配 `SecurityConfig` 未配置 `authenticationEntryPoint` / `accessDeniedHandler`。
- **风险**：前端拿到非标准响应，难以区分"未登录"与"无权限"。
- **修复方案（不改表）**：在 `SecurityConfig` 注册两个处理器，输出 `ApiResult`：

```java
http.exceptionHandling()
    .authenticationEntryPoint((req, res, e) -> writeJson(res, 401, ApiResult.fail(401, "未登录或登录已过期")))
    .accessDeniedHandler((req, res, e) -> writeJson(res, 403, ApiResult.fail(403, "无权限访问该资源")));
```

- **表结构影响**：**无**。
- **验收点**：无 token 请求受保护接口 → JSON `{"code":401,...}`；有 token 无权限 → `{"code":403,...}`。

### S-10 CORS 全开（`*` + 凭据）

- **现象定位**：`SecurityConfig.corsConfigurationSource()`：`addAllowedOrigin("*")` + `addAllowedHeader("*")` + `addAllowedMethod("*")`，且 `setAllowCredentials(true)`。
- **风险**：任意站点可携带用户 Cookie/凭据发起跨站请求；浏览器实际会因 `*` + credentials 拒绝，但配置语义错误，且部分客户端（非浏览器）会接受。
- **修复方案（不改表）**：改为配置驱动白名单：

```yaml
cors:
  allowed-origins:
    - https://board.example.edu.cn
    - http://10.255.12.0/24   # 如为内网，建议在网关层限制
  allow-credentials: true
```

```java
@Bean

    UrlBasedCorsConfigurationSource s = new UrlBasedCorsConfigurationSource();

```

- **表结构影响**：**无**。
- **验收点**：非白名单 Origin 的预检请求返回 403/无 `Access-Control-Allow-Origin`。

### S-11 `SamrtLockController` 中的可变共享状态（实例字段）

- **现象定位**：`SamrtLockController.java` L45 `private final ExecutorService executorService = Executors.newFixedThreadPool(10);`；L48 `private HashSet<...SearchResult> devicesList;`。Controller 是**单例**，`devicesList` 被多请求共享 —— 并发下互相污染，且线程池大小不可配、无优雅关闭。
- **风险**：设备搜索结果串号；线程池耗尽；应用无法优雅停机。
- **修复方案（不改表）**：
  1. 删除 `devicesList` 字段，改为**方法内局部变量**；
  2. 线程池抽为 `@Bean`（`ThreadPoolTaskExecutor`），核心/最大/队列大小配置化，注册 `setWaitForTasksToCompleteOnShutdown(true)`；
  3. `SearchDeviceCommand` 的搜索结果由 `CompletableFuture` 返回，避免共享集合。

```java
@Bean(name = "lockSearchExecutor")
public ThreadPoolTaskExecutor lockSearchExecutor() {
    ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
    e.setCorePoolSize(props.getSearchCore());
    e.setMaxPoolSize(props.getSearchMax());
    e.setQueueCapacity(props.getSearchQueue());
    e.setThreadNamePrefix("lock-search-");
    e.setWaitForTasksToCompleteOnShutdown(true);
    e.setAwaitTerminationSeconds(20);
    e.initialize();
    return e;
}
```

- **表结构影响**：**无**。
- **验收点**：并发 20 次搜索接口，结果互不串；关闭应用无任务丢失日志。

## 三、R 级问题修复方案（18 项，可靠性）

### R-01 开锁结果不校验 —— "假成功"（**最高优先级**）

- **现象定位**：`SmartLockSwitch.openDoor(...)`：
  ```java
  CompletableFuture<Boolean> futurePrice = CompletableFuture.supplyAsync(() -> { ... });
  // 🔴 创建后从未 get / join / 判断返回值，方法 void 返回
  ```
  Controller 侧 `updateSwitchStatus` 先 `smartLockService.updateSwitchStatus(...)` **落库为"已开"**，再异步调 SDK —— 即使设备离线/密码错/超时，数据库也已记成成功。
- **风险**：**平台显示已开，实际门未开**；安防事故。
- **修复方案（不改表）**：
  1. `openDoor` 改为 `public static boolean openDoor(...)`，**阻塞等待 Future 结果**（带总超时），返回真实结果；
  2. Controller 调整顺序：**先调 SDK，成功后再落库**；失败则不落库并返回明确错误码；
  3. 无论成败都写 `sys_operation_log`（`remarks` JSON 内含 `resultCode`），实现"操作必留痕"；
  4. 引入幂等令牌 `lock:op:nonce:*` 防止用户连点。

```java
// SmartLockSwitch
public static boolean openDoor(String ip, int port, String sn, String channel, long timeoutMs) {
    CompletableFuture<Boolean> f = CompletableFuture.supplyAsync(() -> doOpen(ip, port, sn, channel));
    try {
        return Boolean.TRUE.equals(f.get(timeoutMs, TimeUnit.MILLISECONDS));
    } catch (TimeoutException e) {
        log.warn("openDoor timeout lock={} sn={}", ip, sn);
        return false;
    } catch (Exception e) {
        log.error("openDoor error lock={} sn={}", ip, sn, e);
        return false;
    }
}
```

```java
// Controller
boolean opened = SmartLockSwitch.openDoor(lock.getIpAddress(), lock.getPortNumber(),
                                          lock.getSnCode(), lock.getRemarks(), 8000);
switchRecordService.record(lock.getLockId(), userId, OperationMethod.OPEN, opened, "manual", channel);
if (!opened) {
    return ApiResult.fail(ErrorCode.LOCK_OPEN_FAILED, "设备未响应，开锁失败");
}
smartLockService.updateSwitchStatus(lock.getLockId(), 1);   // 仅在真开后落库
```

- **表结构影响**：**无**（结果码进 `remarks` JSON）。
- **验收点**：断开设备网线 → 接口返回失败、`switch_status` **保持 0**、`sys_operation_log` 有一条失败记录。

### R-02 开锁日志 `userId` 恒为 `-1`

- **现象定位**：`SamrtLockController.updateSwitchStatus` 中开锁日志写死 `userId = -1`（`LOCK_ONLY_USER` 场景无法归属到人）。
- **风险**：审计无法追责。
- **修复方案（不改表）**：

  2. `JwtAuthenticationFilter` 解析时把真实 userId 放入 `Authentication` 的 details / 自定义 `LockPrincipal`；
  3. 写日志取 Principal 的 userId，`LOCK_ONLY_USER` 时至少记录签发人的 userId + 票据摘要。

- **表结构影响**：**无**（`sys_operation_log.user_id` 是 text，可直接存真实 id）。
- **验收点**：用 A 账号登录后开锁，日志 `user_id` 为 A 的真实 id；`remarks` 中保留票据摘要。

### R-03 门状态回写覆盖 `JSH` / `remarks`

- **现象定位**：`SmartLockSwitch.queryDoorStatus` 回调里 `targetLockInfo.setSwitchStatus(dp.GetDoor(1)); smartLockService.update(targetLockInfo);`，而 `SmartLockMapper.update` 的 SQL 是：
  ```sql
  UPDATE sys_lock_info SET JSH=#{classroomNumber}, switch_status=#{switchStatus}, remarks=#{remarks} WHERE lock_id=#{lockId}
  ```
  SDK 回调时 `targetLockInfo` 只有 `lockId` + `switchStatus`，`classroomNumber`/`remarks` 为 `null` → **把教室号与通道号清空**。
- **风险**：设备一查询状态，教室绑定与通道号即丢失，门锁失效。
- **修复方案（不改表）**：
  1. **拆出专用更新方法**，只更新状态列：

```java
@Update("UPDATE sys_lock_info SET switch_status = #{switchStatus} WHERE lock_id = #{lockId}")
int updateSwitchStatusOnly(@Param("lockId") Integer lockId, @Param("switchStatus") Integer switchStatus);
```

  2. `queryDoorStatus` 改用该方法；
  3. 需要完整更新时，先在 Service 层 `selectById` 取全量再合并，**禁止用半填充对象直接 update**。

- **表结构影响**：**无**。
- **验收点**：调用状态查询 3 次后，`sys_lock_info.JSH` 与 `remarks` 不变。

### R-04 `queryDoorStatus` 为实例方法且回调线程直接写库，无事务/无异常处理

- **现象定位**：SDK 回调线程中直接 `smartLockService.update(...)`，异常只打印不抛，且非 `static` 导致调用链耦合。
- **风险**：DB 抖动后状态永久不一致。
- **修复方案（不改表）**：回调中改为**投递到 Spring 事件/持久化队列**（内存 `BlockingQueue` + 单消费者线程，或用 `@Async` + 重试），失败落 Redis 待重试列表 `lock:status:retry`（List），由定时任务补偿。

- **表结构影响**：**无**。
- **验收点**：模拟 DB 断开，恢复后状态最终被补偿写入。

### R-05 `SmartLockSwitch` 的 `public static int StatusSwitch` / `public static LockInfo lockInfo`

### R-07 SDK 连接未复用 / 未释放，每次开锁重建 TCP

- **现象定位**：`SmartLockSwitch.openDoor` 每次 `new TCPClientDetail(...)` 并连接；`CommandAllocator` 亦维护连接。
- **风险**：高并发下句柄泄漏、开锁延迟高。

### R-08 `SmartLockQuartz` 执行链路异常未捕获，Quartz 中断后续触发

- **现象定位**：`SmartLockQuartz.execute` 中 SDK 调用与 DB 更新顺序执行，无 try/catch 包裹全局；一旦抛异常，Quartz 记为失败，`loop_count` 不自减，任务卡死。
- **风险**：任务静默失效。
- **修复方案（不改表）**：`execute` 整体 `try/catch(Throwable)`；失败也**照常扣减** `loop_count` 并写 `lock:task:log:{taskId}`（含 `success=false` + 异常摘要）；超过 N 次连续失败则把 `task_status` 置为异常态并告警。

- **表结构影响**：**无**。
- **验收点**：故意让 SDK 抛异常，任务仍按次数递减并记录失败。

### R-09 `updateSwitchStatus` 与 SDK 调用的顺序错误（见 R-01）

### R-10 一锁只能挂一个定时任务（JobKey 仅用 lockId）

- **风险**：无法配置"工作日早 8 点开、晚 6 点关"等多个任务。
- **修复方案（不改表）**：JobKey / TriggerKey 加入 `taskId`：

JobKey jobKey = JobKey.jobKey("smartLockJob_" + lockId + "_" + taskId, "smartLockGroup");
TriggerKey triggerKey = TriggerKey.triggerKey("smartLockTrigger_" + lockId + "_" + taskId, "smartLockGroup");

同时 `addTimer` 不再无脑 `deleteJob`，只对同 `taskId` 覆盖（先删同 Key 再建）。

- **表结构影响**：**无**（`sys_schedule_task` 天然支持一锁多条记录，只是原来被 JobKey 抹掉了）。

### R-11 `loopCount` 语义不一致（`> -2` vs `> 0`）

- **现象定位**：`SamrtLockController.addTimer` L362 `if (scheduleTask.getLoopCount() > -2)`；`setTimerTask` L492 `if (scheduleTask.getLoopCount() > 0)`；`QuartzConfig.createCronTrigger` 中 `repeatCount >= 0` 才设 `maxExecutionCount`；`ScheduleLoad` 用 `> 0`。
- **风险**：同一数据在不同入口行为不同，任务要么无限重复要么不执行。
- **修复方案（不改表）**：定义**唯一语义**并抽公共方法：

```java
public enum LoopMode { UNLIMITED, LIMITED, ONCE }
/** loopCount: -1 = 不限次；0 = 不执行；N>0 = 执行 N 次 */
public static LoopMode modeOf(Integer loopCount) {
    if (loopCount == null || loopCount < 0) return LoopMode.UNLIMITED;
    if (loopCount == 0) return LoopMode.ONCE;   // 兼容"至少跑一次"的历史数据
    return LoopMode.LIMITED;
}
```

所有 4 处调用同一方法；`createCronTrigger` 内 `UNLIMITED` 时不设 `maxExecutionCount`。

- **表结构影响**：**无**（`loop_count` 列沿用，仅统一解释）。
- **验收点**：`loopCount=-1/0/3` 三种值在 add/set/load 三个入口行为完全一致。

### R-12 `loopCount` 递减非原子，且无执行日志

- **现象定位**：`SmartLockQuartz.execute`：`updateLoopCount(currentCount - 1, taskId)` —— 读后写，多线程/多实例下丢失更新。
- **风险**：任务多跑或少跑。
- **修复方案（不改表）**：**Redis 作为权威计数器**：

```java
String k = "lock:task:count:" + taskId;
Long left = redis.opsForValue().decrement(k);      // 原子
redis.opsForList().leftPush("lock:task:log:" + taskId, json);
redis.opsForList().trim("lock:task:log:" + taskId, 0, 199);
if (left != null && left <= 0) { pauseTrigger(taskKey); }
```

Redis 计数在任务创建时用 `loopCount` 初始化（`-1` 表示不限，不设 TTL，每次执行不递减）。

- **表结构影响**：**无**。**取舍**：多实例共享 Redis 计数，语义正确；Redis 丢失时以 DB `loop_count` 兜底重建。

### R-13 任务暂停/恢复未持久化，重启后状态错乱

### R-14 `countDay` 解析脆弱（按字符下标取数字）

- **现象定位**：`ScheduleLoad.run`：`char[] c = countDay.toCharArray(); ... Days[i] = ...`（用**原下标 i**，遇到两位数字/分隔符即错位）；`SamrtLockController.trantoScheduleTask` 用 `Arrays.toString(int[])` 存（形如 `[1, 2, 3]`）；`setTimerTask` 用 `mapper.readValue(countDay, int[].class)` 回读 —— **两种写法互相不兼容**。
- **风险**：重启后任务日期完全错乱。
- **修复方案（不改表）**：
  1. **统一存储格式**：`countDay` 一律存 **逗号分隔**：`"0,2,4"`；
  2. 抽 `CountDayCodec`：

```java
public final class CountDayCodec {
    public static String encode(int[] days) {   // -> "0,2,4"
        return Arrays.stream(days).distinct().sorted()
                     .mapToObj(String::valueOf).collect(Collectors.joining(","));
    }
    public static int[] decode(String s) {      // 兼容历史 "[1, 2, 3]" 与 "1234567"
        if (s == null || s.isBlank()) return new int[0];
        String t = s.replaceAll("[\\[\\]\\s]", "");
        if (t.contains(",")) return Arrays.stream(t.split(","))
                                          .filter(x -> !x.isEmpty()).mapToInt(Integer::parseInt).toArray();
        return t.chars().map(ch -> ch - '0').toArray();   // 旧格式兜底
    }
}
```

  3. `ScheduleLoad` / `trantoScheduleTask` / `setTimerTask` 全部改用它；写入时一律 `encode`。

- **表结构影响**：**无**（`count_day` 仍是 text，只是内容格式统一，且**兼容读取旧格式**）。
- **验收点**：用旧数据 `[1, 2, 3]` 重启，任务仍正确恢复；新写入为 `1,2,3`。

### R-15 任务执行时未校验设备在线，离线也照记"成功"（见 R-01 合并）

- **表结构影响**：**无**。

### R-16 通道号来自 `remarks`，解析失败抛 `NumberFormatException`

- **现象定位**：`SmartLockSwitch.openDoor` 中 `parameter1.Door.SetDoor(Integer.parseInt(Channel), 1)`；`Channel` 来自 `lock.getRemarks()`（自由文本）。
- **风险**：管理员把备注改成 "3号门" 即导致开锁 500。
- **修复方案（不改表）**：
  1. 抽 `ChannelResolver`：`Integer.parseInt` 失败时回退默认通道 1 并**记录告警**，不抛异常；
  2. 在锁的**新增/编辑接口**做输入校验：`remarks` 若存在必须匹配 `^[1-8]$`（写库前校验，不改表）；
  3. Redis 缓存 `lock:meta:channel:{lockId}`，避免每次解析。

```java
public static int resolveChannel(String remarks) {
    if (remarks != null && remarks.matches("[1-8]")) return Integer.parseInt(remarks);
    log.warn("invalid channel remarks={}, fallback to 1", remarks);
    return 1;
}
```

- **表结构影响**：**无**。

### D-11 查询 JOIN 使用 `COLLATE` 强制转换

- **现象定位**：`SmartLockMapper` 全部 SQL：`l.JSH COLLATE utf8mb4_general_ci = c.JSH COLLATE utf8mb4_general_ci`。列上 COLLATE 会导致**索引失效**（无法走索引，全表扫描）。
- **修复方案（不改表 —— 不能改列 collation）**：
  1. 移除 SQL 中的 `COLLATE`（若两列 collation 本就一致则无需转换）；

  3. 对高频查询加 **Redis 缓存**（`lock:meta:*`）。

```java
// 应用层合并，替代 COLLATE JOIN
List<LockInfo> locks = lockMapper.selectAllSimple();               // 无 JOIN
Set<String> jshs = locks.stream().map(LockInfo::getClassroomNumber).filter(Objects::nonNull).collect(toSet());
Map<String, Classroom> roomMap = classroomMapper.selectByJshIn(jshs).stream()
        .collect(toMap(Classroom::getClassroomNumber, c -> c, (a,b) -> a));
locks.forEach(l -> l.setClassroomName(roomMap.getOrDefault(l.getClassroomNumber(), new Classroom()).getClassroomName()));
```

- **表结构影响**：**无**。
- **验收点**：`EXPLAIN` 显示走索引；10 万行数据查询耗时下降。

### F-2 课表联动自动开关锁（**最高业务价值**）

| 编号 | 功能 | 方案 | 手段 |
|---|---|---|---|
| F-2-1 | 按课表自动开关锁 | 读 `sys_course_schedule`：`ZC`(周次) / `XQJ`(星期) / `SKJC`(节次) / `JSH`(教室) / `JGH`(教师)；映射"节次 → 起止时间"，在课前 5 分钟开锁、课后 X 分钟关锁 | A/C |

| F-2-3 | 节次时间表 | 无专门表 —— 用**配置文件**定义节次时间（`lock.class-periods[].index/start/end`），运维可调；也可用 Redis Hash 覆盖 | E/B |
| F-2-4 | 考试期间自动开关锁 | 复用 `sys_exam`（考试日期/场次/教室），与课表规则合并 | A/C |
| F-2-5 | 节假日/调休排除 | 配置文件维护例外日期列表（`lock.holidays`）或 Redis Set `lock:calendar:holiday` | E/B |
| F-2-6 | 联动任务可视化管理 | 生成的任务仍存 `sys_schedule_task`（已有列足够），仅 `task_details` 存 JSON 标记来源 `courseSchedule` | C |

```yaml
lock:
  class-periods:
    - { index: 1, start: "08:00", end: "08:45" }
    - { index: 2, start: "08:55", end: "09:40" }
    # ... 
  schedule:
    open-ahead-minutes: 5      # 提前开锁
    close-delay-minutes: 5     # 延后关锁
    holiday-url: ""            # 可选：节假日 API
```

**生成逻辑伪码**：

```java
public void syncFromCourseSchedule(Integer week) {
    // 1. 清掉所有来源为 courseSchedule 的旧任务（按 task_details 中 source 标记）
    scheduleService.deleteBySource("courseSchedule");
    // 2. 拉取本周课表
    List<CourseSchedule> list = courseScheduleMapper.selectByWeek(week);
    // 3. 逐条生成开/关任务；同一 (JSH, XQJ, 节次) 去重
    for (CourseSchedule cs : distinct(list)) {
        LockInfo lock = lockService.getFirstByJsh(cs.getClassroomNumber());
        if (lock == null) continue;
        Period p = props.periodOf(cs.getClassPeriod());
        createTask(lock, cs.getDayOfWeek(), plus(p.getStart(), -openAhead), OperationMethod.AUTO_OPEN,  "courseSchedule", cs.getId());
        createTask(lock, cs.getDayOfWeek(), plus(p.getEnd(),   +closeDelay), OperationMethod.AUTO_CLOSE, "courseSchedule", cs.getId());
    }
}
```

- **表结构影响**：无（任务写入现有 `sys_schedule_task`；节次时间在配置）。
- **验收点**：导入课表后，任务列表出现对应开/关任务且时间正确；删除课表条目后对应任务被清理。

## 十、风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| Redis 不可用 | 授权/心跳/密码 scope 失效 | 授权规则可重建；DB 兜底密码仍可用；心跳降级为"未知" |
| 一锁多任务改造后旧任务残留 | 重复触发 | 上线前清理 `smartLockGroup` 下全部 Job，由 `ScheduleLoad` 重建 |
| `countDay` 格式统一 | 历史数据误读 | `CountDayCodec.decode` **兼容旧格式**（`[1, 2, 3]` 与 `1234567`） |
| 开锁改为阻塞等待 | 接口 RT 上升 | 总超时 8s；超时即失败返回，不无限等待 |
| 流水写入 `remarks` JSON | 查询无法走索引 | 控制查询时间范围；量大时评估加列（需升级约束） |
| `sys_menu` 数据订正 | 影响现有角色 | 订正前备份 `sys_menu`；或仅在代码层兼容双权限码 |
| D-12 dump 与线上不一致 | 新环境起不来 | 先与 DBA 核对线上结构，修 dump 文件 |

**回滚策略**：每批次独立分支 + 独立发版；代码层改动可直接回退版本；Redis 数据无需回滚（可重建）；若执行了 `sys_menu` 数据订正，保留订正前快照以便还原。
