## 1. 实际改动

`GET /project/assess/list` 保持原路径及认证用户来源。只替换该接口的查询链路：

1. `ProjectAssessScopeResolver` 一次查询最高有效角色，生成服务端范围。
2. 管理分支通过 XML 在数据库内审计有效 CC 名单，返回首个异常节点 ID；不把异常名单替换为空结果。
3. XML 使用 `JSON_TABLE` 按项目展开直接及角色接收人，`UNION` 按 `(projectId,userId)` 去重。本人分支单独从已有结果生成候选，不依赖当前 CC 名单。
4. 共用 `assessFilteredRows` 表达权限、角色、昵称、时间、分数聚合及状态过滤，分别执行显式 COUNT 和带 LIMIT 的数据查询。
5. 按 `score DESC, projectId ASC, userId ASC` 固定排序。Java 只接收当前页记录，校验宽类型总分并转换成原 `ProjectVo`，设置 `rank=offset+i+1`。
6. 保留顶层 `code/msg/total/list`，补充 `totalPage/page/limit`，不增加 `data` 层。

新增 DTO 使用 Lombok。Java 新增类、字段、构造及方法使用 Javadoc；Mapper 继续继承 MyBatis-Plus `BaseMapper`，自定义 SQL 全部位于 XML。

列表读取入口使用真正由代理执行的 `@Transactional(readOnly=true, isolation=REPEATABLE_READ)`，范围查询、名单审计、COUNT 和数据页共用同一连接及事务快照。正常管理请求最多四次业务 SELECT：最高角色、名单审计、COUNT、当前页；本人请求最多三次。超页不执行数据 SELECT，未覆盖的权重分支直接返回空页。上述次数不包括 JDBC 建连及事务管理命令。

`ProjectQueryParam` 还用于 `downloadEvidence` 的必填校验，本次保留其原注解及下载接口。考核列表在服务层单独校验可选参数，未给共享参数直接添加 `@Valid`。

## 2. 契约与显式行为修正

| 项目 | 实际行为 |
|---|---|
| 展示单位 | 每个项目、用户一行，多 CC、多个角色及重复关联不增加行数或总分 |
| 排名 | 当前权限和筛选全集的顺序编号，同分不并列，第 2 页继续编号 |
| 分数 | 所有结果的 `SUM(score)`，没有追加 `is_finish=1`，无分数归零 |
| 状态 | 最小结果主键对应的 `is_finish=1` 显示 1，其余及无结果显示 0 |
| 本人筛选 | 补齐 projectId、目标 roleId 和 `p.status<>3`；已有结果即为候选，不要求仍属于 CC |
| 昵称 | 字节敏感的字面包含匹配，`%`、`_` 不解释成通配符；不 trim；NULL 表示不筛选，空串只匹配非 NULL 昵称 |
| 时间 | 保留项目覆盖区间：项目开始时间不晚于查询开始、项目结束时间不早于查询结束 |
| 参数 | page≥1，1≤limit≤100，可选项目和角色 ID 为正数，status 仅 0/1，拒绝倒置时间区间 |
| 操作人 | 请求 userId 不替代认证用户，也不扩大范围 |
| 空页 | total=0 时 totalPage=0；超页保留真实 total 和合法请求页码 |
| 数值边界 | long 偏移及 COUNT，Long 接收聚合分数；超出原 Integer score/rank 容量返回受控业务异常 |

名单必须是 JSON 数组。兼容 INT 范围内的整数及匹配 `^-?[0-9]{1,10}$` 的整数字符串。空数组合法；SQL NULL、空串、JSON null、非数组、小数、布尔、对象、嵌套数组、非整数字符串及溢出 ID 均拒绝，错误包含节点 ID。不存在的用户不生成展示行；不在本次任务订正历史名单或删除失联关联。

权限保持原权重分支：≥20、=9、=5、<5 分别对应全部 CC、共享非普通角色、共享权重 2 角色、本人结果。无有效角色或空权重受控返回 403；其他权重仍为空页。辅助共享角色保持旧 `getRoles` 的条件，不新增有效角色或学院限制。因此快照管理员 4、1307 的实际权重 10 仍为空页，未混入独立的管理员授权修复。

快照每项目仅一个 CC，新增跨节点去重不会减少原 362 个组合；每个项目、用户的结果状态一致，最小 ID 规则不会改变快照的状态。构造测试另外覆盖多节点重复和混合状态。本人新增筛选及删除状态条件是明确的行为修正，具体线上受影响记录需在预发核对增量；本次没有导出线上差异。

## 3. 实库兼容与事务证据

本地使用已有 **MySQL 8.0.34** 创建独立实例，绑定 `127.0.0.1:13310`，数据目录位于仓库 `target/t10-mysql/data`，只操作 `project_assess_test`。实际 DDL 来自用户提供的 `softmanage.sql`，保留 TIMESTAMP、字符集、字段类型和原索引。JDBC 使用仓库既有 Connector/J 8.0.19，MyBatis-Plus 3.2.0 和旧 `PaginationInterceptor`，JDK 为 Dragonwell 1.8.0_482。

实际验证发现并处理了两个兼容点：

- Connector/J 8.0.19 在只读连接上对顶层 WITH 的识别会报“Connection is read-only”。查询外包 `SELECT ... FROM (WITH ... SELECT ...)`，保留只读事务，无须升级驱动。
- `JSON_TABLE` 直接引用 CTE 的 VARCHAR 列会报“Incorrect arguments to JSON_TABLE”。接收人展开使用 `CAST(f.u_id AS JSON)` 和 `CAST(f.role_id AS JSON)`，数据库字段仍为原 VARCHAR。

测试注册现有分页插件，实际准备的数据 SQL 含 `LIMIT ?, ?`，未发生插件重复分页。事务测试在真实代理的 COUNT 后通过另一独立连接删除接收节点、修改分数：当前请求的 total、条数及分数仍取旧快照，下一请求观察到变化；同时断言实际事务开启和隔离级别为 REPEATABLE_READ。

源库结构记录的版本为 **8.0.35**，本次未将本地 8.0.34 结果宣称为 8.0.35 同版本预发验收。JDBC 会话设置 `serverTimezone=Asia/Shanghai`；实际 TIMESTAMP 与原 VO 日期格式、项目覆盖时间方向均保留。

扩大样本测试实际执行两份脚本，逐规模添加、回退并重新生成计划。1 万样本的结果关联从全表扫描/hash join 变为 `idx_t10_result_project_user` 的 ref 访问，估算每次约三条；角色展开使用 `idx_t10_user_role_role_user`。filesort 和候选临时表仍存在。小规模及较大规模下 hash join 也可能更快：例如本次 5 万样本未加索引单次约 1,637 ms，而加索引多次采样 p50 约 2,079 ms，不能据此强制宣称这些索引必然缩短新列表耗时。

脚本作为可评估的辅助索引交付，**不是代码运行的必要迁移**。发布前必须核对当前索引，比较典型角色、本人查询和并发读写负载，决定是否全部或部分应用；不添加前缀重复索引。没有为当前仅两个合成流程额外增加流程索引，也没有新增唯一约束或改变现有业务数据。
