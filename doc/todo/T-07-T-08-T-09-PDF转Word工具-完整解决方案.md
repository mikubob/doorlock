## 一、问题定性

这三处 TODO 属于同一条佐证材料导出链路的问题：**输入路径没有可靠校验，PDF 页面读取不完整，图片排版没有依据页面尺寸计算。**

现有实现不是提取 PDF 文字、表格再重建可编辑 Word，而是 **PDF 页面 → 图片 → 嵌入 DOCX**。本方案沿用这一能力边界，目标是让材料完整、比例正确、导出稳定；OCR 和可编辑文本转换不在本次范围。

### 1.1 原代码的问题链

以下为当前实现的关键摘录，省略了不影响分析的部分：

```java
File filepath = new File(path);
String[] pdfFileList = filepath.list();                 // ① 未检查目录，结果可能为 null
XWPFDocument doc = new XWPFDocument();
XWPFParagraph p = doc.createParagraph();                // ② 所有图片共用一个段落

for (String filePath : pdfFileList) {                   // ③ 未过滤文件类型，也未排序
    String imagePath = convertPdfToImage(
            path + pathSeparator + filePath);          // ④ 手工拼接路径，T-07
    FileInputStream fileInputStream = new FileInputStream(imagePath);
    r.addPicture(fileInputStream, XWPFDocument.PICTURE_TYPE_PNG,
            imagePath, Units.toEMU(400), Units.toEMU(600)); // ⑤ 固定尺寸，T-09

}
doc.write(out);                                        // ⑧ 直接写目标文件

// 此后才逐个删除 PNG；前面的操作异常会跳过清理。

// convertPdfToImage 内：

        + getFileNameWithoutExtension(pdfFile) + ".png"; // ⑨ 同目录、同名 PNG

    document.close();                                  // ⑪ 异常路径可能泄漏
}
```

| 编号 | 根因 | 实际后果 |
|---|---|---|
| **T-07** | 字符串拼路径；目录存在性、可读性、文件类型缺少校验 | 目录不存在时可能 NPE；子目录、PNG、DOCX 等混入会被当 PDF 解析；跨环境定位困难 |
| **T-08** | 固定调用 `renderImage(0)`，不遍历 PDF 页数 | 每份 PDF 只有第一页进入 Word，多页证据材料不完整 |
| **T-09** | 图片固定为 `400pt × 600pt`；没有考虑纸张与页边距 | 横向材料、方形图、不同规格 PDF 均可能拉伸；图片还可能超出正文区域 |
| 关联隐患 | 中间 PNG 与上传文件同目录、同名 | 可能复用旧图片，且清理时可能误删原本已存在的 PNG |
| 关联隐患 | 手工关闭流，清理只在成功路径执行 | 出错后可能遗留文件、文件句柄；Windows 下文件占用更容易影响删除 |
| 关联隐患 | 图片共用段落，未设置明确分页 | 即使补上多页循环，仍可能出现图片挤在同页、自动溢页或末尾空白页 |

**对清单中两处表述的补充校正：**

- 重复路径分隔符并不必然导致失败，部分文件系统会容忍它。T-07 的核心是路径拼接、输入验证和文件枚举不可靠，不能只删除一个多余的 `/` 就视为完成。
- 当前 `if (!file.exists())` 会跳过已有 PNG 的生成，因此主要风险是**误复用旧 PNG，并在导出后删除它**，不能笼统认定必然覆盖已有图片。例如 `a.png.pdf` 对应 `a.png.png`，该文件已存在时会被直接使用。

### 1.2 T-09 的单位问题

原注释称“400 像素 × 600 像素”，但 `Units.toEMU(400)` 的参数是 **point（pt）**，因此实际设置为 `400pt × 600pt`。按 `72pt = 1 英寸`，约为 `14.11cm × 21.17cm`，不是注释所说的像素尺寸。API 单位依据见 [POI 4.0 Units 文档](https://poi.apache.org/apidocs/4.0/org/apache/poi/util/Units.html)。

实施时必须明确区分：PDF / Word 页面尺寸用 pt，渲染图尺寸用 px，Word 页面 XML 尺寸用 twip，图片嵌入尺寸用 EMU。不能把 px 直接作为 pt 传给 `Units.toEMU`。

### 1.4 调用方的关联问题：反复覆盖同一份 Word

当前生成服务的实际逻辑是：

```java
for (String path : paths) {
    File file = new File(fileRoot + path.substring(prefix.length()));
    PdfToWordConverter.pdfFilesToWordFile(
            file.getParentFile().getAbsolutePath(), temporary.getAbsolutePath());
}
```

这里传给工具的是**每个证据文件的父目录**，工具每次又新建 Word、以同一个目标路径写出。因此：

1. 来自不同目录的材料会多次生成，先前结果被后一次覆盖，通常只留下最后一次目录转换的结果；
2. 同目录多个证据路径会重复转换整个目录，增加耗时；
3. 实际输出范围是目录内文件，可能包含本次未选择的材料；
4. 空数组会返回刚创建但未写入合法 DOCX 的临时文件；路径前缀也未经显式校验就截取。

**仅修复工具的页码循环，并不能保证业务导出的多份材料全部保留。** 本方案确定联动修复为“仅汇总 evidence 中的文件、只生成一次 Word”，原因见防线 2 和第九章。现有目录扫描是实现缺陷，不再作为业务接口的范围规则保留。

## 二、解决方案设计

核心设计：**先校验并确定输入集合，再逐文件、逐页渲染，按 Word 正文区域等比嵌图，整个请求只生成一份 DOCX。**

```text
evidences JSON 数组 + upload.fileUrl
  → 校验 JSON、访问前缀、文件存在性与根目录边界
  → 确定 PDF 列表、顺序、去重规则
  → 预检页数 / 文件大小 / 页面像素预算
  → 创建一个 XWPFDocument，明确 A4 纸张和页边距
  → 对每份 PDF：打开 → 按页渲染 → 内存 PNG → 等比嵌图 → 关闭
  → 所有页面成功后写入请求独占的临时 DOCX
  → 交给 EvidenceWordExporter 下载并回收
```

### 防线 1：路径由标准 API 处理，校验失败有明确原因（T-07）

**生成服务负责访问路径映射，转换工具负责本地 PDF 输入；不要让两者重复猜测 URL 与文件路径的关系。**

| 层 | 计划做法 |
|---|---|
| JSON 输入 | 使用项目已有 Jackson 的树模型先校验数组与每个元素类型，再提取字符串；拒绝 `null`、空白、非法 JSON、非字符串数组、空数组和空元素；不能依赖可能自动把数字转成字符串的类型转换 |
| 访问路径 | 仅将反斜杠统一成 `/`，检查固定 `/pdf/file/` 前缀；相对路径不得为空，不含空路径段、`.`、`..`、冒号或 NUL；保留合法文件名内部空格；不接受完整 HTTP URL，不新增 URL 解码规则 |
| 本地路径 | 用 `Path.resolve` 组合配置根目录与相对路径；拒绝剩余部分为绝对路径及 `..` 路径段 |
| 根目录边界 | 对根目录及已存在的目标执行 `toRealPath()`，使用 `Path.startsWith` 检查真实路径仍在根目录内；拒绝目标路径中的符号链接 / Windows 重解析跳转，不允许经链接扩大范围；部署时上传目录不得允许无关用户替换路径 |
| 文件验证 | 目标必须是可读普通文件，扩展名按 `Locale.ROOT` 不区分大小写判断 `.pdf`；最终由 PDFBox 解析确认，不把后缀当成格式证明 |
| 目录兼容入口 | 检查目录存在、可读；只枚举本层可读普通 PDF 文件，不递归；枚举失败与“没有 PDF”分别报错 |
| 输出路径 | 业务链使用请求独占临时 DOCX；工具兼容入口校验目标父目录可写，拒绝目标与任一输入文件为同一真实文件 |

保留 `pdfFilesToWordFile(String path, String wordFilePath)` 作为目录兼容入口，其内部完成筛选、排序后委托统一转换核心。新增显式文件列表入口，供生成服务一次传入全部材料。

显式列表入口确定为 `convertPdfFilesToWord(List<Path> pdfFiles, Path output, PdfToWordProperties properties)`，采用静态无状态方法，不读取 Spring 容器。目录兼容入口内部构造并校验默认参数后委托核心，不影响原签名；业务生成服务直接调用显式列表入口，不通过目录兼容入口。

显式列表保留 evidence 数组顺序，按真实文件身份去重、保留首次出现位置；`Files.isSameFile` 覆盖同一文件的不同路径及硬链接，数量上限较低，逐项比对即可。目录兼容入口采用不区分大小写文件名字典序，再以原文件名为次级比较键；不增加数字自然排序。`10.pdf` 排在 `2.pdf` 前是该规则的预期结果，且只影响兼容入口。

Windows 历史反斜杠路径及 Linux 正斜杠路径均接受。上传代码直接返回本地形式的路径，没有 URL 编码步骤，因此不猜测 `%2F` 等字符串是否应解码，也不把 `+` 变为空格；完整 URL 和空路径段等历史异常输入明确报 400，原始数据不自动改写。

### 防线 2：收集全部输入后只生成一次（调用方联动）

**决策：业务接口只导出 `evidences` 明确列出的 PDF，不扫描父目录，不提供目录范围切换开关。**

依据如下，均来自当前源码：

1. `SubTaskIdDto.evidence` 的注释明确为“仅代表该用户某一项子任务的附件”，说明输入集合具有子任务范围。
2. `ProjectController#fileUpload` 以 `user.getUserName()` 作为目录名，`UploadUtils#uploadFile` 把文件保存为 `<上传根>/<工号>/<雪花ID>.pdf`。同一用户不同项目 / 子任务共用目录，目录不代表子任务。
3. `ProjectServiceImpl#resultProject` 把各项 `evidenceList` 序列化保存，附件范围与列表绑定，而不是与整个用户目录绑定。
4. 同级 ZIP 导出接口按 `dto.getEvidence()` 的数组逐个传给下载工具，也没有遍历父目录。Word 应使用相同的材料集合。

例如某用户目录里有任务甲的 A、B 和任务乙的 C，甲的 evidence 为 `[A, B]`，Word 中必须只有 A、B。现有生成服务“保留目录规则”的注释是职责拆分时保留旧行为的说明，不能推翻 DTO、存储结构和 ZIP 接口一致表达的附件范围。

服务一次校验、去重、收集列表，一次调用转换核心，一次写出。目录兼容入口只为原工具签名保留，不参与 HTTP 导出，也不作为失败后的回退路径。

### 防线 3：遍历全部页，失败时不交付残缺结果（T-08）

每个 PDF 使用 try-with-resources 打开，读取 `getNumberOfPages()`，遍历 `0..pages-1`。索引从 0 开始，对用户显示页码时加 1；使用 `renderImageWithDPI(pageIndex, dpi, ImageType.RGB)`，默认 DPI 确定为 150。PDF 解析使用 `MemoryUsageSetting.setupTempFileOnly(maxScratchBytes)` 的有界临时存储模式，其中 `maxScratchBytes` 由 `max-pdf-scratch-size-mb × 1024L × 1024L` 换算，默认 256MiB；预检与正式渲染采用相同加载方式，不另写死预算。

PDFBox 2.x 的渲染 API 支持指定页码及 DPI，语义参考 [PDFBox 2.0.13 PDFRenderer 文档](https://pdfbox.apache.org/docs/2.0.13/javadocs/org/apache/pdfbox/rendering/PDFRenderer.html)。本轮另通过本机 **2.0.24 JAR 的 javap 只读核对**，确认 `PDDocument.load(File, MemoryUsageSetting)` 与 `setupTempFileOnly(long)` 存在；旧测试报告中的版本也与 POM 一致。本方案不切换库版本，不把旧报告当成本方案已经编译通过。

| 场景 | 计划行为 |
|---|---|
| 正常多页 PDF | 所有页面按原顺序插入，包括原本的空白页 |
| 零页文档 | 返回明确错误，不生成空 Word |
| 文件损坏、不能读取 | 整次生成失败，指出材料名与失败阶段 |
| 加密 / 需密码 PDF | 本迭代统一拒绝加密文档，提示提交未加密版本；不新增密码参数 |
| 第 N 页渲染失败 | 整次失败，提示文件与第 N 页；不跳页、不返回前 N-1 页当作成功 |
| 超出页数或资源预算 | 生成前拒绝并提示上限，不截断后继续成功 |

默认不增加封面、标题页或页码标签，使页面对应关系便于验收：**嵌入图片数 = 汇总输入 PDF 的总页数**。

### 防线 4：一页 PDF 对应一个 Word 页面（T-08 / T-09）

- 每张页面图使用独立段落，居中，段前段后间距为 0；
- 第一张图片不设置段前分页，后续图片所在段落设置明确的段前分页；
- 不在最后一张图片后追加分页符，避免人为制造末尾空白页；
- 明确纸张、页边距与段落行布局，为行框预留高度；不能设置会裁掉大图片的固定小行高；
- 总页数以 Word / WPS 实际打开后的排版为准，不能仅靠图片数量或 DOCX 的统计属性判定页面数。

清单示例中的 `r.addBreak()` 是普通换行，无法保证新页面。POI 区分普通换行与指定类型的换行，见 [XWPFRun API 文档](https://poi.apache.org/apidocs/4.0/org/apache/poi/xwpf/usermodel/XWPFRun.html)。本方案使用段前分页表达页面边界。

### 防线 5：按可用宽高等比缩放，统一尺寸单位（T-09）

第一版采用统一 **A4 纵向 Word 页面**，横向 PDF 也等比放入正文区域。优先保证完整展示，横向材料会留白；逐页横纵向切换涉及分节，作为后续增强。

确定默认版式：A4 约 `595.3pt × 841.9pt`，四边页边距 `36pt`，图片段落额外预留高度 `18pt`。计算得到可用图片区域约 `523.3pt × 751.9pt`。这些值必须同步写入 Word 页面属性，不能只在缩放计算中使用。

```text
1 英寸 = 72 pt = 1440 twip = 914400 EMU
1 pt = 20 twip = 12700 EMU

Wmax = 纸张宽度pt - 左边距pt - 右边距pt
Hmax = 纸张高度pt - 上边距pt - 下边距pt - 段落预留高度pt

W0 = 渲染图宽度px × 72 / 渲染DPI
H0 = 渲染图高度px × 72 / 渲染DPI
s  = min(Wmax / W0, Hmax / H0, 1)
最终宽度pt = W0 × s
最终高度pt = H0 × s
```

宽高共用一个缩放系数，限制其同时落在正文区域内；末尾 `1` 表示默认只缩小、不把小页面强行放大。使用渲染后的实际宽高，遵循 PDFBox 2.0.24 对裁剪框和页面旋转的渲染结果，不再另写页面旋转或特殊缩放补偿。输入框尺寸必须有限且为正数，像素预算使用该版本渲染器相同的 CropBox / DPI 尺度保守向上取整，在分配位图前检查。

最终调用 `Units.toEMU(widthPt)` / `Units.toEMU(heightPt)`，结果作为 `addPicture` 的宽高。`addPicture` 接收 EMU 尺寸，单位依据见 [POI XWPFRun 的 addPicture 文档](https://poi.apache.org/apidocs/4.0/org/apache/poi/xwpf/usermodel/XWPFRun.html#addPicture-java.io.InputStream-int-java.lang.String-int-int-)。

举例：一张约 `842pt × 595pt` 的横向页面，在上述正文区域内缩放为约 `523pt × 370pt`，而不是强行设为 `400pt × 600pt`。宽高比保持约 `1.415`，文字、圆形印章和表格不因非等比设置变形。

### 防线 6：逐页内存 PNG，移除上传目录的中间图片

优先采用：**当前页 BufferedImage → ByteArrayOutputStream 编码 PNG → ByteArrayInputStream → POI 嵌图**。不再将 PNG 写入上传目录，不再用文件名判断是否已有“缓存图片”。

| 资源 | 计划归属与释放方式 |
|---|---|
| `PDDocument` | 每份 PDF 独立 try-with-resources，渲染完成或异常均关闭 |
| `BufferedImage` | 仅保留当前页引用；嵌图后在 finally 调用 `flush()` 并结束引用，便于回收 |
| 图片编码流 / 输入流 | 每页独立创建并限定生命周期；验证 `ImageIO.write` 返回值，编码失败立即报错 |
| `XWPFDocument` | 每次生成一个，try-with-resources 管理；全部材料结束后统一写出 |
| DOCX 输出流 | try-with-resources；写入失败由生成服务删除本请求临时文件 |
| 最终临时 DOCX | 生成失败由 `EvidenceWordService` 回收；生成成功交给 `EvidenceWordExporter` 下载后回收 |

**内存 PNG 不等于零内存成本，也不等于常量内存。** POI 仍会持有文档中的图片数据，PDFBox 也可能持有解析缓存；逐页处理只避免额外同时保留全部高分辨率位图。因此仍必须设置总页数、总文件大小、像素预算与并发上限。

**第一版不设 PNG 落盘开关。** PNG 逐页在内存编码，PDFBox 自身的解析临时文件与最终 DOCX 使用 JVM 临时目录，由各自的资源所有者关闭 / 删除。PDFBox 临时存储限制为每次打开文档最多 256MiB，不意味着位图或 POI 图片数据也已转移到磁盘。未来如改变 PNG 存储方式，须另写方案，不能在本次实现中临时分叉。

### 防线 7：限制资源消耗，异常信息保留定位线索

第一版确定执行以下限制：

1. **生成前预检**：文件数量、单文件大小、总输入大小、单 PDF 页数、总页数；预检 PDF 逐个打开并关闭；
2. **每页渲染前检查**：根据有效页面尺寸、DPI 和旋转估算像素数量，使用 `long` 避免乘法溢出；超过预算先拒绝，不先分配大图再检查；
3. **生成过程累计**：PNG 编码总字节数设置预算；编码输出使用计数上限，达到剩余预算立即中止，不能先无限增长 `ByteArrayOutputStream` 再检查；DOCX 输出同样使用有界流，写完复核文件大小；超限拒绝并清理；
4. **每实例并发控制**：默认 1 个许可，服务内共享 `Semaphore`，`tryAcquire()` 不排队等待；从预检开始到 DOCX 写完占用许可，在 finally 释放；下载过程不持有转换许可；
5. **生成时限**：使用 `System.nanoTime()` 计算 60 秒预算，包含预检、渲染、编码和写出，不含 HTTP 下载；在各阶段和每页前后检查，发现超时或线程中断即停止进入下一阶段并清理；
6. **资源前提**：首版要求 JVM 最大堆至少 1024MiB；不足时只拒绝 Word 生成并报 503，不阻止其他业务启动。临时目录必须能创建、写入、关闭和删除本请求探测文件；探测失败明确报服务器错误。

预检与渲染之间仍可能发生文件变化，实际转换时再次校验页数和读取结果；任何变化导致失败均回收本次临时 DOCX。本方案不承诺仅靠阈值彻底排除 OOM，也不把 HTTP 超时当作自动停止渲染任务的保证。

新增 `PdfConversionException`，确定携带 `status`、`stage`、材料文件名、页码及 cause，语义分类见第九章。示例：`佐证材料 report.pdf 第 3 页渲染失败`、`本次材料共 51 页，超过 50 页上限`。用户提示不包含服务器绝对路径或底层异常全文；内部日志记录请求标识、文件数、页数、耗时和失败阶段，不记录图片内容。

## 四、配置说明（实施时写入）

以下数值是**确定的首版默认规则，尚未压测，不是已证实的生产容量**。本轮将原来的 100 页 / 2 并发收敛为 50 页 / 1 并发，以适应同步 HTTP 生成和 POI 累计持有图片的实现。配置后缀 `mb` 统一表示 MiB，即 `1024 × 1024` 字节，所有字节计数使用 `long`。

```yaml
evidence:
  word:
    render-dpi: 150
    page-width-pt: 595.3
    page-height-pt: 841.9
    margin-pt: 36
    paragraph-reserve-pt: 18
    max-files: 20
    max-pages-per-pdf: 50
    max-total-pages: 50
    max-file-size-mb: 50
    max-total-input-size-mb: 100
    max-page-pixels: 12000000
    max-total-image-size-mb: 64
    max-output-size-mb: 64
    max-pdf-scratch-size-mb: 256
    max-concurrent-exports: 1
    max-generation-seconds: 60
    min-jvm-max-heap-mb: 1024
```

| 配置 | 用途与调整原则 |
|---|---|
| DPI | 首版 150；合法范围 72～200，禁止默认跳到 300；调整需通过相同容量验收 |
| 纸张 / 边距 / 段落预留 | 同时用于写 Word 页面属性与计算图片可用区域；调整后重验横向和接近满页的材料 |
| 文件 / 页数 / 输入大小 | 限制解析和生成总量；超出时整次拒绝，不截断 |
| 单页像素 | 防止页数很少但页面尺寸极大的 PDF 在渲染时分配超大位图 |
| 图片总量 / 输出大小 | 限制文档累计数据；图片总量是提前检查，最终文件大小是交付前检查 |
| PDF 解析临时存储 | 单个同时打开的 PDF 最多 256MiB；使用 JVM 临时目录，关闭文档回收 |
| 并发数 | 首版 **每实例 1 个**，无等待队列；多实例按此配置独立执行 |
| 生成时限 | 60 秒，阶段边界与有界输出写入时检查；不承诺能强制打断一页内部的第三方渲染调用 |
| JVM 最大堆 | Word 生成要求至少 1024MiB；不足报 503，其他业务仍可启动 |

绑定时使用 `@Validated` 与项目已有 Bean Validation，校验所有限制为正数、DPI 为 72～200、纸张扣除边距和段落预留后宽高为正数、单文件 / 单 PDF 上限不大于总量上限。配置非法时启动失败；临时目录和堆资源检查在导出请求中执行，避免仅因 Word 环境不足阻断整套业务启动。转换工具接收显式配置参数，不自行从 Spring 容器取配置，也不引入可变全局静态参数。

请求 JSON 原始数组最多 20 项，先检查数量再做文件 I/O；重复路径也计入原始数组限制，去重后再计算页数及输入大小。文件达到字节阈值允许，大于阈值拒绝；页数、图片量、输出大小采用相同的“允许等于、拒绝超过”规则。临时目录解析为 `java.io.tmpdir` 的真实目录，首版不增加路径配置、不创建上传根目录、不创建缺失的 PDF 或上传目录。

页数、像素与大小上限是准入规则，60 秒是生成预算；不保证每一份同时满足所有准入上限的复杂 PDF 都能在预算内完成。复杂材料超时须报错，不能降低 DPI、跳页或截断内容再返回成功。

当前上传配置已有 50MB 文件限制，但它约束上传请求，**不能替代导出文件集合、总页数或渲染像素限制**。

| 维度 | 改造前 | 改造后目标 |
|---|---|---|
| **T-07 路径** | 手工拼接、截取前缀；目录错误可能 NPE | 标准路径解析、明确验证、真实路径根目录约束，错误可定位 |

| **容量** | 无页数 / 像素 / 并发预算 | 首版 20 项 / 总 50 页 / 单实例 1 转换 / 60 秒预算，图片和输出各最多 64MiB；超限明确拒绝 |
| **可编辑性** | Word 内是图片 | 仍为页面图片，不新增 OCR 或可编辑表格能力 |

**具体效果示例：**

子任务的 evidence 数组为 `[证明A.pdf, 证明B.pdf]`，A 为 3 页、B 为 2 页，即使它们位于不同目录，也应生成一份 **5 页 Word**：先 A 的 1～3 页，再 B 的 1～2 页。横向证明保持横向图片比例并完整缩放显示，圆形印章不变椭圆；同工号目录中另一项任务的 C 不进入文档。

若数组为 `[B, A, B]`，则按首次出现顺序生成 B 的 2 页，再 A 的 3 页，共 5 页，第二次 B 不重复。若数组所列某份 PDF 缺失或不能转换，整次报错，不用该目录内其他文件代替。

验收必须同时满足：**材料集合口径正确、图片引用与页序完整、实际 Word 分页正确、比例正确、原文件未改动、失败文件已回收**。只清除 TODO 注释或只看到“下载成功”，不能认定问题完成。

### 9.2 固定 HTTP / JSON 错误分类

专用异常先于通用 RuntimeException 处理，保留原 cause 仅供日志排查。异常公开文案由分类构造，不直接使用文件系统或 PDFBox 异常原文。缺失文件的响应不附带绝对路径；无权限读取也不向用户泄露部署细节。

| 场景 | HTTP 与 body.code | msg 示例 / 行为 |
|---|---|---|
| 非法 JSON、空列表、非字符串元素、错误前缀、路径越界、链接跳转、非普通文件或非 PDF 后缀 | 400 | `佐证材料路径不合法` / `请选择至少一份 PDF 佐证材料` |
| 合法路径对应的选中 PDF 已不存在 | 404 | `佐证材料 123.pdf 不存在，请重新上传`；整次失败 |
| 超过文件项数、页数、输入大小、页面像素、图片累计或输出预算 | 413 | `本次材料共 51 页，超过 50 页上限，请分批导出` |
| 确认的格式无效、零页或加密 PDF | 422 | `佐证材料 123.pdf 已加密，请提交未加密 PDF`；不新增密码参数 |
| 文档内部渲染 / 编码异常、未分类解析 I/O、临时目录故障、输出写入失败、服务器读权限问题 | 500 | `佐证材料 123.pdf 第 3 页转换失败，请联系管理员`；底层路径仅入内部日志 |
| 单实例许可已占满 | 503 | `Word 导出繁忙，请稍后重试`；`Retry-After: 5`，无等待队列 |
| JVM 最大堆不足、生成预算用尽或线程中断 | 503 | `Word 导出资源不足` / `Word 生成超时，请拆分材料后重试`；不返回部分 DOCX |

格式分类不得依靠模糊字符串匹配把所有 IOException 当“文件损坏”；无法可靠识别的底层故障按 500 处理并记录 cause。PDFBox 的加密标记 / 专用密码异常可用于确定 422。预算由本方案显式计数器抛 413；PDFBox 内部临时存储失败若无法精确分类，同样按 500，不伪装为用户输入错误。

成功仍返回原下载组件的 DOCX 文件内容。生成失败发生在 `UploadUtils.download` 设置头和写字节前，响应为 `application/json`，不带附件下载头。下载开始后出现连接错误，不再尝试向已提交响应追加 JSON；沿用 exporter 的清理职责，该阶段与“生成失败”分开统计。

前端如果将失败响应作为 Blob 接收，应按 Content-Type 解析 JSON 并显示 `msg`；本仓库不含前端，实现文档仅规定协议，不宣称客户端处理已改好，也不把前端改动纳入本次代码清单。

### 9.4 验收样本与发布失败分支

验收样本固定包括：5 页基础材料、10 页含小号中文 / 表格 / 印章的典型材料、50 页含扫描图和文本的混合材料，以及横向、方形、旋转、CropBox、空白页、未嵌入字体、加密、伪 PDF、巨幅单页和故障注入材料。每个正常页面带可辨识编号，便于对照输入 / 输出顺序；采用实际材料时先复制到独立测试目录，不修改真实上传文件。

首版发布检查使用第四章默认配置，在第 9.3 节资源基线上每组正常样本重复生成 20 次；第五章给出的耗时、内存、分页、比例和文件保护标准全部通过才能发布。PNG 累计过限或生成超时是明确拒绝行为，不能把该行为当作样本正常导出通过。

- 默认样本清晰度不合格：可将 DPI 调到 200，重新跑全部容量与排版验收；仍不合格则暂停本功能发布，用户用原 PDF / ZIP 查看，不新增 OCR。
- 默认样本容量不合格：先降低并发以外的实际负载、修复字体 / 存储问题或增加实例资源，重新验收；生产并发仍为 1。不静默减少页数、降 DPI 或恢复目录扫描。
- 个别 PDF 格式或渲染不支持：按固定错误分类返回并保留日志，不能跳过该材料成功生成。
- 配置确需调整：在公共节点明确记录变更参数与验收结果，重新执行同一套门槛；不新增环境特判代码。

### 9.5 明确不作扩展的事项

HTTP 接口参数仍为 `SubTaskIdDto` 的原 `evidence` JSON 字符串，生成服务仍返回临时 `File`；不迁移数据库字段、不增加保存 DOCX 记录、不改接口为异步链接、不增加整目录范围开关、不新增 Redis 队列或锁、不改变原 PDF / ZIP 下载。证据归属和导出权限独立于文件系统校验，本方案不通过“目录相同”推断授权，也不声称权限风险已修复。

这些是首版已经确定的范围约束，不是待确认项；若未来需要 OCR、逐页横纵向分节、异步大文件或归属权限改造，另立任务。
