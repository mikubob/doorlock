## 一、问题定性

**规划结论：导入后保留 `sys_project_item`，第一阶段仅实现按来源子项差量合并，不开放清理；第二阶段按需提供独立预览的受控替换。已有结果、Redis 暂存、扩展材料或审批的项目，冻结任务集合及评分规则。九章逐项给出待确认项的默认决策、证据及实施门槛。**

这里存在两个不同的数据对象：

| 对象 | 当前用途 | 导入后的处理建议 |
|---|---|---|
| `sys_project_item` | 保存分类、子项及评分标准，是任务生成来源 | 保留；导入不删除、不修改 |
| `sys_task` | 保存项目实际任务，供教师填写及结果查询使用 | 根据来源关系新增或更新；默认不删除 |
| `sys_result` | 教师结果及完成状态，含 `task_id`；独立暂存入口实际写 Redis | 全部保留，不能通过导入重建 |
| `sys_result_extend` | 扩展项及佐证，含 `task_id`、`result_id` | 全部保留，不能通过导入清理 |
| `sys_result_item` | 项目级审批信息，含 `p_id`，不是任务级记录 | 全部保留；作为项目冻结条件之一 |

因此，原注释中的“删除原来的 projectItem 表数据”不宜作为导入的默认行为。删除来源会使后续维护、再次导入和来源追溯失去依据；直接清空任务则可能破坏结果与任务的关联。

### 1.1 当前代码的问题链

**对清单结论的补充校正：**

1. 当前链路首先存在空主键的插入失败风险。仓库 SQL 中 `sys_task.id` 是非空字符串主键；是否存在额外主键填充器、线上行为如何，应在实施前核对。不能把“重复插入 N 批”当作已经观察到的运行结果。
2. `saveBatch` 来自 MyBatis-Plus，其内部可能已有事务支持。Controller 没有事务，不等于已证明当前一定留下半批；应结合实际依赖与事务代理验证。需要新增的是覆盖整个业务流程的 Service 事务。
3. 同名同类型的 `category`、`standard`、`score`、`isFile`、`isExtend`、`remark` 可以复制；确定不匹配的是主键，以及需要手工映射的项目 ID、名称。显式映射用于明确规则，不应泛称所有字段都失效。

## 二、解决方案设计

### 2.1 业务策略选择

| 策略 | 行为 | 评价 |
|---|---|---|
| 全量删除后重建 | 删除整个项目的旧任务，再生成新 ID | 不推荐；可能破坏结果关联，也会删除 Excel 等其他来源任务 |
| 受控替换 | 同来源任务保留 ID；更新无业务数据任务；清理完整快照之外的无引用来源任务 | 可作为明确的高级操作，必须预览并限制范围 |
| 差量合并（默认建议） | 按项目与来源子项匹配；新增缺失项，更新允许变更的已有项，不删除未选任务 | 适合现有列表请求，误删风险较低 |
| 禁止重复导入 | 项目已有任务即拒绝 | 简单，但无法补充新子项，适合作为临时止血规则 |

原清单推荐“删除未产生结果任务，再插入”。本计划将其收紧为**默认合并、可选受控替换**：现有请求是一个列表，无法证明它是项目的完整快照；而已有任务没有来源标记，也无法证明哪些任务可由本接口删除。

两种模式共用以下原则：

- **子项始终保留**，导入不会消耗来源数据。
- 幂等键采用 **`(p_id, source_project_item_id)`**，不采用 `(projectId, taskName)`。名称可修改，也允许不同分类同名。
- 已映射任务继续使用原 `Task.id`；新增任务使用现有雪花 ID 工具生成字符串主键。
- 默认合并仅处理选中的来源子项；未选中不代表需要删除。
- 存在任意项目业务记录时，只允许完全无变化的重复请求成功，新增、更新、清理均拒绝。
- 一次请求存在任意错误或冲突则整批失败，不做隐式部分成功。

### 防线 1：服务器决定数据来源

保留原 `POST /project/item/insertIntoTask` 路径及列表请求，降低前端迁移成本。旧 VO 只用于提取 `projectId` 与子项 `id`，评分规则从数据库重读。

实施时依次校验：

1. 请求非 null、非空，并设置合理的批量上限。
2. 第一项及每一项非 null，项目 ID 非空且全部相同。
3. 子项 ID 非空、不重复，数据库中全部存在，并属于指定项目。
4. 项目存在；`status=0`（未发布）且未使用时允许变更，`status=1`（已发布）只允许无变化重试；`status=3`、null 及未知状态拒绝。发布和导入遵守同一项目锁，具体依据见 9.2。
5. 来源确实是可生成任务的子项。按仓库 DDL 语义核对 `grade=2`、父级分类存在、父子属于同一项目、分类 `parent_id=0`。
6. 从父级读取分类名，按 9.4 校验名称、标准、分值、标志、字符集及数据库字段长度。SQL 的子项分值为 varchar、实体为 Integer，必须先核验原始字符串，不能依赖隐式转换后再判断合法性。

不信任请求的 `category`、`pname`、`standard`、`score` 等副本。对只有分类没有子项的占位行，返回明确错误；前端应先过滤占位行，后端仍保留校验。

### 防线 2：权限与项目生命周期检查

Controller 接收当前身份，Service 按 9.3 校验：有效 `admin` 角色可管理全部项目；非超管只能管理认证用户名与 `create_name` 相同的项目。当前无明确委派管理关系，院长、书记、学院管理员和流程参与者不因此获得他人项目的导入权限。后续委派能力另行设计，不在第一阶段推断授权。

`Project.createName` 是创建人工号字段，不能直接与用户数字 ID 比较。身份必须从认证上下文获取，不能由请求指定。

只允许管理者维护未发布且未使用项目的任务；项目发布后或已有教师暂存、提交、扩展材料、审批时，冻结任务集合及评分规则。虽然 `Project.status` 的实体注释仅列出 1/3，`getProjectList` 的源码注释与 DDL 默认值确认 0 表示未发布，不需要新增状态值。

### 防线 3：建立来源关系并显式映射

建议在 `Task` 增加可空 `Integer sourceProjectItemId`，映射 `source_project_item_id`。

| 任务字段 | 数据来源或规则 |
|---|---|
| `id` | 已有任务保留；新增时 `String.valueOf(snowFlowUtils.nextId())` |
| `pId` | 已验证且锁定的项目 ID |
| `sourceProjectItemId` | 数据库中的子项 ID |
| `category` | 同项目父级分类的 `pname` |
| `taskName` | 子项 `pname` |
| `standard` / `score` | 子项的评分标准与分值 |
| `isFile` / `isExtend` / `remark` | 子项的对应字段，经校验后赋值 |
| `result` | 非持久化字段，不参与导入 |

新增唯一索引，保证一个项目的同一来源子项最多对应一个任务。Excel 或其他来源任务的来源字段保持 null，本接口不会自动清理或覆盖这些任务。

### 防线 4：差量比较与业务数据保护

默认合并的处理矩阵：

| 当前情况 | 处理结果 |
|---|---|
| 来源子项尚无映射，项目未发布、未冻结且历史审核通过 | 新增任务 |
| 已有映射，全部导入字段相同 | 跳过，原任务 ID 不变 |
| 已有映射，字段不同，项目未发布、未冻结且历史审核通过 | 原位更新，原任务 ID 不变 |
| 项目已发布或已有业务数据，需要新增或更新 | 返回冲突，整批不写入 |
| 未选中已有任务 | 保留，合并模式不推断删除意图 |
| 历史任务无来源，疑似与子项重复但无法确认 | 阻止相关导入并提示先处理映射，不能再生成一个疑似重复任务 |

**“已有业务数据”采用保守定义**：存在项目首次暂存持久化标记、旧 Redis 暂存、任何 `sys_result` 行、任何关联该项目任务或结果的 `sys_result_extend` 行，或任何项目级 `sys_result_item` 历史行，即视为已使用。不以分数大于 0、`is_finish=1` 或材料非空作为唯一依据。审批检查包含逻辑删除的历史行，使用专用 SQL，不依赖 MyBatis-Plus 默认过滤。

实际 `projectStaging` 将答案写到 Redis 的 `用户名-项目ID` 键，15 天过期；它不写 `sys_result`。因此不能把“查询结果表”当作“已检查所有暂存”。第一阶段增加项目导入状态表记录首次暂存时间：暂存入口取得项目行锁并校验任务后，先提交冻结标记，再写 Redis；缓存写入失败也保持冻结并允许用户重试，避免数据库与 Redis 非原子写入放开任务变化。该保守行为应在错误提示中说明。旧 Redis 缓存在维护窗口审核并回填，核验失败的项目不开放变更。标记不随 Redis 过期自动撤销。

### 防线 5：受控清理，明确删除边界

受控替换作为第二阶段功能，建议独立提供预览与执行入口，使用明确 DTO，不把删除模式偷偷加到现有列表请求中。

```text
POST /project/item/taskImport/preview     （拟新增）
POST /project/item/taskImport/replace     （拟新增）
```

替换输入必须声明完整快照。服务器校验它与当前项目全部可导入子项一致；空快照不等同于“清空任务”，拒绝执行。若确实需要清空，应走独立维护流程。

预览返回新增、更新、待删除、跳过、保留的其他来源任务，以及阻断原因；执行携带预览摘要，服务器在锁内重算。任务、来源或业务记录变化导致预览失效时，返回冲突并要求重新预览。

仅允许删除：

1. `p_id` 为当前项目；
2. 来源已确认，`source_project_item_id` 非 null；
3. 不在当前完整来源快照中；
4. 没有任何结果、暂存、扩展材料及其他任务引用；
5. 项目未发布、没有已产生的业务记录或暂存冻结标记，且预览与当前状态一致。

删除使用限定项目和任务 ID 的 `DELETE`，**禁止 TRUNCATE、禁止全表删除、禁止级联删除结果和文件**。同来源的仍有效任务保留主键，不能“保留旧任务后再生成同一来源的新任务”。

被删除来源的旧任务可通过保留的来源 ID 识别；不建议使用会级联删除任务的物理外键。来源删除后的历史追溯可结合备份和审计，是否增加来源快照表属于后续增强。

### 防线 6：Service 事务与并发互斥

新增独立 `ProjectTaskImportService`，由 Controller 调用其公开事务方法。建议使用 `@Transactional(rollbackFor = Exception.class)`，覆盖检查、比较、写入、受控清理与成功审计。失败抛异常触发回滚，不能捕获后只返回一个错误对象而提交已写数据。

按项目对 `sys_project` 现有记录执行 `SELECT ... FOR UPDATE`，在同一个数据库事务中保持锁到提交。不同项目可并行，同一项目串行；唯一索引提供最终去重约束。关键检查在取得锁后进行，必须读取锁后的当前已提交状态，避免基于旧快照决策。

**只锁导入入口不足以防止“检查时无结果，删除时结果已写入”。** 任务新增/修改/删除、项目子项修改/删除、项目删除以及教师暂存、提交、扩展项和审批写入路径，应遵循相同项目锁顺序。取得锁后重新检查项目、任务是否存在及是否仍允许操作。旧版本实例不遵守锁协议，因此涉及清理的版本不宜混跑。

发布入口同样接入项目锁，发布前确认任务集合与导入状态；Redis 暂存入口按上述“先持久化冻结、后缓存写入”的顺序执行。锁后用于比较与冻结判断的查询采用明确的当前读（必要时 `FOR UPDATE`），或对整个事务明确使用 READ COMMITTED；实施中固定一种方案，不能在 MySQL 默认 REPEATABLE READ 下混用锁前快照和锁后普通查询。

实施前盘点包括 Excel 导入在内的所有写入口。未完成并发协议与业务写入回归前，受控替换不得启用；不能声称一个唯一索引或单独的导入锁已经解决结果写入竞态。

```java
// 业务流程示意，非可直接编译的代码；方法名均为拟设计
@Transactional(rollbackFor = Exception.class)
public TaskImportResult merge(List<ProjectItemImportParam> request, User operator) {
    ImportSelection selection = validateRequest(request);
    Project project = lockProject(selection.getProjectId());
    checkManagePermission(operator, project);
    List<ProjectItem> sources = loadAndValidateSources(selection);
    ImportPlan plan = calculateDiffUsingCurrentData(project, sources);
    checkLegacyMappingsForChanges(plan); // 纯无变化重试不因其他任务未审核而失败
    if (plan.hasChanges() && !canChangeTasks(project)) {
        // 包含发布状态、数据库业务记录、首次暂存标记及历史审核门槛
        throw new TaskImportConflictException("项目已发布、已使用或历史来源未核验，不能变更任务");
    }
    applyDiffOrThrow(plan); // 检查批量返回值及实际写入结果，失败即回滚
    writeSuccessAudit(plan, operator);
    return buildResult(plan);
}
```

### 防线 7：返回可核对的执行结果

沿用仓库真实的 `ApiResult.ok("data", ...)`、`ApiResult.error(...)` 风格，不能引用仓库不存在的 `ApiResult.fail`。业务错误码与实际 HTTP 状态分别处理；仅在 Map 中写 `code=409` 不会自动改变 HTTP 响应状态。

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "projectId": 1001,
    "mode": "MERGE",
    "requested": 3,
    "created": 1,
    "updated": 0,
    "skipped": 2,
    "deleted": 0,
    "retainedOtherTasks": 1
  }
}
```

数字为示意数据。合并成功应满足 `requested = created + updated + skipped`，且 `deleted=0`。空请求为 400，未登录为 401，无管理权限为 403，项目不存在为 404，冻结或预览失效为 409；具体接入统一异常处理器。

日志记录操作者、项目、模式、变更任务 ID、计数、耗时及失败原因。受控清理保留删除前字段快照用于恢复，不记录教师材料正文。前端根据计数提示“新增 1 项，跳过 2 项”，重复点击提示“无变化”。

## 四、历史数据与实施规则

### 4.1 历史来源映射

增加字段后，历史任务来源默认 null。不能直接依据名称批量回填或自动删除：改名、同名分类、Excel 任务与子项导入任务均可能造成歧义。

1. 备份当前任务、子项、结果、扩展和审批数据，统计来源可匹配与无法匹配的数量。
2. 以项目、分类、名称、标准、分值及标志等生成候选匹配报告，仅供审核。
3. 由业务人员确认来源后回填，保留原任务 ID；每个来源只能确认一个对应任务。
4. 已有多个候选或来源缺失，列入人工处理，不自动合并结果、不删除任务。
5. 审核完成后持久化项目审核状态、审核人和时间，再开放其变更导入；未核对项目不得新增疑似重复任务。已映射且无变化的重复请求仍可通过，不能因其他来源未审核而把纯重试误当成新增。

已有重复任务的治理单独执行：无业务引用的重复项可在审核后清理；任何已引用项均保留，涉及结果合并需要另行方案，不能放入正常导入请求。

### 4.2 实施阶段顺序

| 阶段 | 内容 | 完成条件 |
|---|---|---|
| A：实施前核验 | 按九章默认规则核验线上结构、旧 Redis、历史来源与权限数据 | 形成核验报告；无法核验的项目保持禁止变更 |
| B：基础改造 | 来源字段、唯一索引、导入状态、主键生成、校验、授权和 Service 事务 | 合并、异常与回滚用例通过 |
| C：历史映射及并发协议 | 历史审核、Redis 暂存标记、全部写入口锁协议 | 审核状态可追溯，跨入口并发用例通过后才开放合并 |
| D：可选受控替换 | 预览摘要、完整快照、清理审计 | 无引用限定删除和恢复演练通过 |

默认模式固定为 MERGE，原列表入口不允许调用者切换删除模式。第二阶段替换入口发布前保持不可用，可通过现有功能授权体系控制；无需为本问题新增一组未经确认的环境配置。

## 六、上线与回滚

### 6.1 上线顺序

1. 以九章默认规则完成权限、线上库结构、历史来源、旧 Redis 及全部写入口核验；保留未通过项目的关闭清单。
2. 在预发完成迁移、历史映射审核、功能与并发验证，演练备份恢复。
3. 生产维护窗口暂停相关导入、任务维护和填报写入，备份相关数据。
4. 执行来源字段、唯一索引及导入状态表增量迁移；按审核报告回填来源、审核状态与旧暂存冻结标记。
5. 发布全部遵循项目锁协议的相关实例，避免旧入口绕过协议；先开放合并。
6. 验证首次导入、重复导入、已有数据冻结和历史查询，逐步恢复相关入口。
7. 受控替换在独立验收通过后开放，不与基础能力默认同时启用。

DDL 的锁表影响需根据实际 MySQL 版本、表规模和迁移方式评估，不能承诺零停机。线上不运行仓库中的整库导出 SQL，只运行审阅过的增量脚本。

### 6.2 回滚

- **事务内失败**：直接回滚本次请求，恢复请求前状态。
- **版本回滚**：先暂停导入与清理入口，再切回兼容版本；可空来源字段和索引暂时保留，避免删除追溯信息。旧版本不具备幂等和锁协议，不能继续开放原导入入口。
- **已提交的任务更新/清理**：代码回滚不能恢复数据。依据审计和备份按项目恢复原任务 ID 及字段；恢复前重新核对期间的结果、扩展、审批与来源冲突。
- **已经产生后续业务记录**：不能直接整库覆盖或删掉新记录，应进入人工数据修复流程，必要时停写并评审专项恢复方案。

| 新增、更新、跳过和删除数 | 重复导入应跳过；合并删除数必须为 0 |

### 7.1 具体业务示例

项目 P 原有来源子项 A、B，对应任务 T-A、T-B，另有一个 Excel 任务 T-X：

1. 首次导入 A、B：若尚无映射任务，新增两个任务；子项 A、B 保留。
2. 再次导入相同内容：跳过两项，T-A、T-B 的 ID 和项目任务数量均不变。
3. 项目未发布、未产生业务记录且历史审核已完成时，修改 A 的标准、增加 C：合并更新 T-A、新增 T-C，T-X 保留。
4. 来源删除 B 后执行普通合并：T-B 保留，并提示存在未处理任务；不会因为请求缺少 B 而删除。
5. 经完整快照预览确认后受控替换：仅在项目未发布、无业务记录和暂存标记、T-B 无引用时清理 T-B；T-X 与所有子项保持不变。
6. 项目已发布，或任一教师已暂存、提交、存在审批：需要新增/更新/删除的请求整批拒绝；完全相同的重复请求仍跳过成功。

可验收的最终状态是：**导入不会消耗来源子项，不会重复生成同一来源任务，不会通过重建主键或自动清理破坏已有填报、佐证和评分记录。**

| 新考核周期或已填报项目改标准 | 建议新建项目或未来引入版本化，不强行修改当前项目 |

本方案不增加任务版本系统、自动重算历史成绩、自动迁移佐证或清理磁盘文件。是否允许教师填报后追加任务、是否撤销旧任务，应作为独立业务变更设计。

### 9.2 SQL 与代码证据，以及冻结规则

以下统计针对仓库导出文件的 INSERT 记录，**不是实时线上统计**：

| 核查对象 | 已核实事实 | 规划影响 |

| `all.sql:1` 导出头 | 标注 MySQL 8.0.35；相关表为 InnoDB | 以 MySQL 8.0 预发验证行锁、可空唯一索引及迁移；上线仍核验真实版本 |
| `all.sql:6985` 项目 | 有项目 46–49，均 status=1；create_name 有工号与 ab 用户名 | 导出中的项目已发布，不能作为新任务变更的试验对象；不能用数字 userId 与 create_name 比较 |
| `all.sql:7011` 子项 | 表结构存在，但没有 INSERT 记录；project_id、score 是 varchar(255) | 不能声称已确认历史任务来自 Excel，也不能恢复来源 ID；需原始值核验 |

| `all.sql:7034` 结果 | 7,720 条 INSERT；存在零分和空证据结果 | 行存在即保护，不以分数/材料/完成标志过滤 |
| `all.sql:14777` 扩展 | 3,670 条 INSERT；有 task_id、result_id，没有 p_id | 同时经任务归属与结果归属检查引用；归属不一致或孤儿引用列入异常报告，关联项目禁止清理 |
| `all.sql:18469` 审批 | 604 条 INSERT；status 有 0/1；实体 ResultItem 使用 @TableLogic | 冻结查询包含所有历史状态，不能只用通用 list/count |
| `ProjectServiceImpl.projectStaging/getProjectStaging` | Redis 键为用户名-项目ID，TTL 15 天；不写结果表 | 增加持久化首次暂存标记并核验旧缓存；all.sql 本身不包含暂存完整信息 |
| `ProjectServiceImpl.resultProject` | 结果保存后删除并重建对应扩展项 | 提交与导入必须共用项目锁，锁内重新验证每个 task_id 的项目归属 |
| `FlowServiceImpl.submitApprove` | 批量改结果并新增审批；打回将历史 status 改为 0 | 审批与导入共用锁，打回不解除任务冻结 |

冻结判断顺序：取得项目锁 → 验证项目身份与状态 → 读取当前任务/来源 → 计算差异 → 若有变化，检查审核状态、首次暂存标记及所有引用 → 允许后整体写入。没有变化的请求仍验证身份、来源存在与项目归属，但不因已发布/冻结而失败。

**生命周期固化：**

- status=0：仅在没有使用记录或暂存标记、历史审核通过时允许任务变化。
- status=1：无论是否已有结果，只允许完全一致的重复请求；需要变更标准则新建项目，不用管理员身份绕过。
- status=3、null、未知值：拒绝导入，不将未知状态视作未发布。
- 项目子项评分内容及分类名称在发布/使用后也禁止影响任务的修改与删除，避免维护端绕过冻结造成来源漂移；此计划不自动把来源变化传播给历史任务。
- 冻结标记不随 Redis TTL、打回、材料删除自动撤销；更改冻结规则属于独立业务变更。

**旧暂存核验：**维护窗口暂停暂存和相关任务写入，通过已知用户与项目构造现有键并查询，必要时使用 Redis SCAN 辅助盘点；不使用生产 KEYS 全量阻塞扫描，也不简单按第一个连字符切用户名。解析 JSON 核验 projectId 与 task_id，记录核验时间和数量；有效缓存回填冻结标记，归属异常或无法核验的项目保持关闭。导出 SQL 缺少子项或缓存，不能据此证明“没有历史填报”。

### 9.3 权限默认规则

`UserServiceImpl.getUserAuthority` 依据 `sys_role.role_code` 生成 `ROLE_...`；`all.sql` 中 admin 的 role_id=2、weight=10，而 `HnkjzyEncode.ADMIN` 为 100。规划使用**有效角色代码 admin**，不采用 `weight>=100`，也不采用中文显示名。使用认证主体的 userId 重读有效用户与角色关系，并校验角色状态；不能接受请求携带的操作人、角色或创建者字段。具体账户有效状态沿用现有认证语义，实施前核验数据库值。

| 操作者 | 第一阶段导入管理权限 |
|---|---|
| 有效 admin 角色 | 全部项目；仍受生命周期、冻结、来源核验限制 |
| 非 admin 且认证 username 等于项目 create_name | 本人项目；仍受上述限制 |
| 非创建者的 dean、clerk、director 或学院行政角色 | 无该项目导入管理权限 |
| 流程的审批人、抄送人、参与教师 | 不因流程关系获得导入管理权限 |
| 未登录、无效主体或无法验证角色/范围 | 拒绝；不默认提升为管理员 |

目前导入、子项新增/修改和子项删除均缺少完整项目授权，必须一并接入同一管理检查。身份可在 Controller 读取 Authentication 后转换成 Service 使用的操作人信息，Service 不反向依赖 `soft_main` 中的 AccountUser。

不为“委派管理员”临时复用 flow.user_id 或 flow_task.role_id。当前若确有非创建者维护需求，由现有 admin 操作；将来需显式项目授权关系后再扩展。新增菜单权限编码不是第一阶段必要条件，不能要求当前数据库不存在的权限导致所有创建者被拒绝。

### 9.4 字段空值、类型、长度与字符集契约

| 字段 | 默认校验/映射规则 |
|---|---|
| project_id | 核验原始值为合法 int 项目 ID，并与请求及父分类一致；非法历史文本进入修复报告，不静默转 0 |
| 分类与子项名称 | trim 后非空；按来源 pname 的 255 字符上限及目标长度共同校验 |
| standard | trim 后非空；当前来源 varchar(255)，不能以目标 4096 为由允许来源写入超长内容 |
| score | 对原始 varchar 做严格整数解析，范围 0–2147483647；拒绝空串、小数、负数、单位文字及溢出；零分合法 |
| is_file / is_extend | null 归一化为 0；非空仅 0/1；此为明确规划默认值，不表示数据库原本都 NOT NULL |
| remark | 可空；空白统一成 null，非空不超过 255 字符 |
| grade / parent_id | 子项 grade=2；父分类 grade=1、parent_id=0；父子同项目；不依赖当前 VO 返回 grade |
| order_by | 仅影响来源展示，当前 Task 没有排序字段；不纳入任务评分差异，也不在本次新增排序能力 |

校验先于映射及任何写入。实施时增加原始来源读取 DTO 或专用查询，避免 varchar 脏值在映射到 ProjectItem.Integer 时先报转换异常，或者数据库隐式转换使错误值变成合法整数。错误返回具体子项 ID/字段，不输出教师信息或材料正文。

`sys_project_item` 使用 utf8mb4，`sys_task` 使用 utf8mb3。第一阶段对目标字符集不能保存的四字节字符明确拒绝，不截断、替换或偷偷迁移整库字符集。来源幂等匹配只使用整数来源 ID；字段差量在应用层按统一空值规则比较，不用数据库的不区分大小写排序规则判断内容相同。可选字段从有值改为空必须显式写入 NULL，不能被 MyBatis-Plus 默认非空更新策略跳过。单次导入暂定最多 1,000 个不同子项，超限整批拒绝；上限在预发按真实数据量验证后调整，不能通过分批绕过完整业务事务。

### 9.5 历史治理、清理阶段与责任

**历史治理：**业务项目负责人提供可信来源说明，数据管理员生成和执行审核后的映射，后端负责人验证唯一性、归属与引用完整性。上述为职责分配，仓库无法给出具体姓名；实施前在核验报告登记负责人。all.sql 的子项表为空时，不生成“名称相同就回填”的自动脚本，不重建假的子项 ID，不改历史 task.id。

审核结果分为已确认子项来源、已确认其他来源、来源未知、重复/引用异常四类。只有第一类回填 source_project_item_id；其他来源仍为 null，审核凭据存入受控迁移报告。来源未知或异常未处理的项目保持待审核，禁止产生新的疑似重复任务。项目审核完成以持久化状态和报告为准，不以“字段为 null 就一定是 Excel”判断。历史发布项目保持冻结，审核映射本身不触发评分更新。

**清理阶段：**第一阶段交付合并与保护，不创建或开放 replace/preview 入口。第二阶段仅在明确需要治理过期来源任务时启动，仍限定未发布、未使用项目；不可将历史有结果项目列入普通清理范围。

| 职责 | 第一阶段/后续职责 |
|---|---|
| 后端负责人 | 合并、授权、事务、冻结状态、锁协议、冲突计数与集成验证；第二阶段实现服务端预览重算 |
| 业务项目负责人 | 来源审核、字段规则验收；第二阶段确认每次清理范围 |
| 数据管理员/发布负责人 | DDL 核验、备份、历史映射执行、缓存核验、停写发布与恢复演练 |
| 前端负责人 | 第一阶段展示计数与冻结原因；第二阶段实现完整快照预览和显式执行 |

第二阶段不能只依赖日志文本恢复删除任务。若启用清理，拟增加独立持久化审计记录，保存操作 ID、操作者、项目、预览摘要、删除前完整任务字段及来源、执行结果与时间，并在任务事务中提交；表结构在该阶段设计。恢复演练保留原 task.id，检查期间新增引用及唯一来源冲突。没有前端预览、持久化快照或恢复演练时，清理入口继续关闭。现有操作日志可记录摘要，不假定其已经支持完整快照。

执行依赖顺序：

1. **只读核验**：真实 DDL、触发器、有效角色、历史任务、旧缓存、所有写入口、引用异常；形成逐项目开放/关闭报告。不能连接线上时保持该门槛未完成。
2. **预发迁移与实现**：来源字段/索引/状态表 → 原始来源校验与主键 → 权限/状态/差量事务 → 所有相关写入口锁和暂存标记 → 执行结果与异常响应。
3. **历史与回归**：审核映射和缓存标记，验证 SQL/实体类型差异、发布状态、纯重试、事务回滚、Redis 失败、跨入口并发及历史查询。
4. **维护窗口上线**：暂停相关写入，备份数据库和必要缓存，迁移并全实例发布，核验通过的项目逐个开放合并；任何来源歧义、旧缓存未核验或锁协议遗漏均阻止开放。
5. **独立可选清理**：有业务需求后才实现预览、快照与恢复；不能提前在第一阶段放一个可调用的删除开关。

整体工作包含跨入口并发和历史治理，原清单 IMP-05 的 0.5d 只适用于极简接口改造，**不作为本计划总工期承诺**。实施前核验完成后按基础实现、写入口联动、历史治理、集成验证、发布演练分别估算；未掌握数据规模前不编造精确天数。
