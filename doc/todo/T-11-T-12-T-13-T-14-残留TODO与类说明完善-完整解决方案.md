### 2.2 T-12：重复审批校验已存在，注释与异常语义待完善

当前 `FlowServiceImpl#submitApprove` 的关键逻辑如下，省略非核心代码：

```java
@Transactional(rollbackFor = Exception.class, isolation = Isolation.READ_COMMITTED)
public void submitApprove(ResultItem resultItem, User user) {
    projectTaskGuard.lock(resultItem.getPId());
    projectTaskGuard.validateTasks(
            resultItem.getPId(), resultItem.getUId(), resultItem.getResults(), true);
    ApproveVo vo = getApproveVo(user, resultItem.getPId());
    if (ObjectUtil.isNull(vo)) {
        throw new RuntimeException("没有审批权限！");
    }

    //TODO 判断是否已审批
    LambdaQueryWrapper<ResultItem> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(ResultItem::getPId, resultItem.getPId())
            .eq(ResultItem::getUId, resultItem.getUId())
            .eq(ResultItem::getUserId, user.getUserId())
            .eq(ResultItem::getStatus, 1)
            .eq(ResultItem::getStep, vo.getSort());
    Integer count = resultItemService.count(wrapper);
    if (count > 0) {
        throw new RuntimeException("已进行审批，不能再重复审批！");
    }
    // 设置服务端审批步骤、审批人，更新结果并插入审批记录
}
```

#### （1）校验维度应完整表达

实际重复判定为：

```text
项目 pId + 被考核用户 uId + 当前认证审批人 userId
+ 服务端解析的审批步骤 sort + 有效记录 status=1
```

因此，同一个审批人对同一被考核用户、同一项目、同一步骤存在有效记录时被拒绝。当前 `getApproveVo` 按步骤升序选取首个匹配当前用户或角色的节点；不同审批人可各自留下记录，提交时直接更新共享结果的步骤，最后一步直接设置完成状态，代码没有等待全体审批人的会签计数。本方案确定保留这种现有行为；不能删除 `userId` 条件，改成“一个步骤只能有一条审批记录”。详细依据见 9.2。

`ResultItem.status` 标有 `@TableLogic`，当前环境配置为 `logic-not-delete-value: 1`、`logic-delete-value: 0`。`isFlag` 表示是否打回，不能用它代替有效性或审批轮次。

#### （2）原清单的“无并发保护”已不符合当前入口

当前源码存在以下链路：

```text
经 Spring 事务代理进入 submitApprove（READ_COMMITTED）
    → ProjectTaskGuard.lock(pId)
    → ProjectTaskGuardImpl.lock（MANDATORY，要求已有业务事务）
    → ProjectTaskImportMapper.lockProject
    → 锁定项目行（Mapper SQL 使用 FOR UPDATE）
    → 校验任务归属、审批权限与已有有效审批记录
    → 更新结果、插入审批记录
    → 提交或回滚后释放项目锁
```

据此可以判断：经该入口提交的同项目审批请求已有数据库项目行锁提供串行保护，不能再描述为完全没有锁。锁粒度是**项目级**，不是只锁某个审批人。

但这仍需实施阶段并发验证，且不能扩展为“数据库无条件保证全系统审批唯一”：绕过锁的其他写入口、手工写库、未来代码以及实际表引擎和事务配置均不在这条入口链路的静态证据内。现有仓库建表脚本使用 InnoDB，部署库状态仍需单独核验。

#### （3）异常响应需要依据现有处理器判断

当前 `GlobalExceptionHandler` 对普通 `RuntimeException` 返回 `ApiResult.error(400, e.getMessage())`，返回类型为 `ApiResult`，未在该处理器设置实际 HTTP 状态。

因此，原清单泛化的“裸运行异常导致 HTTP 500”不能直接套用到这个版本。准确问题是：**预期的权限拒绝与重复审批冲突，均落入通用运行异常处理，通常是默认 HTTP 200 配合响应体 `code=400`，并打印堆栈；缺少明确的 403/409 响应。** 实际接口状态仍需请求验证，不能只看 Java 异常类型猜测。

当前已有 `ProjectTaskException` 及其专用处理器，能同步设置实际 HTTP 状态与 `ApiResult.code`，可定点复用，不必照抄尚不存在的 `BusinessException(ErrorCode.ALREADY_APPROVED, ...)`。

#### （4）服务端有效状态应固定，避免客户端影响重复判定

`ResultItem` 直接作为请求体，`id`、`status` 均可反序列化；当前服务只覆盖 `step` 与 `userId`，没有显式固定 `id` 和 `status`。本方案必须补充服务端 `id=null`、`status=1` 的赋值，避免依赖客户端传值或数据库默认值来产生有效审批记录。同时将仅有非空校验的 `isFlag` 限定为 `0/1`。

这是保证 T-12 有效记录判重与新增记录语义的定点补强，不是引入新的审批轮次或请求级幂等协议。

#### （5）打回后重新审批是已有流程，必须保留

当前打回分支将该项目、该被考核用户的已有审批记录置为 `status=0`，同时更新结果状态并发送打回通知。后续有效记录查询只匹配 `status=1`。

这意味着“曾经审批过”不等于“永远不可再审批”。当前方案以有效记录界定冲突，不引入新的审批轮次模型。尤其是两次并发请求中第一次为打回时，先一次操作已将记录失效，后一次可能再次通过记录计数校验。进一步核对发现，`ProjectTaskGuardImpl#validateTasks` 校验任务、结果和扩展项归属，**不校验结果是否处于待审批状态**；不能将打回重试防护归因于该方法。当前方案明确不提供打回请求的完整重放保护，采用第 9.3 节确定的重试策略，不承诺所有并发提交都恰好只成功一次。

### 方案 2：T-12 将 TODO 替换为准确的校验说明（A）

建议仅替换注释，查询条件保持不变：

```java
// 校验：同一审批人对同一项目、同一被考核用户、同一步骤不得重复提交有效审批。
// 仅检查 status=1 的记录；打回后失效的历史记录不在此范围内。

```

建议在 `submitApprove` 方法说明中补充“在项目行锁与事务内校验并写入；审批步骤和审批人由服务端确定”。不把“已经有校验”误写成“已经有数据库唯一约束”。

### 方案 3：T-12 固定有效记录写入并区分权限拒绝与重复冲突（B）

当前 `FlowServiceImpl` 已使用 `ProjectTaskGuard`，处于项目生命周期业务链。确定复用已有异常及处理器：

```java
if (ObjectUtil.isNull(vo)) {
    throw new ProjectTaskException(403, "没有审批权限！");
}

// 原查询维度保持不变
if (count > 0) {
    throw new ProjectTaskException(409, "已进行审批，不能再重复审批！");
}
```

在任何结果更新、审批插入和打回通知之前，增加 `isFlag` 的 `0/1` 取值校验，非法值抛 `ProjectTaskException(400, "是否打回仅允许0或1")`。`step`、`userId` 继续来自服务端；在插入前明确设置：

```java
resultItem.setId(null);             // 只新增审批记录，主键由现有生成机制产生
resultItem.setStatus(1);            // 本次记录先成为有效记录，不信任请求体状态
resultItem.setStep(vo.getSort());
resultItem.setUserId(user.getUserId());
```

正常通过后保持 `status=1`；打回时继续由现有分支将该项目、对象的记录置 `status=0`。不修改实体字段或数据库默认值，不接受通过请求体 `status=0` 绕过有效记录判重。

| 场景 | 计划后的接口行为 |
|---|---|
| 正常首次审批 | 沿用原成功响应，审批结果、记录及缓存行为保持现有契约 |
| 已进入服务、审批流程无对应权限 | 实际 HTTP 403，响应体 `code=403` |
| 命中已有有效审批记录 | 实际 HTTP 409，响应体 `code=409` |
| `isFlag` 非 `0/1` | 实际 HTTP 400，响应体 `code=400`；不更新结果、不插入记录、不发送打回通知 |
| 数据库错误、保存失败等技术故障 | 不捕获并伪装成“重复审批”，仍交现有故障链路处理 |

**确定的发布验收要求**：前端必须在非 2xx 分支读取 `msg`；403 作为审批权限提示，409 作为当前有效记录冲突提示，均不直接触发重新登录或自动重发审批。仓库未包含前端源码，当前兼容性不能靠后端代码推断；后续实施必须在实际客户端完成联调，未通过时先修复适配再发布 B。后端不新增“兼容 HTTP 200”开关。此处属于已确定的验收标准，不是等待选择方案；本次仍只改计划书。

`GlobalExceptionHandler` 无需新增宽泛兜底处理器；`ProjectTaskException` 已有对应映射。本方案不引入新错误码体系，也不改动全仓 `RuntimeException`。

### 方案 4：保留 T-12 现有锁和事务，验收其实际作用

保留 `projectTaskGuard.lock(pId)` 位于已有记录查询和业务写入之前的顺序，以及 `READ_COMMITTED`、回滚声明和现有缓存注解。核验项目行锁在事务提交或回滚前不会释放。

并发验证分两类：

1. **两次正常通过审批**：同项目、同被考核用户、同审批人、同服务端步骤，两次独立事务同时提交，且首次不打回。预期一个成功，另一个在取得锁后命中有效记录并被拒绝。

### 8.1 不直接采用原清单唯一索引示意的原因

原清单同时出现了基于 `status=1` 的唯一性建议，以及包含 `is_flag` 的索引示意。两者并不等价：

1. `is_flag` 是打回标志，不能代表记录是否有效；把它作为唯一键的一部分不能实现现有校验口径。
2. 直接将 `(p_id,u_id,user_id,step,status)` 设为唯一键，会连 `status=0` 的历史记录一起限制，可能阻断多轮打回后的历史留存。
3. 不含审批人的步骤唯一键会改变多审批人规则。
4. 数据库约束不能替代结果更新、审批记录及状态变更之间的事务一致性。
5. 当前入口已经具有项目行锁，新增约束应先说明它要覆盖的其他写入口和具体业务风险。

因此，确定本次不提供 `ALTER TABLE`，不新增审批轮次、唯一约束或 Redis 锁，也不运行任何去重操作。后续若另立数据库增强任务，必须独立设计审批轮次与有效记录约束、盘点历史数据并制定迁移及回滚方案；它不影响本次 A+B 范围的确定性。

### 8.2 保留的已知边界

- 项目锁可能让同项目不同审批请求排队，这是现有锁粒度的取舍；缩小粒度需连同任务生命周期一致性单独设计。
- 只对有效记录做重复判定，不等于请求级幂等；打回后失效记录尤其需要区分。
- 不因 Service 类说明更完整就承诺接口文档自动变化，自动生成结果需在真实工具链验证。
- 当前角色范围仍遵循既有权重语义，本计划不将注释清理升级为授权政策变更。

## 九、原待确认项的确定方案与代码依据

本节逐项替代原五个问题。**“代码事实”指本次只读核对结果；“实施决策”指在现有契约和本任务范围内采用的确定方案。** 静态代码不能证明客户端已经兼容、插件已经运行或生产验证已经通过，这些内容转为明确的实施验收标准，不再作为选择方案的待确认问题。

### 9.1 A 与 B 同一迭代实施，采用实际 HTTP 400/403/409 契约

**代码事实**：

- `GlobalExceptionHandler#handler(ProjectTaskException)` 已通过 `ResponseEntity.status(e.getStatus())` 同步设置 HTTP 状态与响应体业务码；项目已有专用业务异常契约。
- `FlowController#submitApprove` 调用服务后返回成功，不捕获服务异常，因此定点抛 `ProjectTaskException` 能进入现有处理器。
- `soft_main/src/test/java/com/hnkjzyxy/ab/ResultPermissionHttpTest.java` 已使用 JUnit 5、MockMvc 与真实全局异常处理器验证其他接口的 HTTP 契约，可复用其组织方式。
- 当前仓库未找到前端 `package.json`、Vue/React 入口、Axios 响应拦截器等，不能宣称已核对实际客户端。

**实施决策**：A+B 是本计划完整范围，不新增响应模式开关、不因缺少前端源码改用 HTTP 200 包装失败。后端使用既有项目异常，固定 400（打回标志非法）、403（无流程审批权限）、409（有效记录重复）。客户端的非 2xx 提示与禁用自动重发作为发布验收项目，先在测试环境完成联调，再发布 B；这是交付门槛，不是待选择的业务政策。

### 9.2 多审批人规则固定为保留现有独立留痕及共享结果更新

**代码事实**：

| 代码位置 | 确定含义 |
|---|---|
| `FlowTaskMapper.xml#getFlowStepList` | 按 `sort asc` 读取有效审批节点 |
| `FlowServiceImpl#getApproveVo` | 用户 ID 命中节点的用户集合，或匹配其角色集合时，返回首个匹配节点；没有匹配时返回空 |
| `FlowServiceImpl#isCheckApprove` | 角色集合采用任一匹配，并排除角色 ID `1` |
| `FlowServiceImpl#submitApprove` 的有效记录查询 | 包含当前审批人 `userId`，一个人的记录不自动阻止其他审批人首次留痕 |
| `submitApprove` 中 `setStep` 与 `setIsFinish(1)` | 任一合法提交都会更新请求覆盖的结果步骤；到最大审批步骤时直接设置完成，未等待全部候选审批人 |
| `getProjectFLow` | 同步骤可能查询到多条有效记录，展示按创建时间倒序取出的第一条；展示一条不等于数据库只允许一条 |

**实施决策**：保留用户/角色候选授权、首个匹配步骤、各审批人有效记录判重；不增加全票会签、投票阈值、均分或步骤唯一规则。共享 `sys_result` 按成功事务的写入顺序更新，后一次合法提交可能覆盖请求所携带的评分或步骤，不能在说明中称为“多人分数汇总”。

这里确定的是**保持现有代码契约**，不推断这就是业务方对全部未来流程的意图。当前入口也没有完整的“只能从上一节点推进”状态校验，本次不新增状态机；会签和严格节点推进均排除在 T-11～T-14 技术债治理之外。

### 9.3 重复审批采用有效记录拒绝，不新增请求级幂等与审批轮次

**代码事实**：

- `ResultItem` 没有请求幂等键或审批轮次；目前依赖项目行锁与五维有效记录查询。
- 当前 `id`、`status` 来自可反序列化实体，服务尚未显式固定；这会影响“新增有效审批记录”的前提。
- 打回分支将历史记录置 `status=0`、结果置 `isFinish=3` 与 `step=0`，随后调用 `noticeReturn` 保存通知；旧记录失效后，原计数校验不能区分“旧请求重试”和“合法新一轮审批”。
- `validateTasks` 只校验归属和任务有效性，没有待审批状态判断；`ProjectServiceImpl#resultProject` 在项目锁内保存重新提交结果，但没有轮次令牌。

**实施决策**：

1. 服务端显式固定新记录 `id=null`、`status=1`，继续覆盖审批人和步骤；`isFlag` 只允许 `0/1`。这是 B 的必要补强。
2. 对仍存在有效记录的重复提交，返回 409 并保持业务数据不变。语义是**拒绝重复操作**，不缓存并重放首次成功响应。
3. 保留打回后的历史失效和合法再审批路径，不新增轮次字段、请求 ID、去重表、Redis 去重键或唯一索引。
4. 客户端及调用方不得自动重试 `POST /api/submit/approve`；超时表示结果未知，应先刷新有权限访问的审批列表/目标对象详情，再由用户确认当前状态后决定新操作。403/409 不触发自动重发。
5. 完整“打回请求至多执行一次”不在本次完成声明内：重复打回仍可能产生新的历史记录和通知。本计划不声称单靠禁止自动重试能挡住恶意或手工重放，也不声称已有任务归属检查能阻止重放。

读取路径使用现有审批列表 `/api/project/result` 和审批详情 `/api/approval/result` 的实际授权与参数契约。`/api/project/flow/{pId}` 会绑定当前登录用户为被考核对象，不能直接用它查询其他被考核人的流程状态。若以后需要跨打回轮次的重放保护，应另立包含版本绑定、请求标识和数据迁移的流程一致性任务，本次不以这项增强作为 A+B 的前置条件。

### 9.4 类说明按仓库 Javadoc 约定验收，不依赖 Apifox 插件

**代码事实**：`doc/README.md` 已规定类及字段用 Javadoc 说明职责、公开方法保留 `@param`、`@return`、`@throws`；当前未找到可证明 ApifoxHelper 配置、运行或导出产物的项目文件。Service 实现类也不是 HTTP 路由声明位置。

**实施决策**：T-13 使用方案 5 的首行摘要与正文，保留作者、日期、版本；T-14 保留当前已完整的说明。A 的验收只检查源码 Javadoc 是否准确、无占位、无业务变化。**不安装插件、不新增配置、不要求 Apifox 导出、不承诺修改接口目录。** 本方案无需知道开发者本机是否安装某插件才能实施。

### 9.5 当前生产源码审批写入集中在一个事务入口，保留未调用的旧 Mapper

本次核对范围为各模块 `src/main` 的 Java 与 Mapper XML，按 `ResultItemMapper`、`ResultItemService`、`sys_result_item` 及 `submitApprove` 检索，并追踪每个直接引用：

| 位置 | 当前用途 | 本方案处理 |
|---|---|---|
| `FlowController#submitApprove → FlowServiceImpl#submitApprove` | 唯一检出的 HTTP 审批提交链路 | 保持 Spring 事务代理调用与项目行锁，作为审批写入入口 |
| `FlowServiceImpl` 的 `resultItemMapper.insert` | 当前实际审批记录新增调用 | 在同一事务内保留，并固定服务端字段 |
| 同方法的 `resultItemService.lambdaUpdate` | 打回时失效历史记录 | 保留在项目锁内，不拆成独立事务 |
| `ResultItemMapper#submitApprove` 与 XML 同名 insert | 旧接口声明，SQL 使用 `parent_id`；检索不到当前 Java 调用方 | 不视为活跃写入口；本次不调用、迁移或删除，不以它替代现有 insert |
| `ResultItemServiceImpl` | 仅继承 `ServiceImpl`，没有自定义写业务方法 | 无另一个被检出的调用链；不新增直接从 Controller 调 `save` 的入口 |
| `ProjectController` 的 `ResultItemService` 字段、`ResultServiceImpl` 的 `ResultItemMapper` 字段 | 当前仅有注入声明，未检出其方法调用 | 本次不借机清理字段或扩展修改范围 |
| `ResultItemMapper.xml` 其他查询、`ProjectTaskImportMapper.xml` 审批计数 | 读取审批状态或生命周期使用情况 | 不是写入口，保留 |

**实施决策**：本次无需为已检出业务入口补第二套锁；沿用项目行锁和事务，对 `submitApprove` 完成 B 即可。旧 Mapper 的 `parent_id` 模型与当前实体/建表脚本不同，其存在不是它已被执行的证据，保持原状并不将其纳入当前审批路径。

本结论限于当前仓库的静态直接调用，不覆盖外部脚本、手工 SQL、第三方服务或未来新增入口。未来新增审批写入口必须走同一项目锁、服务端有效字段和业务校验约定，这条约束已经确定，无需等待发现第二个入口后再决定。
