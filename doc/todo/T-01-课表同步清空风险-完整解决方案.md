## 一、问题定性

原 TODO 注释 `// TODO: 在这里添加您需要执行的业务逻辑` 只是表象。真正的问题是**这个方法被接在了两个不该接的地方**，且**执行顺序不可逆**。

### 1.1 原代码的风险链

```java
@PostConstruct
public void executeOnStartup() {          // ① 每次重启都跑
    Thread.sleep(5000);                   // ② 阻塞 Bean 初始化线程
    performTask();
}

@Scheduled(cron = "0 0 3 * * ?")
public void executeDailyAtNoon() {
    // TODO: 在这里添加您需要执行的业务逻辑
    performTask();                        // ③ 每天 3 点跑
}

private void performTask() {
    courseScheduleService.truncateTable();        // ④ 先 TRUNCATE（DDL，隐式提交，不可回滚）
    String dataJson = getClassBoardData("", "");  // ⑤ 再调 OA
    if (dataJson == null || dataJson.isEmpty()) {
        return;                                   // ⑥ 拉不到就 return —— 表已经空了！
    }
    ...
}
```

| 序号 | 风险 | 实际后果 |
|---|---|---|
| ① | `@PostConstruct` 启动即执行 | 每次重启都做一次「清空赌运气」 |
| ② | `Thread.sleep(5000)` | 阻塞 Bean 初始化，拖慢优雅启停 |
| ④ | `TRUNCATE TABLE` 是 **DDL** | 隐式提交，**后续任何异常都无法回滚** |
| ⑤⑥ | 先清空再拉取 | OA 超时 / 返回 `{}` / 返回 HTTP 500 / 业务码非 10000 → 直接 `return`，**表永久为空** |
| — | 无锁 | 多实例部署时 3 点并发 `TRUNCATE` + 批量插入，主键冲突 / 数据错乱 |
| — | 无事务 | 610 条按 100 条分批提交，第 3 批失败留下半张表 |

**关键放大器**：`OaRequestAPIUtils.getClassBoardData` **把异常全部吞掉，失败时返回 `null`**：

```java
} catch (Exception e) {
    System.err.println("调用接口或解析数据时发生异常：" + e.getMessage());
    e.printStackTrace();
}
return dataJson;   // 失败时是 null
```

所以「网络超时」「鉴权失败」「业务码错误」「真的没有排课」在调用方**完全无法区分**——这正是数据丢失最容易被触发的路径。

### 1.2 影响面

`sys_course_schedule` 是**电子班牌 / 门锁**的排课数据源（`CourseScheduleMapper.xml` 中 `selectListByCondition` 被班牌接口调用）。表被清空意味着：

- 班牌当天课程显示为空；
- 门锁的「排课回退授权」判定（`SKRQ = 今天`）全部失败，教师开不了门；
- 数据无备份，只能等下一次 3 点同步成功才恢复，**最长影响 24 小时**。

## 二、修复设计：六道防线

核心思路一句话：**把「先删除再拉取」改成「先拉取、再校验、最后事务内整体替换」，并让任何一步失败都退化为「不动数据」。**

```
        拉起
  ┌───────────────┐
  │ 1 拉取 OA 数据 │  失败/为空 → 抛异常，正式表一个字都不动
  └───────┬───────┘
          ▼
  ┌───────────────┐
  │ 2 分页截断检查 │  条数 == page-size(1000) → 疑似被截断，放弃
  └───────┬───────┘
          ▼
  ┌───────────────┐
  │ 3 逐行字段校验 │  缺必要字段的行跳过并计数
  └───────┬───────┘
          ▼
  ┌───────────────┐
  │ 4 数据量闸门   │  0 条 / < min-rows / 较上次收缩超阈值 → 放弃
  └───────┬───────┘
          ▼
  ┌───────────────┐
  │ 5 事务整体替换 │  DELETE + saveBatch，同一事务，失败整体回滚
  └───────┬───────┘
          ▼
  ┌───────────────┐
  │ 6 结果落库/日志│  结构化日志 + Redis 状态 + 接口返回明细
  └───────────────┘

  ①~④ 全部在锁内执行：
     进程内 AtomicBoolean  →  Redis 分布式锁(Lua 安全释放)  →  Redis 不可用则降级为单机串行
```

### 防线 1：顺序反转（最重要）

**先拉取、后落库**。拉取失败直接抛异常，正式表的数据完全不参与本次操作。

### 防线 2 / 4：数据量闸门

单纯「拉取成功」不足以证明数据可信，必须加量级判断：

| 闸门 | 配置项 | 默认值 | 触发条件 |
|---|---|---|---|
| 空数组保护 | — | — | 有效记录数 = 0 |
| 最小值保护 | `min-rows` | 50 | 有效记录数 < 50 |
| 收缩保护 | `shrink-guard-ratio` | 0.5 | 本次 / 上次 < 50%（例如上次 618 条，本次只有 120 条） |
| 分页截断保护 | `page-size` | 1000 | 返回条数 >= 1000（`per_page=1000` 说明数据被截断） |

> **分页截断是真问题**：`OaRequestAPIUtils` 里 URL 写死 `&per_page=1000`，而当前线上 `AUTO_INCREMENT = 619`。一旦某个学期排课超过 1000 条，旧代码会**静默丢失超出部分**，新代码会直接报错放弃并提示先处理分页。

### 防线 3：DELETE 替代 TRUNCATE

| 维度 | `TRUNCATE TABLE`（原） | `DELETE FROM`（新） |
|---|---|---|
| 类型 | DDL | DML |
| 事务 | 隐式提交，**不可回滚** | 可回滚 |
| 中途失败 | 表永久为空 | 自动恢复到替换前状态 |
| 读一致性 | 存在「表为空的窗口期」 | InnoDB MVCC，**提交前其他会话仍读到旧数据**，无空窗期 |

**副作用说明（不构成风险）**：`DELETE` 不会重置 `AUTO_INCREMENT`。按每天 1 次、每次约 619 条估算，`int UNSIGNED`（上限 4,294,967,295）可用约 1.9 万年，无需处理。

### 防线 5：分布式锁

- **进程内锁**：`AtomicBoolean`，防止同一实例内「定时任务」与「手动刷新」并发；
- **Redis 分布式锁**：`SET key token NX EX ttl`，多实例只有一个能跑；
- **Lua 安全释放**：比对 token 后才 `DEL`，避免误删他人重新获取的锁；
  脚本**独立存放**在 `soft_common/src/main/resources/lua/release_lock.lua`，与加载器同属公共模块，不在 Java 里拼字符串；
- **降级策略**：Redis 不可用时打 `error` 日志并退化为「单机串行」，**不阻断同步**；
- **实现要点**：必须用 `StringRedisTemplate` 而不是项目自定义的 `RedisTemplate`（后者 value 走 Jackson JSON 序列化会带上引号，Lua 里 `get` 出来的值和写入值不相等，**锁永远释放不掉**）。

#### 为什么 Lua 脚本要放独立文件

| 维度 | 内联 Java 字符串（原写法） | 独立 `.lua` 文件（现写法） |
|---|---|---|
| 可读性 | 单行挤在一起，无缩进无注释 | 有缩进、有块注释、有参数/返回值说明 |
| 语法校验 | IDE 无语境，写错了只能运行期发现 | IDE 提供 Lua 语法高亮与检查 |
| 复用 | 只能复制粘贴，容易版本漂移 | 多个工具类共用同一份脚本 |
| 脚本演进 | 改逻辑要重新编译 Java | 改文件即可 |

加载方式使用 Spring Data Redis 的 `RedisScript.of(Resource, Class)`：

```java
private static final RedisScript<Long> RELEASE_LOCK_SCRIPT = loadScript("lua/release_lock.lua");

private static RedisScript<Long> loadScript(String location) {
    ClassPathResource resource = new ClassPathResource(location);
    if (!resource.exists()) {
        // 本类是 @Component，Spring 启动时实例化它即触发静态初始化
        // → 资源漏打包会在启动阶段暴露，而不是等到第一次释放锁
        throw new IllegalStateException("Redis Lua 脚本不存在，请检查资源是否被打包：" + location);
    }
    return RedisScript.of(resource, Long.class);
}
```

#### 资源文件跟随所属模块（2026-10-02 包结构复查更新）

Lua 释放锁脚本位于 `soft_common/src/main/resources/lua/release_lock.lua`，与 `RedisLockUtils` 同属公共模块；加载路径仍为 `classpath:lua/release_lock.lua`。公共模块独立使用时也能加载脚本，不再依赖 soft_main 提供资源。

Mapper 接口与 XML 同属 soft_mapper：`CourseScheduleMapper.xml` 位于 `soft_mapper/src/main/resources/mapper/`，各环境的 `mapper-locations` 使用 `classpath*:mapper/*.xml` 从所有依赖模块查找。

可执行 JAR 中，主模块资源位于 `BOOT-INF/classes/`，依赖模块资源保留在 `BOOT-INF/lib/` 下对应的模块 JAR 内，Spring 通过运行时 classpath 访问它们；依赖资源并不会全部搬入 `BOOT-INF/classes/`。

Lua 仍通过 `RedisScript.of(Resource, Class)` 加载并懒计算 SHA1。脚本跟随 soft_common 的资源配置打包；资源是否存在及内容是否完整需检查该模块 JAR，不能再以 soft_main 的产物路径作为依据。

### 防线 6：启动执行改造 —— 为什么不再用 `Thread.sleep`

| 原实现 | 新实现 |
|---|---|
| `@PostConstruct` + `Thread.sleep(5000)` | `ApplicationRunner`（容器完全启动后执行） |
| 无条件执行 | `@ConditionalOnProperty(sync-on-startup=true)`，**默认关闭** |
| 阻塞 Bean 初始化线程 | 不阻塞 |
| 日志打印到 `System.out` | `@Slf4j` 结构化日志 |

**`Thread.sleep` 放在 `@PostConstruct` 里，三个层面的问题：**

1. **时机错，且是「用时间赌正确性」**。`@PostConstruct` 在 Bean 初始化阶段执行，此时上下文还没 refresh 完，数据源连接池可能没预热、Redis 可能没连上、其它 Bean 的初始化可能还没跑。`sleep(5000)` 赌的是「5 秒应该够了」——没有任何机制保证，纯靠时长设定者的直觉。而它后面紧跟的是**清空全表**，等于把不确定性放在了最危险的操作之前。
2. **阻塞容器主启动线程**。Spring Boot 的 `main` 线程被卡住，启动变慢；容器环境下会拖累 readiness probe 与优雅启停。
3. **不可取消、无超时、无重试**。中断要自己处理 `InterruptedException` 并恢复中断标志（原代码做了这一步，算是唯一写对的地方），但它既不能感知异常，也不能在依赖就绪时提前返回。

**更根本的是：「延迟执行」这个意图本身不该用 sleep 表达。** 按意图选工具：

| 想要的语义 | 正确做法 | 说明 |
|---|---|---|
| 等**容器完全就绪** | `ApplicationRunner` / `ApplicationReadyEvent` | ✅ 本次采用。确定性的等待，不靠猜时长 |
| 等**外部依赖可用** | 带退避的重试（固定 / 指数 backoff）或 `RetryTemplate` | 可设最大次数、超时、可观测；sleep 做不到 |
| **稍后异步**执行 | 异步线程池 / 延迟队列 | 不阻塞任何主流程 |
| **周期性**执行 | `@Scheduled` | ✅ 3 点任务用这个 |

**当前策略**：同步失败即放弃，保留上一轮数据，等下一个周期（每天 3 点）或手工触发。对课表同步而言这是合理的——数据不会丢，只是晚一点。若将来希望「OA 瞬时抖动也能自愈」，正确做法是加**带退避的重试**（例如 3 次、间隔 2s/4s/8s），而不是把 sleep 加回来。

### 3.3 核心代码

**`CourseScheduleServiceImpl#sync` —— 锁 + 编排**

```java
@Override
public CourseScheduleSyncResult sync(String source) {
    if (!syncProperties.isEnabled()) {
        log.info("[课表同步][{}] 同步开关已关闭，本次跳过", source);
        return CourseScheduleSyncResult.skipped("同步开关已关闭");
    }
    String token = acquireLock(source);                 // 进程内锁 → Redis 锁 → 降级
    if (token == null) {
        return CourseScheduleSyncResult.skipped("其他实例正在同步，本次跳过");
    }
    try {
        result = doSync(source);
    } finally {
        releaseLock(token);                             // Lua 比对 token 后释放
    }
    recordStatus(result);                               // 写 Redis，供运维排查
    return result;
}
```

**`replaceAtomically` —— 单事务 DELETE + 批量写入**

```java
private void replaceAtomically(List<CourseSchedule> schedules) {
    int batchSize = syncProperties.getBatchSize() > 0 ? syncProperties.getBatchSize() : 500;
    // 用 TransactionTemplate 而非 @Transactional：同类方法自调用时注解会失效
    transactionTemplate.executeWithoutResult(status -> {
        int deleted = courseScheduleMapper.deleteAll();        // DELETE，可回滚
        for (int i = 0; i < schedules.size(); i += batchSize) {
            int end = Math.min(i + batchSize, schedules.size());
            saveBatch(new ArrayList<>(schedules.subList(i, end)), batchSize);
        }
    });
}
```

**`CourseScheduleSyncJob` —— 只做触发器**

@Scheduled(cron = "${schedule.sync.cron:0 0 3 * * ?}")

## 五、验收用例

### 5.1 数据安全（核心）

前置：`SELECT COUNT(*) FROM sys_course_schedule;` 记为基线 N。

| 用例 | 构造方式 | 断言 |
|---|---|---|
| A-1 OA 超时 | 断网 / 将 `classBoardURL` 指向不可达地址 | 行数仍为 N；日志含「本次同步放弃」；**表内容逐行一致** |
| A-2 OA 返回 `{}`（业务码非 10000） | Mock 返回 `{"code":1,"message":"invalid token"}` | 行数仍为 N |
| A-3 OA 返回 HTTP 500 | Mock 返回 500 | 行数仍为 N |
| A-4 返回空数组 `[]` | Mock 返回 `result.data = []` | 行数仍为 N（不放行「合法的空」） |
| A-5 返回 1000 条 | Mock 返回 1000 条 | 行数仍为 N，日志提示「数据疑似被截断」 |
| A-6 返回 120 条（基线 618） | Mock 返回 120 条 | 行数仍为 N，日志提示「低于收缩保护比例」 |
| A-7 正常返回 615 条 | Mock 真实报文 | 行数 = 615；`SELECT MAX(id)` 递增（证明是 DELETE 非 TRUNCATE） |

### 5.2 并发

| 用例 | 构造方式 | 断言 |
|---|---|---|
| B-1 双实例同时 3 点 | 起两个实例，同时触发 | 只有一台打印「完成」；另一台打印「未获取到分布式锁，本次跳过」 |
| B-2 cron 与手动 `/refresh` 并发 | 同时调用 | 一个执行、一个跳过；**过程中任一时点 `COUNT(*) > 0`** |
| B-3 Redis 停机 | 停掉 Redis 后触发同步 | 打 `error` 日志，同步仍能成功（降级为单机串行），不抛 500 |
| B-4 锁能正常释放 | 同步结束后 `redis-cli EXISTS lock:schedule:sync` | 返回 `0`（证明 Lua 脚本加载成功且令牌比对通过）；若恒为 `1` 说明脚本没被正确加载或用了 JSON 序列化的 RedisTemplate |
| B-5 锁不会被误删 | 手工 `SET lock:schedule:sync other-token` 后调用一次同步 | 同步跳过；锁 key 仍存在且值为 `other-token`（Lua 未删除他人锁） |

### 5.3 事务回滚

## 六、上线与回滚

### 6.1 上线顺序

1. 先确认 `prd` 的 `schedule.sync.sync-on-startup` 为 `false`（**这一步是防事故的关键**）；
2. 发布本次代码（无 DDL，无需停服，可滚动发布）；
3. 发布后**先手工验证一次**，不要等凌晨 3 点：

```bash
# 同步前留底（强烈建议）
mysqldump -uroot -p soft_manage sys_course_schedule > /tmp/course_schedule_bak_$(date +%F%H%M).sql

curl -s "http://<host>:9696/api/courseSchedule/refresh" | jq
# 期望：{"code":200,"msg":"刷新成功","data":{"executed":true,"success":true,
#        "totalRows":615,"validRows":615,"savedRows":615,"previousRows":618,...}}

SELECT COUNT(*) FROM sys_course_schedule;   # 与 savedRows 一致
```

4. 观察 1~2 天后，再决定是否把 `cron` 调整到业务低峰。

### 6.2 回滚

- **代码回滚**：`git revert` 本次提交即可。数据库结构无变更，无需数据订正。
- **数据回滚**：若同步结果不符合预期，用步骤 3 的 dump 恢复；或把 `schedule.sync.enabled` 改为 `false` 冻结同步，再人工修数。

### 6.3 值班关注点

| 日志关键字 | 含义 | 处理 |
|---|---|---|
| `本次同步放弃` | 闸门拦截，**数据是安全的** | 检查 OA 接口 / 阈值配置 |
| `执行失败，正式表数据保持不变` | 同步异常但数据未受损 | 看堆栈定位 |
| `未获取到分布式锁` | 有其他实例在跑 | 正常，多为并发触发 |
| `获取分布式锁异常，降级为单机串行执行` | **Redis 挂了** | 需立即处理 Redis |

## 七、与其他问题的边界

本次只做 T-01，以下问题**明确未处理**，但已预留接口：

| 编号 | 问题 | 与 T-01 的关系 |
|---|---|---|
| **T-02** | OA `key`/`secret` 硬编码明文 | **未做**。T-01 仍在调用静态的 `OaRequestAPIUtils.getClassBoardData`。改造为 `OaApiClient` Bean 时，只需把 `CourseScheduleServiceImpl#doSync` 的第一行换成注入的客户端调用即可，**校验与替换逻辑不受影响**。 |
| **R-04** | `OaRequestAPIUtils` 用 `System.out.println` 打印全部 1000 条报文和 token | **未做**。建议随 T-02 一并改为 `@Slf4j` 并脱敏。当前日志量大，排查时注意。 |
| **R-05** | `TruncateTable` 使用 DDL 无法回滚 | **已解决**（本方案的防线 3 即为此项）。 |
| — | `OaRequestAPIUtils` 吞异常返回 `null` | **未做**。被 T-01 的「null 视为失败」兜住了，但 `null` 无法区分「网络失败」和「真的没数据」。建议 T-02 改造时改为抛异常或返回带状态的结果对象。 |

### 遗留的已知边界（需评估）

1. **全量替换而非增量 upsert**。当前设计是「整表替换」。若后续要保留班牌手工调整过的数据，需要改成按业务键 upsert + 差异删除；`sys_course_schedule` 目前**只有主键 `id`，没有业务唯一键**，要 upsert 必须先加唯一索引（属于改表，需走另一条路线）。
2. **`id` 会持续增长**（不再 TRUNCATE 重置）。按现有数据量估算可用约 1.9 万年，不处理。
3. **单次请求上限 1000 条**。若某学期排课超过 1000 条，同步会被闸门拦下并报错——这是**有意的**（宁可不同步也不能丢数据），届时需要先实现分页拉取。
4. **`refresh` 接口无鉴权**。`/courseSchedule/**` 在 prd 白名单里是放行的，任何能访问该端口的人都能触发同步。建议后续加管理端鉴权或改为 POST + 权限校验。

## 八、待确认项

1. `sys_course_schedule` 的**业务唯一键**怎么定？（`KKXND + KKXQM + SKRQ + SKJC + JSH + BJMC`？）——决定后续能否做增量 upsert。
2. `min-rows` / `shrink-guard-ratio` 的阈值是否合适？当前 50 / 0.5 是基于 dump 中 618 条的量级估的，**开学初期数据量小的时候可能需要临时调低**（例如假期只有几十条课）。
3. 学期结束后课表是否应该清空？如果「假期 0 条」是正常状态，则闸门会一直拦住同步——需要按学期切换策略或增加「允许空数据」的开关。
4. 是否需要把同步结果落库（同步历史表）而不只是写 Redis？影响可观测性的持久化程度。
