### 1.2 当前代码的问题链

```text
认证用户 → 查最高有效角色 → 查询项目对应 CC 流程节点
    → 每个节点解析 u_id / role_id JSON
    → 每个角色查用户，合并成该节点的接收人集合
    → 每个接收人判断可见范围
    → 每个接收人查项目、用户、状态、分数并组装 VO
    → 全部 VO 在 Java 按 score 降序排序
    → 为全部记录设置 rank=1、2、3……
    → PageUtils.subList 截取当前页 → 返回 total / list
```

普通教师分支不同：先从 `sys_result` 查询本人已有结果的去重项目 ID，再逐个查项目及分数。它目前没有应用 `projectId` 和 `roleId` 过滤，不能直接用管理人员的接收人 SQL 替换而不说明行为差异。

| 问题 | 根因 | 影响 |
|---|---|---|
| 全量占用应用内存 | 分页之前已创建全部 VO | 每次请求的结果对象数量随候选记录数增长，并发请求进一步放大堆占用及 GC 压力 |
| 循环查询放大耗时 | `addProjectVos` 与权限判断内部多次查库 | SQL 往返次数随接收人、流程节点、角色数量增长；小页也承担全量查询成本 |
| 全量 Java 排序 | 数据库没有按最终分数排序分页 | 对 N 条候选记录进行约 `O(N log N)` 排序；全量结果对象空间约 `O(N)` |
| 同分次序不稳定 | 仅按分数排序，候选集合含 `HashSet` | Java 稳定排序不能保证来自无序集合的同分输入顺序；重复请求可能出现翻页漂移 |
| 跨节点重复展示 | 每个节点独立去重，节点之间未去重 | 同一教师、同一项目经多个 CC 节点命中时可能出现多行、重复占排名 |
| 总页数缺失 | `PageUtils` 忘记返回已计算的值 | 前端需自行计算，分页响应不完整 |
| 参数边界缺失 | `int` 默认值不等于合法性校验 | `page<=0`、`limit<=0`、超大页大小及乘法溢出缺少统一处理 |
| 状态不确定 | `LIMIT 1` 无排序 | 同一项目、用户的结果状态不一致时，换执行计划可能换到另一条状态 |

**风险定级仍为 P2**：当前已具备分页功能，主要缺陷是可扩展性及返回契约。本文没有线上响应时间、内存峰值或事故数据，不据此声称已经发生 OOM。

### 1.3 对原总清单的必要校正

1. **全局排名不是天然错误。** `rank` 在截页前赋值，第 2 页首条为 `limit+1` 正好符合全局顺序编号。改变页大小，只要筛选结果和排序不变，同一记录的排名不应变化，只会改变所在页。
2. `score` 当前两条组装分支均有 `null → 0` 兜底，排序 NPE 不是已经确认的主问题；新方案继续将空分数归零。
3. 实际项目名称字段为 `sys_project.title`，**没有 `project_name`**；总分来自 `sys_result.score` 聚合，**没有 `total_score`**。
4. `sys_flow_task` 通过 `parent_id → sys_flow.id → sys_flow.p_id` 关联项目，**不能写成 `ft.project_id=p.id`**。
5. 当前时间条件是 `p.start_time <= 查询开始时间`、`p.end_time >= 查询结束时间`，表示“项目覆盖查询区间”；原示例的反向比较会改变筛选结果。
6. 接收人必须按项目和有效 CC 节点关联。把各项目接收人合成一个全局 `visibleUserIds` 再与所有项目连接，会把 A 项目接收人错误配到 B 项目。
7. 原示例 `com.hnkjzyxy.ab.vo.ProjectVo` 包名正确，但查询参数实际在 `params` 包；示例不能直接照抄为实现。

相关表的文本字段使用 `utf8mb3_general_ci`，因此昵称的字面匹配不能默认依赖大小写不敏感的普通 LIKE；时间字段为 TIMESTAMP，实施时要核对 JDBC / 数据库会话时区与原接口保持一致。

## 二、解决方案设计

推荐采用 **服务端确定权限范围 → SQL 生成候选项目与用户关系 → 按项目、用户汇总分数及状态 → SQL 过滤、排序、COUNT、LIMIT → Java 只给当前页设置排名**。

实施第一阶段保留现有角色分支的有效行为，明确记录原逻辑缺陷；独立的权限政策调整不得混入分页替换。响应保持原顶层结构，增加分页元数据。

### 2.1 先固化接口契约与排名语义

| 项目 | 计划口径 |
|---|---|
| 展示单位 | 默认采用 `(projectId, userId)` 一行；一个项目一个教师的总分及状态，不是单条任务分数 |
| 排名范围 | **当前登录用户可见、当前筛选条件命中的结果全集**；不是跨权限范围的全校绝对名次 |
| 同分规则 | 仍按顺序编号，使用 `score DESC, projectId ASC, userId ASC`；同分不并列、不跳号 |
| 分页排名 | `rank = (page - 1) × limit + 当前页内序号`，页内序号从 1 开始 |
| 总数 | 满足全部权限和筛选条件的展示记录数；不是结果明细条数或教师去重人数 |
| 空结果 | `total=0, totalPage=0, list=[]`，保留请求的合法 `page / limit` |
| 超出末页 | `list=[]`，保留真实总数；不自动回到首页 |
| 分数 | 保留 `SUM(sys_result.score)`，空值归零，不额外添加 `is_finish=1` 条件 |
| 时间 | 可选，保留“项目覆盖查询时间区间”；开始时间晚于结束时间时拒绝请求 |
| 用户来源 | 登录身份来自认证；请求中的 `userId` 不能指定操作人、扩大权限或替换本人 |

该排名口径与 [T-04 计划书第 9.7 节](T-04-项目子项导入任务与原有数据清理-完整解决方案.md) 一致。对于同分 90、90、80，排名为 1、2、3，而不是 1、1、3。

**跨 CC 节点去重是显式行为修正**：旧实现可能将同一 `(projectId,userId)` 放入多次，而 VO 没有填入可区分的流程节点 ID。默认新方案按项目、教师去重，避免重复计数和排名。发布前须输出受影响节点及差异；如业务实际要求逐节点展示，则必须把 `flowTaskId` 纳入行标识、排序和 COUNT，调整本方案后再实施，不能悄悄减少记录。

本快照每项目只有一个有效 CC 节点，跨节点重复数为 0，按该规则去重不会减少当前候选 362 个组合。用户角色关联确有重复，因此接收展开去重依然必要。

### 2.2 权限范围下推：保留实际判断，避免按注释猜范围

新增 `ProjectAssessScope` 表达本接口的范围，由服务层用当前认证用户及数据库角色构造；Mapper 不接受前端传入的权限范围。

| 现有分支 | 当前实际判断 | 第一阶段 SQL 范围 |
|---|---|---|
| 最高有效权重 `>=20` | 查看符合条件的有效 CC 接收人 | `ALL_RECIPIENTS`，仍必须命中具体项目接收关系 |
| 最高有效权重 `=9` | `checkDeanRoles`：双方共享至少一个非权重 1 角色；内部并未建立学院与教研室关系 | `SHARED_ROLE_RECIPIENTS`，用角色关联 `EXISTS` 等价表达；**不声称已保证学院隔离** |
| 最高有效权重 `=5` | 双方共享至少一个权重 2 角色 | `SHARED_DEPARTMENT_RECIPIENTS`，保留对应判断 |
| 最高有效权重 `<5` | 本人已经存在结果的项目 | `SELF_RESULTS`，只用认证用户 ID |
| 无有效角色、权重为空 | 当前可能 NPE | 返回明确的无权访问业务错误，禁止退回全量 |
| 其他权重 | 当前无分支，空结果 | `NONE`，返回空页；不推导新的访问能力 |

注意：`DEPARTMENT` 和 `COUNSELLOR` 在当前枚举中都是权重 2；最高有效权重又受真实角色表值影响。这些都是旧授权口径的限制，不能只凭权重或“院长”“教研室”字样判断新权限。

实际权重现已由 all.sql 确认：`admin=10`、`dean/clerk=9`、`director=5`，快照没有 >=20 的角色。本表的全量分支保留代码兼容性，不能把它描述为当前有真实账号命中；管理员空列表问题按 1.5.2 节独立登记。

第一阶段辅助角色关系按现有 `getRoles` 语义翻译；若改为只允许有效角色或使用 `role_code / college`，属于权限收紧与授权规则变更，要单独列出差异、同步验收。院长真实学院隔离的缺陷应与 [T-05/T-06 权限计划](T-05-T-06-权限校验空指针与角色判定口径不统一-完整解决方案.md) 衔接；已有成绩查询范围不能未经核验直接套到本接口。

COUNT 与数据 SQL **共用同一候选关系、权限条件和筛选条件**。没有范围时 SQL 显式返回零行；不能通过“省略 WHERE”表示缺少权限。

### 2.3 接收人关系在数据库内展开，避免全量用户 ID 列表

当前接收人存于 `sys_flow_task.u_id / role_id`，内容为 JSON 数组字符串。推荐在 MySQL 8 环境通过 `JSON_TABLE` 展开：

```text
已筛选项目 p
    → 有效流程 f（f.p_id=p.id、f.status=1）
    → 有效 CC 节点 ft（ft.parent_id=f.id、ft.status=1、ft.type='CC'）
    → 直接接收人：展开 ft.u_id，得到 (p.id,userId)
    → 角色接收人：展开 ft.role_id，连接 sys_user_role / sys_user
    → UNION，按 (projectId,userId) 去重
    → 服务端可见范围约束
```

用户提供的实际结构文件 `soft_main/src/sql/softmanage.sql` 明确记录源库和目标库为 MySQL **8.0.35**，据此将 `JSON_TABLE` 确定为本计划的主方案，**不需要升级 MySQL 或修改接收名单字段类型作为实施前提**。测试及预发环境应采用相同版本验证；发布时记录 `SELECT VERSION()` 作为环境一致性检查，而非继续将已提供的数据库版本视为未知。驱动 8.0.19 与服务器 8.0.35 是不同信息，不混用。

`JSON_TABLE` 的关系展开语法依据 [MySQL 8.0 官方文档](https://dev.mysql.com/doc/refman/8.0/en/json-table-functions.html)。下面为设计示例，不是本次已落地的 Mapper：

```sql
SELECT p.id AS projectId, jt.userId
FROM sys_project p
JOIN sys_flow f ON f.p_id = p.id AND f.status = 1
JOIN sys_flow_task ft ON ft.parent_id = f.id
    AND ft.status = 1 AND ft.type = 'CC'
JOIN JSON_TABLE(
    ft.u_id, '$[*]' COLUMNS (
        userId INT PATH '$' ERROR ON EMPTY ERROR ON ERROR
    )
) jt ON TRUE
WHERE p.status <> 3
  -- 实施时加入绑定的 projectId / 时间条件；与角色展开分支共用
```

角色展开分支对应 `roleId INT PATH '$'`，随后连接 `sys_user_role ur ON ur.role_id=jt.roleId` 与存在的 `sys_user`。接收关系必须始终带着 `projectId`，不能只返回无项目关联的用户 ID 集合。

**实施前数据审计**：检查活动 CC 节点字段是否为合法数组，是否含 `null`、对象、浮点数、非整数字符串、超范围 ID 或不存在用户；正常无接收人使用 `[]`。历史 SQL NULL、空串及数字字符串需与当前 Fastjson 行为对照，明确兼容规则或经业务核验订正。JSON 的类型转换可能容忍部分格式，不能把 `ERROR ON ERROR` 当作完整的数据校验。

本快照已经完成这项格式核对：19 个节点的接收字段均为整数数组，活动 CC 无格式异常；实施前审计只需覆盖快照之后的新增及变更。正常数据无需预先迁移或改为原生 JSON 列。

不使用“非法 JSON 自动替换为空数组”隐藏异常；运行时结构错误应产生可定位的业务错误，不返回一个看似正常的缺失列表。格式修复须另留记录，本文不执行修复。

仅当其他部署环境与提供的 MySQL 8.0.35 基线不一致、不能执行该查询时，才评估“按节点批量解析、只传递项目与用户 ID 对”的过渡方案，批量查用户与分数，降低循环查询。该方案仍有全量候选集合成本，**不能作为 T-10 已完全解决的验收结论**；当前实际结构对应的主方案仍为数据库展开，不默认增加接收关系表或写入链路。

### 2.4 按候选项目、用户汇总结果，防止连接放大分数

设 `candidate` 为已经按权限及基础筛选生成的去重 `(projectId,userId)` 关系。先关联候选关系，再聚合结果；不要先把全部角色、流程节点与结果明细直接连接后 `SUM`。

```sql
-- 设计片段：candidate 在最终 XML 中由共享查询片段构成
SELECT c.projectId, c.userId,
       COALESCE(SUM(r.score), 0) AS score,
       MIN(r.id) AS firstResultId
FROM candidate c
LEFT JOIN sys_result r
       ON r.p_id = c.projectId AND r.u_id = c.userId
GROUP BY c.projectId, c.userId;
```

这样一个用户同时通过直接接收与多个角色命中，或者同项目存在多个 CC 节点，都不会把总分乘倍。`sys_result` 一人一项目允许多条任务记录，**不能为 `(p_id,u_id)` 添加唯一索引**。

继续保留无结果的管理分支接收人：总分 0、状态 0。不能把 `LEFT JOIN` 后的结果条件放到 WHERE 导致这些人消失。

#### 状态取值的明确计划

现有状态为“任意首条 `is_finish` 等于 1 则显示 1，否则显示 0”，既不是所有任务完成，也不是有一项完成。为使分页与状态筛选稳定，计划按 **最小结果主键 `id`** 对应的 `is_finish` 取值，再映射成 0/1；无结果为 0。

这属于消除未定义取值的修正。all.sql 中 193 个项目、用户组合内部状态均一致，当前快照没有混合状态，因此该确定化规则不会改变本快照展示的 0/1 状态。实施前补核快照之后的混合状态及返回差异。若业务实际要求“全部完成”或“任一完成”，另改契约及验收；**不能擅自用 `MAX(is_finish)` 或 `MAX(is_finish=1)` 替代**。计数和分页必须应用同一个派生状态筛选。

总分使用 `SUM(score)` 的现有口径。MySQL 聚合行为可参见 [官方聚合函数说明](https://dev.mysql.com/doc/refman/8.0/en/aggregate-functions.html)。数据库总分与偏移量可能超出 Java `Integer`，内部用宽类型接收并检查；保持原 VO 字段类型时使用范围校验，超范围报明确错误，不能直接强转截断。

### 2.5 所有过滤都在分页之前生效

| 参数 / 条件 | 计划行为 |
|---|---|
| `projectId` | 可选，非空需正数；统一用于管理与本人分支。补齐普通教师分支目前遗漏的过滤，作为显式行为修正 |
| `roleId` | 可选，非空需正数；通过目标用户角色 `EXISTS` 过滤，并与权限取交集；本人分支也应用 |
| `nickName` | 保留字面子串匹配；`null` 表示不筛选，空串对应旧 `contains("")` 行为；不自动 trim 改变输入 |
| `status` | 只允许 0 / 1；基于前述派生状态过滤 |
| `startTime / endTime` | 分别应用已有方向的比较；没有参数就不加条件 |
| 删除 / 失效状态 | 管理分支保留项目非删除、有效流程和 CC 节点条件；本人分支计划补齐 `p.status<>3`，避免已删除项目以空名称展示，需记录返回差异 |

昵称原先使用 Java `String.contains`，`LIKE CONCAT('%',参数,'%')` 会把 `%`、`_` 当通配符，默认数据库排序规则还可能忽略大小写。建议用字节敏感的 `LOCATE(CAST(#{param.nickName} AS BINARY), CAST(u.nick_name AS BINARY)) > 0` 保留字面含义，并覆盖中文、大小写、空串及空昵称测试；不直接换成宽松 LIKE。

`ProjectQueryParam` 现有 `projectId / userId` 的 `@NotNull` 与当前实际可选使用并不一致。本方案默认保持 `projectId` 可选、认证确定操作人；不要只给 Controller 添加 `@Valid`，导致原来不传这些参数的查询突然失败。实施时整理为与真实契约一致的约束，服务层也做分页和范围校验。

### 2.6 显式 COUNT + 数据 LIMIT，规避老分页插件复杂 SQL 改写

仓库使用 MyBatis-Plus **3.2.0**，已经注册旧版 `PaginationInterceptor`。本方案不升级框架，不引入新版 `PaginationInnerInterceptor`。

对于 JSON 展开、UNION、聚合和权限 EXISTS 组成的查询，第一阶段推荐使用普通 Mapper 方法显式执行 COUNT 和 LIMIT，不依赖插件自动改写复杂 COUNT，也不再传 `IPage` 让插件重复加分页：

```java
long countAssessList(@Param("param") ProjectQueryParam param,
                     @Param("scope") ProjectAssessScope scope);

List<ProjectVo> selectAssessListPage(
        @Param("param") ProjectQueryParam param,
        @Param("scope") ProjectAssessScope scope,
        @Param("offset") long offset,
        @Param("limit") int limit);
```

```xml
<!-- 结构示意：最终片段须包含完整候选、聚合、状态及过滤逻辑 -->
<select id="countAssessList" resultType="java.lang.Long">
    SELECT COUNT(*) FROM (
        <include refid="assessFilteredRows"/>
    ) q
</select>

<select id="selectAssessListPage" resultMap="assessPageResultMap">
    SELECT q.* FROM (
        <include refid="assessFilteredRows"/>
    ) q
    ORDER BY q.score DESC, q.projectId ASC, q.userId ASC
    LIMIT #{offset}, #{limit}
</select>
```

COUNT 包裹的是“一项目一用户”的最终过滤结果，**不能 COUNT 原始结果明细、流程节点或 UNION ALL 展开的接收记录**。结果显式映射原 `ProjectVo` 字段与时间格式；不顺带加载 `assessList`。

SQL 值全部用 `#{}` 绑定；必须传集合时用 `<foreach>`。不使用 `${visibleUserIds}`、`${orderBy}` 等请求字符串拼 SQL，排序字段和方向写为服务端固定表达式。

两次 SELECT 在同一短只读事务、同一 InnoDB 可重复读快照与连接上执行，避免一次请求内 COUNT 与列表读到不同快照；实施时核验实际事务隔离级别及数据源路由。需要一致时由实际代理生效的 Service 入口开启事务，不能靠同类自调用注解或 `readOnly=true` 单独保证。

**SQL 下推仍有数据库成本**：分数排序通常需要聚合并排序候选结果，深页 OFFSET 还会跳过很多记录。这里的承诺是应用不再拉取全部 VO、不再循环逐人查询；不承诺数据库只扫描 `limit` 行或总耗时为 `O(limit)`。

### 2.7 当前页排名、边界校验和响应兼容

建议默认 `page=1 / limit=10`，`1<=limit<=100`，`page>=1`；非法输入返回参数业务错误，不默默改成合法值。页大小上限 100 是本计划建议，实施前与前端现有选择项核对。

```java
// 计划流程伪代码；不是本次提交的实现
validateQuery(param);
ProjectAssessScope scope = scopeResolver.resolve(authenticatedUser);
long offset = ((long) param.getPage() - 1L) * param.getLimit();
long total = projectMapper.countAssessList(param, scope);
long totalPage = total / param.getLimit()
        + (total % param.getLimit() == 0 ? 0 : 1);
List<ProjectVo> list = offset >= total
        ? Collections.emptyList()
        : projectMapper.selectAssessListPage(param, scope, offset, param.getLimit());
for (int i = 0; i < list.size(); i++) {
    list.get(i).setRank(Math.toIntExact(offset + i + 1L));
}
return ApiResult.ok(buildPageMap(total, totalPage, param, list));
```

页码和页大小先转 `long` 再计算。`offset>=total` 不执行数据 SELECT，直接返回空页，避免超大无效偏移查询。超出当前 `rank` 字段容量时给出受控错误；如果真实规模要求 `Long rank`，需单独调整前后端类型契约。

保持响应顶层的 `code / msg / total / list`，新增 `totalPage / page / limit`：

```json
{
  "code": 200,
  "msg": "success",
  "total": 25,
  "totalPage": 3,
  "page": 2,
  "limit": 10,
  "list": [
    {"projectId": 46, "userId": 185, "score": 90, "rank": 11, "status": 1}
  ]
}
```

示例省略其他 VO 字段及页内后续记录，不代表只返回一条。实际继续返回原字段和日期格式。

本接口改为自行构建数据库分页响应后不再调用 `PageUtils`，局部解决 R-03。`FlowServiceImpl` 等仍使用该工具；全局补齐工具返回值作为独立小改动回归，不强行纳入此次 SQL 替换，也不声称全仓 R-03 都已完成。

原 `ResultMapper.findTotalScore / findResultStatus` 可能仍有其他调用，不因本接口改造删除或全局改变语义。`PageUtils`、`SourceConfig`、POM 默认不修改。

### 3.3 数据库与索引（实施时评估）

按用户提供的实际结构，`sys_result / sys_user_role / sys_flow / sys_flow_task` 均仅有主键，本接口涉及的关联和筛选列目前没有辅助索引。索引评估因此有明确结构依据；发布前用 `SHOW INDEX` 复核是否在提供结构之后发生变更，并结合实际执行计划确定最终组合：

| 表 | 候选非唯一索引 | 目的 |
|---|---|---|
| `sys_result` | `(p_id,u_id,id)`；必要时比较 `(u_id,p_id)` | 项目与用户聚合、代表结果取值及本人项目查询；实际结构仅有 `PRIMARY KEY(id)` |
| `sys_user_role` | `(role_id,user_id)`、`(user_id,role_id)` | 角色接收人展开、可见范围和目标角色筛选；实际结构仅有 `PRIMARY KEY(id)` |
| `sys_flow` | `(p_id,status)` | 筛选项目的有效流程；实际结构仅有 `PRIMARY KEY(id)` |
| `sys_flow_task` | `(parent_id,type,status)` | 筛选有效 CC 节点；实际结构仅有 `PRIMARY KEY(id)` |

这些是候选，不要求全部添加；避免与已有索引前缀重复。按读写负载比较额外索引空间和写入开销，确定后独立编写迁移与回退脚本。JSON 字符串展开和聚合分数排序不会因为普通索引就变成直接索引分页，最终以执行计划与压测为准。

`sys_role.role_code` 已有唯一索引，无需重复添加；`sys_user.user_id` 已是主键，无需单列重复建索引。`sys_user_role` 的复合索引采用非唯一索引，不顺带强制清理重复角色关联；`sys_result` 不建立项目、用户唯一约束。结构文件包含 `DROP TABLE`，只用作结构依据，实施时单独编写必要的 `ALTER TABLE ... ADD INDEX` 迁移，不把整份导出文件当作索引发布脚本。

## 四、实施顺序与环境核验

1. **固定现状证据**：以用户提供的 `softmanage.sql` 为结构基线，记录源码版本和发布环境一致性检查；补采候选规模、现有分页响应，导出典型账户和筛选条件的结果作为数据基线。

3. **实现范围与查询**：建立本接口 scope；实现项目绑定的接收关系、本人与管理分支、聚合及共享过滤；先验证 COUNT 和全局有序结果正确，再接入 LIMIT。
4. **替换 Service 分页**：加入边界校验、同快照读取、当前页 rank 和顶层元数据；移除本接口全量 VO 组装与 TODO。
5. **测试与性能验证**：通过第五章用例；确认数据查询有 LIMIT、无循环逐人 SQL，再根据计划评估必要索引。
6. **灰度发布与观察**：单实例或小流量发布，对照典型账号与预发基线；通过后全量发布并填写验证记录。

无新增必需环境变量；沿用现有数据源和 MyBatis 配置。若为过渡采用旧接口 fallback，必须单独标记部署方式，不在生产每次请求中同时运行两套全量查询。

原 IMP-07 的 **1.5d** 只能作为原始粗估；JSON 数据治理、权限等价验证与复杂 SQL 压测均会影响工作量。实施前核验后按查询实现、回归、性能验证和发布分别估算，不承诺未经评估的精确工期。

### 5.4 性能验证与放行标准

先使用真实快照关系验证正确性：现有 4 项目、7,720 条结果明细、362 个接收组合；该规模本身不代表已经出现显著性能事故。再在隔离测试库生成 **1 万名教师** 的扩展样本，比较 1 千 / 1 万 / 5 万名教师及多个项目、角色和结果明细组合。单页分别用 10 / 100 条；覆盖首页、中间页、深页和超页。结果明细规模单独登记，不能把快照全部 2,117 名用户当成参评教师数，也不能把计划中的合成规模写成真实数据量。

在相同 JVM 堆、数据库、索引、硬件和并发条件下，先预热，再重复采样，比较旧版和新版：

| 指标 | 必须证明的目标 |
|---|---|
| 应用结果对象数量 | 本次数据查询读取的 VO 不超过 limit，不再构造全集 VO |
| SQL 往返 | 角色范围查询次数有固定上界；列表至多 COUNT + 一次数据查询，无逐教师 SQL 循环 |
| SQL 内容 | 数据查询包含实际 LIMIT 和固定 ORDER BY；COUNT 有一致范围 / 筛选 |
| 正确性 | 静态数据下，各页合并结果等于按新契约生成的全集，无跨项目串人、重复聚合或未授权记录 |
| 延迟 | 记录 p50 / p95 / p99；建议 1 万样本首页 p95 比旧版下降至少 50%，作为待基线核定的目标，不是效果承诺 |
| 堆与 GC | 用请求分配量、GC 日志或分析工具证实无全量 VO 分配；不以一次 Runtime.freeMemory 差值作可靠峰值 |
| 数据库负载 | 记录执行计划、扫描行数、排序 / 临时表、CPU；同负载下无不可接受退化 |

若延迟未达核定目标、权限或统计错误、出现全量 VO 或循环逐人 SQL，则不放行。数据库方案性能不达标时调整查询与索引，不能仅凭 Java 端有分页对象就宣布完成。

## 六、上线与回滚

### 6.1 上线顺序

1. 复核 softmanage.sql 的结构及 all.sql 数据统计之后的变化，保留快照基线与增量差异；确认管理员空页是继续保持还是独立授权变更，登记所有行为修正和受影响记录。
2. 如需索引，先在预发演练 DDL，评估锁等待、空间、耗时及回退；不默认声称在线加索引完全不阻塞。
3. 在预发通过典型账户、新旧响应兼容、静态全量结果对照及性能验收。
4. 小范围发布，观察接口错误率、延迟、数据库负载、统计与排名；通过后全量发布。
5. 形成实施记录，写明真实数据规模、对比指标、索引选择、发布版本和遗留权限边界。

### 6.2 回滚

第一阶段只改变查询，代码回滚可恢复旧接口行为，无业务数据迁移需要回撤。额外非唯一索引可暂时保留；若确实造成写入退化，按单独索引回退脚本处理，避免紧急回滚时临时猜测索引名称。

回滚会恢复全量内存分页、缺少新增元数据，以及旧重复 / 状态不确定行为；若前端已依赖 `totalPage`，需同时准备兼容处理。JSON 历史订正如实际发生，必须独立备份与审计，不因代码回滚擅自还原成非法数据。

### 6.3 运行观察

记录接口耗时、COUNT 与数据 SELECT 耗时、请求 page/limit、结果 total 和返回条数；慢查询重点检查角色展开、候选量、聚合及深页跳过成本。异常日志包含可定位的项目 / 节点 ID，不打印全量教师名单或结果报文。

业务数据持续变化时，两个分页请求之间可能因成绩、接收名单变化出现名次移动。固定排序及同请求快照只保证静态结果和单请求一致性；需要多页冻结排名时，应另行设计快照版本，而不是增加不完整缓存来掩盖变化。
